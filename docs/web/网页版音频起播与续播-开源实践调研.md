# Biu 网页版音频起播与续播：开源实践调研

> 2026-10-13；只读调研，基于本地 `master` 的 `d6ae20a`。没有改动播放器、代理或部署，也没有进行线上真实播放验收。本文给开发者定位与选型，不把静态代码推断写成线上根因。

## 结论

1. **目前没有证据证明“被 B 站限流”。**慢可能发生在分集/元数据、WBI `playurl`、同源代理、CDN 首字节、浏览器解码/手势、后台恢复任一环。先按一次播放意图分段计时，记录 HTTP 状态与 B 站业务码，再决定动哪一层。
2. **不需要从零引入“音频代理”。**当前 Web 已有同源 BFF、会话绑定的短期媒体 token、Range/206 转发、源站 Referer、PCDN 排除、换源和 25 秒前预取下一首 URL；要查的是这些机制在“长时间暂停”和“频繁切歌”时的实际表现。[本地代理](../../web-server/media-proxy.ts)、[请求/响应转发](../../web-server/proxy-common.ts)、[播放日志](../devlog/2026-Web版.md)。
3. **最值得先核查的静态风险：活跃标签页把已过期的代理 URL 当作永久有效。**`isUrlValid()` 对所有同源代理 URL 直接返回 `true`；服务端 token 只存在内存，最多两小时、且不晚于上游 `deadline`，过期/服务重启会使旧 token 返回 404。新页面持久化恢复时已剥离 token，故“刷新后的恢复”和“同一标签页后台放置很久后的恢复”是两条不同路径，不能混为一谈。[客户端有效性](../../src/common/utils/audio.ts)、[服务端 token](../../web-server/media-token-store.ts)、[队列落盘脱敏](../../src/common/utils/playback-url.ts)。这是**代码可证的失效组合**，但是否命中用户最近的卡顿仍需事件日志。
4. **现阶段更适合借成熟播放器的机制，不宜直接换播放内核。**特别借鉴 `SegmentBase` 精确索引、主/备 CDN 的有界切换、启动分段 trace；但 Biu 的 iPhone 原生直连曾实测前摇长，现有 MSE 快速 seek 有已记录的约束，不能为了后台恢复把 iOS 一律退回原生 `<audio>`。[踩坑记录](../ideas/005-Web版手机播放.md)。

## 现有链路与历史：先别重复造轮子

`点歌/续播 → （缺信息时）view 或 pagelist 取 cid → WBI playurl JSON → BFF 将音频 CDN URL 改写为会话 token → PC <audio> / iOS ManagedMediaSource → 同源 BFF Range → B 站 CDN`。`playurl` 返回的是含 `dash.audio[].baseUrl/backupUrl/SegmentBase` 的 **JSON，不是 MPD 文件**。[取址类型](../../src/service/player-playurl.ts)、[URL 选择](../../src/common/utils/audio.ts)、[JSON 改写](../../web-server/media-response.ts)。

### [Gemini's response]（2026-10-13，用户 Chrome 新对话；仅作署名输入）

Gemini 初答主张“同源流式代理 + Range + 原生 `<audio>`”优先于手写 MSE，建议分辨取址 API、媒体代理、浏览器手势与后台生命周期的耗时。追问证据后，它撤回了“`playurl` 直接给 MPD”“过期必为 403”“原生 audio 完美解决后台”“本机时钟调快即可测 URL 过期”“空白音频解锁后异步换源必成功”等绝对化说法，也承认初答引用的 Kikoeru `AudioController.ts` 路径是编造的。第二答给出的 `github.com/Jmiao11/bili-music` 在本轮独立打开和 GitHub API 查询均为 **404**，因此不作为参考实现。Gemini 没读到本地 DEVLOG/源码；其“旧请求占满连接池”“iOS MSE 是罪魁祸首”等说法仍是猜测，不能压过现有 BFF 已有的中止逻辑与 iPhone 历史实测。

## 给开发者的下一步（按证据门槛排列，不是一次性重构清单）

### P0：一次播放意图的分段证据

先选**可复现的 3 类场景**：首次点播、10 次快速切歌、同一标签页暂停/后台放置后续播；再各录 PC Chrome 与 iPhone Safari/Chrome。每次以 `attemptId + playId` 关联：点击时间、`view/pagelist` 与 `playurl` 开始/结束、API HTTP + JSON `code`、BFF token 签发/失效类别（不记原始 token）、媒体请求首字节/状态/Range/上游 host、`loadedmetadata/canplay/playing`、首个 `timeupdate`、`waiting/stalled/error`、`visibility/freeze/resume`、当前 `readyState/networkState/bufferedAhead`、当前代理源种类。只上传**脱敏、分桶**指标，不上传带签名的 CDN URL、Cookie、BVID、标题。可借 [bili-webos startup trace](https://github.com/asdf17128/bili-webos/blob/e38ed9a83f12d9561a2ecf129c30af615dfc1ee1/app/src/player/startupTrace.js#L1-L110)；Biu 已有[生命周期诊断](../../src/platform/web-lifecycle-diagnostics.ts)和 `X-Request-ID`，优先串起来。

判读：API HTTP 412/429 或 B 站 JSON 风控码才讨论 API 风控；代理 404 要先看 token/会话；CDN 403、长 TTFB、206 正文截断分别定位；`NotAllowedError` 属手势；`QuotaExceededError` 先检查 seek 目标与 `buffered` 的关系。**请求 Pending 本身不能证明限流，也不能证明旧流未 abort。**当前 PC 换 `src` 后会 `load()`，BFF 在响应提前关闭时会中止上游；应在真实瀑布图里验证取消是否传到底，而非凭经验判定连接池堆积。[当前中止路径](../../web-server/media-proxy.ts)。

### P1：确认命中后，优先修“过期资源”和恢复状态

- 活跃页：核对 `isUrlValid(proxyUrl) === true` 时，token 过期/服务重启/媒体会话丢失的首次请求与恢复时延；给客户端提供**不含签名地址**的有效期元数据，或在受限 BFF 的 404 分型后单飞重新 `playurl`，保留原进度与当前播放意图。不要先逐个重试同一会话签出的旧 token；当前代码只在 `failedSrc` 被识别为代理 URL 时走“先重新取址”。
- iOS MSE：当前 watchdog / `onerror` 取的是 `audio.src`，它在 MSE 时是 `blob:`；真实代理源另存 `currentSourceUrl`。核查诊断探针和“失效即刷新”分支是否因 blob URL 漏判；**这是静态代码风险，须用事件复现确认**。[播放源设置与探针](../../src/store/play-list.ts)。
- 刷新恢复：保持现有“恢复歌曲与进度但不擅自自动出声”的产品行为。`play-current-time` 与队列 `playId` 分开存；切歌写 0 时不覆盖本地旧时间，快速切歌后立即刷新有进度错配风险，做针对性夹具验证。[进度 store](../../src/store/play-progress.ts)。后台 `freeze/discard` 不能保证 JS 持续运行；PC“待久仍能播放”验收应定义为**用户回来触发后可从正确进度恢复**，正在播的后台连续性另测。[Chrome 生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)。

### P2：只有计时指向起播链路才缩短关键路径

若 `view` 慢，确认页面已有的 `bvid/cid/标题/封面` 能否直接复用；`13a5e67` 只优化了已有队列路径，首次点播仍可走完整详情。若 `playurl` 慢，使用既有 WBI key 缓存和按 `playId` 单飞，不增加并发风暴。若媒体首字节慢，比较主/备**API 原生** CDN 的短 Range 与实际播放首响；只把经同一条签名/字节一致性验证的源加入候选，不做任意镜像。若只在个别无损/杜比曲目慢，当前 `auto` 会先选 FLAC/Dolby，后续 MSE 才测类型；对照 [bili-webos 先按真实 codec 过滤](https://github.com/asdf17128/bili-webos/blob/e38ed9a83f12d9561a2ecf129c30af615dfc1ee1/app/src/player/mediaSelection.js#L95-L131)，确认是否出现不支持的音轨被选中。以上各项都以首响 trace 选择，不同时改。

### P3：iOS 原生 `<audio>` vs 现有 MMS vs Shaka，做对照而非凭口号迁移

同一曲目/同一网络，分别测从 0 秒与 90 秒起播、暂停 30 分钟与超过 token TTL、切歌 10 次；保留现有 MMS 作为基线。只有原生 `<audio>` 在真机首响和续播都胜出，才考虑替换；先前原生直连在 iPhone 上曾出现十几秒前摇。[已否决方案](../ideas/005-Web版手机播放.md)。若 MMS 快 seek 在特定 fMP4 上定位失准，才评估 `SegmentBase.indexRange`/Shaka 音频-only MPD 的小范围实验；不能把其电视端 30 秒 buffer 参数抄到 iPhone。

## 验收矩阵（建议目标，不是当前已达成效果）

| 场景 | 最低验证 | 候选版本的目标 |
|---|---|---|
| PC/手机首次点播、列表双击与播放按钮 | 成功出声、曲目正确、只拉音频轨；区分首次/已入队 | 与基线同网同曲相比，P95 首响明显下降；目标值由基线数据确定，不能先写“秒播”。 |
| 10 次连续切歌（含切回同曲） | 最终只播最后一次意图；旧请求终止、无串台与请求风暴 | 每首只允许有界 `playurl`/媒体重试；没有“超时后自动扫穿歌单”。 |
| 同页暂停至 token 到期、服务重启、Cookie 会话失效 | 从 90 秒附近恢复；记录 404/403/业务码与刷新次数 | 一次单飞重取址后继续；服务/登录态确已失效时明确提示，而非无限等待。用短 TTL 测试夹具或真实等待测**服务端**到期；不要改本机时钟冒充 CDN 到期。 |
| 移动端 90 秒处刷新、杀页再进、锁屏播下一首 | 刷新后显示正确曲目和进度，用户点播放才出声；锁屏跨曲无手势请求风暴 | 不把上一首的 90 秒错误套到下一首；MSE seek 目标未缓冲时不强行设置 `currentTime`。 |
| 弱网/损坏 Range/`NotAllowedError` | 验证 206 的 `Content-Range` 与正文长度；覆盖 200/416/截断、blob 源与浏览器手势 | 有限次数、可归因、可重试；未证实 CDN 限流前不追加绕限流策略。 |
