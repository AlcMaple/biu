# 响应式离线 Demo：实现、落地与迁移规范

## 结论

这个 Demo 不是重新手写一套“看起来像”的 HTML，也不是把截图拼成静态原型。它使用项目真正的 React 路由树、Layout、页面组件、Zustand store、弹窗、抽屉和响应式分支；只在外部副作用的边界把真实服务替换成本地 fixture。

因此可以把它理解为：

```text
同一套页面与状态机
        │
        ├── 开发/生产：service/platform → BFF、B 站、媒体 CDN、同步服务
        │
        └── 离线 Demo：service/platform → 本地 fixture、演示 store、无副作用适配器
```

这正是 `AI_GUIDELINES.md` 中“不能把局部静态画面或虚构交互称为原型”的约束所要求的边界：页面怎么渲染、状态怎么变化、用户怎么操作，都来自真实代码；只有真实账号、真实数据和真实网络副作用被拿掉。

这份文档同时承担两种用途：

1. **落地 Biu**：AI 或开发者可以根据文件路径、接口边界和命令完成本项目的正确实现；
2. **迁移方法**：换服务器、进程管理器、反向代理、证书方案或另一个项目时，仍能保留原理和顺序，只替换必须重新生成的环境值和工具命令。

不能把“示例值”当成“配置值”。本文后面的所有命令都遵守这个约定：项目专属的真实域名、主机、端口、路径、账号、证书和密钥只从受控环境读取；缺失时停止，不猜。

## 0. 给 AI 的执行协议：先分类，再实施

### 0.1 三类内容

| 类别 | 能否照抄 | 代表内容 | 换环境时的动作 |
| --- | --- | --- | --- |
| **A：原理与停止条件** | 可以照抄 | 共享渲染器、不做第二套路由树；公开流程与私有配置分离；分层验收；备份与回滚；证书失败判据 | 原样保留，只把项目名替换成当前项目 |
| **B：实现形态** | 只能照抄思路，不能照抄命令 | `pnpm build:web`、LaunchAgent、Nginx/Apache、Certbot、隧道、Node BFF | 根据当前项目和服务器选择等价工具，保持输入/输出和验收顺序不变 |
| **C：环境生成值** | 绝对不能照抄 | 域名、服务器、监听端口、测试端口、服务标签、目录、证书、私钥、ACME 记录、release 时间戳 | 在目标环境重新规划、生成、冲突检查，并写入仓库外的私有配置 |

判断口诀：**A 保持不变，B 做等价替换，C 每个环境重新产生**。例如“应用必须只监听 loopback，公网由 TLS 反代接入”是 A；“用 systemd 还是 LaunchAgent”是 B；`5678`、`3002`、`biu.example.com` 和证书目录是 C。

### 0.2 AI 开工前的硬检查

AI 在执行任何发布、证书、反代或服务切换前，必须先取得并验证以下事实：

| 必须知道                              | Biu 的来源                           | 不知道时                        |
| ------------------------------------- | ------------------------------------ | ------------------------------- |
| 当前 checkout、分支和待发布 commit    | Git 工作区                           | 停止，不从未知代码构建          |
| 构建输出、启动命令和健康检查          | `package.json`、`web-server/`        | 先读代码，不凭经验改命令        |
| 外网域名与 TLS 终止点                 | 私有运维配置、反代配置               | 停止，不猜域名或证书归属        |
| 应用、sync、挑战服务的监听端口        | 私有端口登记表、监听检查             | 先做冲突检查，不随机占端口      |
| 进程管理器服务标签和 release 目录     | 私有运维配置                         | 停止，不复制别的项目的标签/路径 |
| 当前域名使用哪套 ACME 签发体系        | Certbot 续期配置中的 `authenticator` | 先判断，不复制其他域名 vhost    |
| 备份位置、可回滚 release 和回滚负责人 | 私有运维配置                         | 停止发布，先建立回滚点          |

本项目的私有字段模板是 [`ops/production.example.env`](../../ops/production.example.env)，实际值应在仓库外、权限 `600` 的文件中。不得运行 `env`、`set` 或打印整个私有配置来“确认”值；只检查必需变量是否存在即可。

### 0.3 新环境的固定顺序

无论换什么服务器或项目，都按这个顺序执行：

1. 画组件边界和数据权威性表；
2. 分配 C 类值并做端口、标签、域名、目录和 vhost 冲突检查；
3. 创建私有配置和最小权限凭据；
4. 用当前项目的构建工具生成不可变产物；
5. 在未占用的测试端口隔离试运行；
6. 配置并验证 TLS 证书，再接公网反代；
7. 按“本机 → 内网/隧道 → 公网 → 真实浏览器”逐层验收；
8. 记录 release、备份和回滚点，最后才切生产流量。

顺序不能因为“只是换证书”或“只是换端口”而跳过。证书、端口和反代都是入口层，入口层错误会把后面的应用问题伪装成 502、CORS 或登录失败。

## 1. 统一页面结构：只保留一棵 React 路由树

Demo 构建使用和开发版相同的 `src/`：

- `src/routes.tsx`：同一套路由和页面入口；
- `src/layout/`：同一个导航栏、侧栏、播放栏、移动端壳；
- `src/pages/`：推荐、搜索、历史、稍后再看、收藏夹、合集、系列、关注、动态、用户空间、设置等真实页面；
- `src/components/`：同一批列表、菜单、Popover、Modal、Drawer、Toast 和播放器组件；
- `src/store/`：同一套播放列表、收藏夹、标签、用户、心动 FM 状态。

`docs/responsive-prototype/full-demo.html` 只是一个很薄的入口，它把构建后的 `runtime/index.html` 放进 iframe，并把 hash 路由转发进去。它不包含页面 JSX，也不复制页面 CSS/交互逻辑。响应式修复必须改 `src/`，这样开发版和离线 Demo 会同时得到同一份改动。

## 2. 构建期打开离线模式，而不是运行时猜测

构建命令是：

```bash
pnpm build:responsive-demo
```

脚本 `scripts/build-responsive-demo.mjs` 设置 `BIU_TARGET=demo`，`rsbuild.config.ts` 再把它转换成编译期常量：

```text
BIU_TARGET=demo
    │
    ├── process.env.BIU_OFFLINE_DEMO = "true"
    ├── 输出到 docs/responsive-prototype/runtime/
    ├── 不注入 Umami 统计脚本
    ├── 不安装 Bilibili Web 中间件
    └── 不启用 Electron 目标
```

普通 `pnpm build:web`、Electron、Android 和 iOS 构建不会设置这个 flag，因此不会误把本地 fixture 带进正常版本。`docs/responsive-prototype/runtime/` 是生成物并被 `.gitignore` 忽略，源代码仍是唯一真相。

## 3. 请求层：保留 service 调用，替换 Axios adapter

页面和 store 不直接读取 fixture。它们仍然调用原来的 service，例如推荐、搜索、历史、收藏夹、用户空间和播放信息 service。只有 Axios 的 transport 在 Demo 构建中切换：

```text
页面/Store
    │ 调用原来的 service 方法
    ▼
Axios request instance
    │ isOfflineDemo ? offlineDemoAdapter : 原来的 adapter
    ▼
offlineDemoResponse(config)
    │ 按 pathname、query、HTTP method 分发
    ▼
与真实接口相同形状的 { code, data, ... } 响应
```

实现位置：

- `src/service/request/index.ts`：Demo 只替换 Axios adapter；
- `src/common/offline-demo-fixtures.ts`：按接口路径和参数返回 fixture；
- `src/common/offline-demo.ts`：集中定义构建期 flag。

fixture 不是随便拼一个标题数组，而是按页面实际读取的字段提供 Biu 形状的数据，例如 `archives`、`result`、`medias`、`info`、`pages`、`owner`、`stat`、`relation` 等。这样页面的 loading、空状态、分页判断、错误判断、标题截断和列表分支仍然走真实代码。

### 变更接口的处理方式

Demo 对只读接口返回能驱动页面的本地数据；对菜单中的 POST/变更接口返回成功的本地 no-op：

```text
GET  → fixture 响应，驱动页面渲染
POST → { code: 0, data: 0 }，让真实 optimistic update、Toast、确认框继续执行
```

这不是伪造网络成功后再发一次真实请求，而是 adapter 已经在网络边界截断，请求不会离开浏览器。

## 4. 平台层：用相同接口，不触碰真实账号和文件

页面依赖的浏览器/Electron 能力仍然通过 `Platform` 接口调用，Demo 只提供安全的替身：

| 能力                     | 离线 Demo 行为             | 为什么这样做                       |
| ------------------------ | -------------------------- | ---------------------------------- |
| 用户、收藏夹、标签、设置 | 返回 `DEMO_STORE_DATA`     | 让真实 store 完成 hydration 和渲染 |
| 下载列表                 | 返回 `DEMO_DOWNLOAD_TASKS` | 可以巡检下载页、进度和筛选         |
| 本地音乐扫描             | 返回 `DEMO_LOCAL_MUSIC`    | 可以巡检本地音乐页，不读本机目录   |
| 选择文件/目录、删除文件  | 返回空或失败               | 不触碰测试机文件系统               |
| `openExternal`           | 直接返回 `false`           | 不打开 B 站或任意外部页面          |
| Cookie 读写              | Demo 不读取真实 Cookie     | 演示用户只是一份 UI fixture        |

Demo 的 Web 存储还使用独立命名空间：

- localStorage 前缀：`biu-demo:`；
- IndexedDB：`biu-demo-web-store`。

即使在同一个浏览器中打开 Demo，也不会覆盖开发版的 `biu:` 数据。

## 5. 状态层：复用真实 Zustand store，只关掉不可验证的副作用

### 播放列表和播放栏

播放列表的队列、当前 `playId`、下一首、上一首、播放模式、列表操作和 Toast 仍由 `src/store/play-list.ts` 的真实 action 处理：

- `play`、`playList`、`playListItem` 会更新真实播放队列和当前项；
- `addToNext` 会把项放到下一首位置；
- 播放栏的播放/暂停会切换真实 `isPlaying` 状态；
- 菜单、播放列表抽屉、上一首/下一首仍调用同一套 action。

Demo 只在两个地方做边界保护：

1. `ensureAudioSrcValid` 不解析真实媒体地址；
2. 播放列表订阅不挂载媒体源、不上报播放记录、不触发换源链路。

这样点击播放、暂停、下一首和加入队列仍能验证 UI 状态机，但不会让浏览器加载媒体 CDN，也不会制造 `play()` 拒绝、媒体失败重试或请求风暴。fixture 中的 `data:` 封面和音频字符串只用于满足数据形状/显示需求，Demo 播放 guard 不会把它们交给真实媒体加载链路。

### 心动 FM

`src/store/heartbeat.ts` 仍使用真实页面和真实播放列表，但 Demo 的 `start()` 只把本地“我喜欢的音乐” fixture 放入队列，跳过在线候选池、相似推荐、续供和会话恢复请求。这样可以验证 FM 页的按钮、队列、播放栏和“喜欢/取消喜欢”状态，而不访问推荐接口。

### 同步与日志

两个常驻副作用在边界直接退出：

- `src/service/sync/index.ts`：Demo 不启动版本 watch、同步拉取或写回；
- `src/platform/web-log-transport.ts`：Demo 不把日志 POST 到 `__biu_log`。

这比在页面里逐个删除调用更可靠，因为所有页面共享同一个边界，新增页面也不会意外启动同步通道。

## 6. 为什么页面外观和开发版能保持一致

响应式修改全部落在真实组件，而不是 Demo 专用 CSS：

- 断点由共享的 layout/响应式 hook 决定；
- 移动端列表、表头、搜索筛选、底部播放栏和抽屉走真实组件分支；
- 桌面、窄平板、平板和手机只通过同一份 Tailwind/组件样式切换；
- 任何按钮的可见性、点击区域、Popover、Modal、Toast 和键盘/触摸行为都由真实组件决定。

所以验收路径是“打开 Demo 找到问题 → 修改 `src/` → 同时刷新开发版和 Demo”，而不是“在原型 CSS 里修一遍，再把结果手工翻译回 React”。

## 7. 已覆盖的页面与交互

当前 fixture 覆盖这些页面和状态：

- 推荐、搜索、私人 FM；
- 收藏夹、视频合集、视频系列、本地收藏；
- 历史记录、稍后再看、下载记录、本地音乐；
- 我的关注、用户动态、用户空间、设置；
- 空状态和 404；

收藏夹详情要区分两条真实路由：`#/local-collection/-3` 是截图所示的本地收藏夹 `all`，移动端第一行保留“播放全部 / 更多”，第二行完整显示标签和搜索；手机隐藏“添加到播放列表”，把“失效内容”放进“更多”，不显示“最近收藏”排序，也不提供“下载全部音频/视频”；`#/collection/101` 是远程收藏夹，才使用远程收藏排序和批量下载菜单。不能把这两种页面的 fixture 或操作栏混在一起。

## 8. 明确不模拟的内容

为了满足“不要登录、不要疯狂打别人接口”的要求，以下内容不属于离线 Demo 验收范围：

- Bilibili 登录、Cookie、验证码和账号权限；
- 真实 Bilibili 数据的新鲜度、分页变化和限流行为；
- 真实媒体 CDN 的 Range、解码、切换音源和锁屏续播；
- Electron 原生文件选择、真实下载、删除文件和系统窗口控制；
- 多设备云同步以及服务端通知通道。

这些能力必须在对应的开发/生产环境单独验收；Demo 只验证它们对应的页面、组件和本地状态反馈不会破坏响应式布局。

## 9. 使用和验证

构建后不需要启动 Biu，也不要求 Python：

```bash
pnpm build:responsive-demo
```

然后直接打开 [`full-demo.html`](./full-demo.html)。如果某个浏览器限制 `file://` 页面加载相对资源，再使用任意静态服务器作为备用，例如：

```bash
python3 -m http.server 8765 --bind 127.0.0.1 --directory docs/responsive-prototype
```

建议检查尺寸：`320×568`、`375×667`、`667×375`、`768×900`、`1000×900`、`1440×900`。

代码级检查：

```bash
pnpm build:web
pnpm build:responsive-demo
pnpm exec eslint
pnpm exec vitest run tests/responsive-full-demo.test.ts tests/offline-demo-fixtures.test.ts
git diff --check
```

浏览器级检查应确认：

1. 路由能打开，页面有 fixture 内容而不是空白；
2. 手机尺寸没有横向溢出；
3. 播放、菜单、弹窗、抽屉和 Toast 的状态会变化；
4. 开发者工具 Network 中没有 Bilibili、BFF、同步服务、日志服务或媒体 CDN 请求。

当前全量 Vitest 还存在一个与本改动无关的既有环境问题：`biu-sync-server/src/lib/__tests__/storage-history.test.ts` 无法解析仓库原本就缺失的 `dotenv`；其余测试通过。这个失败不能用安装依赖来掩盖，应单独处理。

## 10. 新增页面或 fixture 的规则

以后扩展 Demo 时遵循以下顺序：

1. 先让真实页面在开发版跑通，确认它实际调用的 service、字段和状态分支；
2. 在 `offline-demo-fixtures.ts` 增加同形状响应，不在 HTML 中另写页面；
3. 如果页面依赖持久化数据，补到 `DEMO_STORE_DATA` 或对应平台 fixture；
4. 如果是变更操作，优先复用真实 optimistic update/Toast，只让 POST 在 adapter 中成为本地 no-op；
5. 如果能力会触碰登录、文件、媒体或常驻网络，放在 `isOfflineDemo` 边界保护；
6. 用真实 React bundle 在至少一个手机尺寸和一个桌面尺寸检查，再跑构建、测试和 Network 检查。

判断标准只有一个：如果必须在 Demo HTML 里复制一段 JSX、状态或交互，说明边界放错了，应回到真实 `src/` 修复，而不是继续堆第二套原型代码。

## 11. 具体落地示例：Biu Web 生产部署与 SSL

下面这节把上面的 A/B/C 方法落到本项目。它不是要求所有项目照抄 Biu 的端口和命令，而是展示如何把**同一套原理**翻译成一个可执行的部署流程。完整的生产维护细节仍见 [Web 生产部署与维护指南](../web/Web%20生产部署与维护指南.md) 和 [Web 部署](../web/Web%20部署.md)。

### 11.1 先画 Biu 的边界

```text
浏览器
   │ 公网 HTTPS
   ▼
TLS 终止反向代理
   │ 只转发合法路径；保留 Host、Range、Set-Cookie 语义
   ▼
Biu Web BFF（仅监听 loopback，例如 127.0.0.1:<WEB_PORT>）
   ├── Bilibili API / 媒体代理
   ├── 登录会话与同源校验
   ├── /__biu_sync/* → sync 服务
   └── /__biu_health
             │
             ▼
      sync 服务（仅 loopback，例如 127.0.0.1:<SYNC_PORT>，单进程）
             │
             ▼
      按用户分隔的数据目录
```

每一层的权威性和禁区必须写出来：

| 组件 | 权威数据/职责 | 绝对不能做 |
| --- | --- | --- |
| React renderer | 页面布局、交互和本地 UI 状态 | 直接访问 B 站、媒体 CDN 或任意本地文件 |
| Web BFF | 上游 API/媒体、登录会话、同源校验 | 变成纯静态站；把 Cookie、JWT 或签名 URL交给浏览器 |
| sync 服务 | `favorites`、`fav-items`、`tags` 的服务端合并数据 | 多进程写同一数据目录；接管不属于它的本地设置/媒体文件 |
| 公网反代 | TLS、Host、Range、缓存和到 BFF 的转发 | 暴露终端、SSH、数据目录或任意 URL 代理 |
| ACME 挑战服务 | 只提供当前域名的 `/.well-known/acme-challenge/<token>` | 根据请求参数转发到任意 localhost 端口 |

这张表可以直接照抄“画表的方法”，但换项目时必须重画内容。判断每个组件时只问两句：**谁拥有这份数据？它绝对不能做什么？**

### 11.2 Biu 中可以复用、需要替换、必须重新生成的值

| 分类 | Biu 示例 | 换服务器/项目时如何处理 |
| --- | --- | --- |
| 可以复用的原理 | BFF 与 renderer 同源；应用 loopback；反代终止 TLS；发布包不可变；本机→公网分层验收 | 原样保留 |
| 可以复用的字段含义 | `PUBLIC_ORIGIN`、`WEB_PORT`、`SYNC_INTERNAL_ORIGIN`、`HEALTH_PATH`、证书配置目录 | 字段语义保留，变量前缀可改成目标项目的前缀 |
| 只能替换实现的命令 | `pnpm build:web`、`pnpm start:web`、LaunchAgent、Nginx、Certbot | 按目标项目的构建器、进程管理器、反代和 ACME 客户端改命令 |
| 不能复用的环境值 | `music.example.com`、SSH 别名、`5678`、`3002`、`15679`、`18095`、release 路径 | 重新规划并冲突检查；文档里的数字只能当示例 |
| 不能复用的秘密/派生物 | JWT_SECRET、SSH key、证书、私钥、ACME TXT、构建时间戳、备份路径 | 在目标环境重新生成，放在仓库外的 `600` 文件中 |

本项目有一个容易混淆的变量映射：运维模板中的 `BIU_PUBLIC_ORIGIN` 是操作人的私有配置字段；启动 BFF 时必须把它作为应用环境变量 `BIU_WEB_PUBLIC_ORIGIN` 传入。它们的值应完全相同，且必须是没有路径、查询参数或凭据的完整 `https://...` origin。

### 11.3 先生成私有配置，不要复制完整 env

在获授权的私有终端中，把 `ops/production.example.env` 复制成仓库外的配置文件，填入**本环境重新产生**的值，并设置权限：

```bash
chmod 600 /受控路径/production.env
export BIU_OPS_CONFIG=/受控路径/production.env
```

加载时只验证必需字段，不打印文件内容：

```bash
: "${BIU_OPS_CONFIG:?需要私有运维配置；未设置时停止}"
test -f "$BIU_OPS_CONFIG"
set -a
. "$BIU_OPS_CONFIG"
set +a

: "${BIU_PUBLIC_ORIGIN:?}"
: "${BIU_WEB_RELEASE_ROOT:?}"
: "${BIU_WEB_SERVICE_LABEL:?}"
: "${BIU_WEB_PORT:?}"
: "${BIU_WEB_TEST_PORT:?}"
: "${BIU_SYNC_INTERNAL_ORIGIN:?}"
: "${BIU_HEALTH_PATH:?}"
```

不能从其他服务器复制证书目录、数据目录、LaunchAgent、服务标签或端口。即使名字相同，也可能指向另一套项目；即使端口当前空闲，也必须登记为本环境的新分配。

### 11.4 端口和同机资源的生成与冲突检查

“启动项目不能同时启动同一个端口”只是 C1 的一个例子。同机唯一资源至少包括：应用端口、sync 端口、ACME 挑战端口、测试端口、进程管理器标签、隧道端点、release 目录、数据目录和反代 vhost。

先在私有端口登记表中分配一组值，再检查，而不是启动失败后才临时改：

```bash
# macOS
lsof -nP -iTCP:"$BIU_WEB_PORT" -sTCP:LISTEN
lsof -nP -iTCP:"$BIU_WEB_TEST_PORT" -sTCP:LISTEN

# Linux 等价检查
ss -ltnp | grep -E ":(${BIU_WEB_PORT}|${BIU_WEB_TEST_PORT})\b" || true
```

预期结果是目标端口没有其他监听者。检查还应覆盖：

```bash
# LaunchAgent 环境
launchctl print "gui/$(id -u)/$BIU_WEB_SERVICE_LABEL"

# systemd 环境的等价动作
systemctl status "$PROJECT_SERVICE_NAME"

# 反代 vhost 必须只出现一次（按实际工具选择）
nginx -T
apachectl -S
```

如果要部署第二个项目，不能复制 Biu 的 `5678`、`3002` 或同一个 service label；应为第二个项目分配新的端口段、标签、数据目录和 vhost，并把反代 upstream 一起改成新值。测试实例也必须使用独立的测试端口，验证完立即停止，不能与生产实例长期共存。

### 11.5 Biu Web 发布流程

以下流程中的原则可以照抄，命令属于 B 类，换工具时只替换实现：

1. **确认源码**：检查当前分支、commit、测试和工作区；线上特有的 BFF/同步/证书挑战实现必须在当前 checkout 中。
2. **构建不可变产物**：运行 `pnpm build:web`，只打包 `dist/web` 和 `dist/server`，计算 SHA-256；发布包不得包含 `.env`、`node_modules`、证书、私钥、浏览器 profile、用户数据或日志。
3. **传输到新 release 目录**：按 release 时间戳创建新目录，不覆盖旧 release；目标端再次核对 SHA-256 和入口文件。
4. **隔离试运行**：以 `BIU_WEB_HOST=127.0.0.1` 和新的 `BIU_WEB_TEST_PORT` 启动，检查 `GET $BIU_HEALTH_PATH`；测试失败立即停止，不切流量。
5. **切换服务**：只替换 release 路径和日志路径，保留经过验证的公网 origin、sync origin、ACME origin 和安全变量；先备份服务定义，再 reload/kickstart。
6. **分层验收**：本机健康检查 → 隧道/内网 → 公网 HTTP/TLS → 真实浏览器登录、列表、播放和 Range。

对应的 Biu 命令入口是：

```bash
pnpm build:web
pnpm start:web
```

如果目标项目使用 Docker、systemd、pm2 或静态托管，不能把这两行原样复制；应保持“不可变产物、隔离试运行、可回滚切换、逐层验收”四个性质。例如 systemd 替换 LaunchAgent 的加载方式，Docker 替换 release 目录的切换方式，但仍要让应用只监听被反代访问的内部端口，并保留健康检查和旧版本回滚点。

### 11.6 SSL 证书配置：先判断体系，再选步骤

证书不能从另一台服务器或另一个域名复制。先确认 DNS、域名归属和 TLS 终止点，再判断当前域名属于哪套 ACME 体系。常见两种形态如下：

| 形态 | 证书在哪里签发 | Biu 配置 | 不能做的事 |
| --- | --- | --- | --- |
| 反代主机本机签发 | 公网 Nginx/Apache/Caddy 所在机器 | 通常不设置 `BIU_ACME_CHALLENGE_ORIGIN`；由反代/ACME 客户端直接处理挑战 | 从“内网挑战回落” vhost 复制挑战转发 |
| 挑战回落到内网 | 内网 Biu 主机上的 Certbot；公网反代只转发固定挑战路径 | 设置 `BIU_ACME_CHALLENGE_ORIGIN=http://127.0.0.1:<ACME_PORT>` | 做成任意 localhost URL 代理；把完整证书私钥写进 Git |

在反代主机上查看续期配置的 `authenticator` 字段来判断，不要凭 vhost 文件名猜。确认体系后按以下过程：

1. **检查 DNS 和入口**：确认 A/AAAA 指向当前反代、TCP 80/443 由预期主机接收；若有旧 vhost，先确认它是否属于同一个域名。
2. **准备最小权限 ACME 配置**：Certbot 配置、工作、日志目录和续期服务标签写入私有配置；证书/私钥目录不放发布包。
3. **配置挑战路径**：
   - 本机签发：由当前反代的 ACME 插件/Certbot 接管，Biu 不需要挑战回落；
   - 内网签发：只允许 `GET/HEAD /.well-known/acme-challenge/<合法 token>` 转发到固定 loopback origin，禁止 query、重定向和任意目标。
4. **先干跑**：

   ```bash
   "$BIU_CERTBOT_BIN" renew --dry-run \
     --config-dir "$BIU_CERTBOT_CONFIG_DIR" \
     --work-dir "$BIU_CERTBOT_WORK_DIR" \
     --logs-dir "$BIU_CERTBOT_LOG_DIR"
   ```

   干跑使用测试证书，不能触发把测试证书复制到生产 TLS 终止点的 deploy hook。

5. **配置续期钩子**：真实续期后先执行反代语法检查，再 reload TLS 终止服务；不要逐域名手工 reload。新证书如果没有 reload，线上仍会继续提供旧证书。
6. **公网验证**：用 `curl -sSI` 检查证书链、协议、`Referrer-Policy`、`X-Content-Type-Options`、缓存策略和 Biu 的健康检查；再用真实浏览器验证登录 Cookie、列表请求和媒体 Range。

如果 Certbot 报错包含 `During secondary validation`，先停止修改 vhost、防火墙和 DNS。它表示 ACME 的其他观察点到你的入口网络不稳定，不是本机配置必然错误；改用 DNS-01 或在签发窗口内重试。不要删除旧证书，也不要把测试证书部署到生产。

### 11.7 Biu 反代必须保持的协议语义

反代产品可以变化，但下面这些语义不能变：

- `Host` 必须原样传给 BFF，并与 `BIU_WEB_PUBLIC_ORIGIN` 的 scheme + host 一致；BFF 不信任任意 `X-Forwarded-Host` / `X-Forwarded-Proto`；
- API、登录、同步、媒体 token、`Set-Cookie` 和 `__biu_health` 不应进入公共缓存；
- 媒体请求必须透传 `Range`、`If-Range`、`206`、`Content-Range` 和客户端取消；
- `/.well-known/acme-challenge/` 只能去固定挑战服务，不能接受 URL 参数决定目标；
- TLS 证书由反代终止时，BFF 仍应使用公网 HTTPS origin 做来源校验，内部 loopback HTTP 只用于反代到应用。

Nginx、Apache、Caddy 或云厂商 LB 的配置语法不同，不能互相复制整段配置；复制的是上面这组协议断言，并在目标产品中逐项验证。

## 12. 迁移到不同服务器或不同项目的操作模板

### 12.1 先建立“等价物映射表”

换项目时先写表，再写命令。不要把 Biu 专属名称直接替换成另一个项目名就执行：

| 能力     | Biu 当前实现               | 目标环境需要重新确认                       |
| -------- | -------------------------- | ------------------------------------------ |
| 页面构建 | Rsbuild + `pnpm build:web` | Vite/Next/其他构建器、输出目录、asset base |
| 应用运行 | Node BFF `pnpm start:web`  | Node/Go/Python/容器入口、监听 host/port    |
| 进程管理 | macOS LaunchAgent          | systemd、pm2、Docker Compose、Kubernetes   |
| 公网入口 | TLS 反代 + 同源 BFF        | Nginx、Apache、Caddy、云 LB；是否有隧道    |
| 证书     | Certbot 或托管 ACME        | acme.sh、Caddy 自动 TLS、云托管证书        |
| 数据服务 | 单进程 sync + JSON 目录    | 数据库/对象存储/其他 sync 服务及并发模型   |
| 健康检查 | `/__biu_health`            | 目标项目的只读健康路径和返回语义           |

这张表中，**能力和验收语义可以复用，工具、路径、端口和命令必须换成目标环境的事实**。若目标项目没有 BFF 或没有持久化服务，不要为了套模板虚构一个；重画边界表并删除不适用的层。

### 12.2 迁移的最小可执行流程

1. 读取目标仓库的启动入口、环境变量解析、反代文档、数据模型和测试；
2. 创建目标项目自己的变量前缀，例如 `APP_*`，不要继续误用 `BIU_*`；
3. 为每个同机唯一资源分配新值并验证空闲；
4. 生成目标环境自己的域名、证书、密钥、服务标签和目录；
5. 在独立测试端口/容器中启动，先通过本机健康检查；
6. 按目标反代产品配置 TLS 和协议透传；
7. 证书干跑成功后再启用真实续期钩子；
8. 完成本机、内网、外网、浏览器四层验收；
9. 保存当前 release、备份和反代/服务定义的回滚点；
10. 把目标项目独有的实现写回它自己的文档，不把 Biu 的真实值带回公共模板。

### 12.3 AI 交付前的“可迁移”判定

AI 生成或修改部署实现后，应明确列出三组结果：

```text
可以照抄：原理、边界、停止条件、验收顺序、回滚策略
需要适配：构建/启动命令、进程管理器、反代语法、ACME 客户端
必须重新生成：域名、主机、端口、标签、路径、证书、密钥、凭据、release 值
```

如果回答中出现“沿用上一台服务器的端口/证书/私钥/服务标签”“复制完整生产 env”“没有访问权限也先猜一个 IP/路径”，则实现不合格，应停止并补齐事实。若缺少 DNS 控制权、证书签发权限、私有配置或服务器访问权，正确动作是报告阻塞项，而不是执行半套部署。

## 13. 最终完成标准

一份既能落地 Biu、又能迁移的实现文档，必须同时满足：

- 读者能从仓库文件和命令找到 Biu 的真实实现入口；
- 读者知道哪些是共享 renderer/state/service contract，哪些是平台或网络副作用；
- 每个不可复用值都有“为什么不能复制、如何生成、如何冲突检查”的说明；
- 生产部署包含不可变发布、隔离试运行、TLS/SSL 证书签发与续期、逐层验收和回滚；
- 换服务器或项目时只替换 B 类实现和 C 类生成值，不改变 A 类原理与顺序；
- 文档不泄露真实域名、IP、端口登记、路径、证书、私钥、Cookie、JWT 或备份位置；
- 所有“成功”都有可执行的验证证据，而不是“配置应该生效”。
