## 结论

**三种渠道均已实际跑通搜索、匹配歌曲、获取歌词及格式检查。** 中文、日文、英文各选一首，每个渠道 3 首，共 9 次完整取词/解析检查通过。本轮 27 个平台请求，每个探测步骤仅发一次，没有自动重试或登录账号；没有启动常驻服务或下载音频。

| 酷狗 | 3/3 | 可解码的逐字 KRC | 可提供词级时间轴候选，保留来源版本并继续检查当前录音匹配 |

## 各渠道的成功路径与接入条件

### QQ

- 按固定版本 MIT 上游的匿名轻量搜索协议查询，获得 songmid 后，再调用普通歌词端点。三首的网关、搜索业务码与取词业务码均为成功值；LRC 解码后均存在有效行时间戳。
- 使用的是匿名协议标记 tmeLoginType=-1，不是用户登录 Cookie；没有读取浏览器或项目账号凭据。
- 本轮普通歌词端点对三首的 trans 字段均为空，因此这条路径只确认了正文，未确认译文或原生 QRC。
- 匿名搜索的实现选择与版本有关；本轮用固定上游已定义的 search_type=7。接入时需固定并验证协议，不能只沿用历史请求。

### 酷狗

成功路径是：**曲库搜索 → 核对歌手/版本、取得 FileHash 与秒制时长 → 用 Hash 与毫秒制时长查歌词候选 → 下载 KRC → 检查文件头并解码、解压 → 读取词级时段。**《アイドル》的歌词候选名称为 Idol，按同一歌手及标题别名匹配。

首次简化请求虽 HTTP 200，正文却是 0 字节。按上游请求层补齐请求形态后，只带关键词又得到业务 status=404、候选为空。取得歌曲 Hash/时长并走完整链路后，三首均得到业务成功与可解码 KRC。

这是成功链路的验证，不是逐参数的因果隔离实验；不据此断言所有歌曲一律必须某一个字段。接入时需要保留客户端参数、请求头、签名与业务码判断，不把 HTTP 200 或空正文当作“有歌词”。

### AMLL

- 官方公开检索端点返回歌曲元数据与文件 ID，再用该 ID 获取完整 TTML，三首均为 HTTP/业务成功。
- 本轮独立脚本用内置 XML 解析工具检查结构，没有引入 AGPL 的官方 TTML npm 包。
- 日文、英文样本还观察到译文与背景人声角色标记；正式实现仍须处理完整时间继承、空格、译文、多声部等语义。
- 带 Origin 的请求观察到响应跨域标头，但这不是浏览器页面中的 CORS 集成测试；Biu 仍应遵守现有固定平台能力/BFF 边界。

## 异常与未收录检查

| 检查 | 实测结果 | 接入时的含义 |
| --- | --- | --- |
| AMLL 不存在的曲目查询 | HTTP/业务 200，items=[] | 可明确显示无匹配 |
| AMLL 不存在的歌词 ID | HTTP/业务 404 | 与服务故障分开 |
| QQ 不匹配的查询 | HTTP 200、网关 code=0，但单项业务 code=2001 | 此码含义未进一步确认；应保留为上游检索异常，勿因数组为空就显示“未收录” |
| 酷狗不存在的曲目查询 | HTTP 200、业务 status=1/error_code=0，lists=[] | 空结果与初次异常空正文分开 |

QQ 返回非零业务码后没有继续向该渠道发起请求。本轮没有主动制造 429/5xx 或探测风控恢复；这些错误处理仍属于接入后的专项验证。固定 QQ SDK 的请求层默认存在重试配置，正式接入应按 Biu 规则关闭相应自动重试；本次探测不运行该 SDK，HTTP helper 没有重试循环。

离线验证另外确认：畸形 XML、含 DTD 的输入、错误 KRC 文件头及损坏压缩体均被拒绝；纯文本不会误标成带时间 LRC。这些是探测器的检查，不是项目现有测试或实际播放器集成通过。

## 已确认的产品决策

**镜台 PV 走独立实现，尽量接近参考视频的真实三维舞台。** 保留空间歌词、前后景深、镜头移动、逐字强调、程序化几何/流体背景；保持当前精美样式可切换，共用 Biu 音频与播放时钟。本轮不移植 Folia/Lumisynth 渲染代码、不联系作者申请模块许可，也不实施 PV。

用户随后明确：**原有精美样式保留，Folia 镜台式三维 PV 与 Lumisynth 式 PV 都纳入目标**。三类外观共用当前音频、歌词、声学对齐和播放时钟；Lumisynth 的具体风格与动态样例继续在[主方案](多源歌词与镜台PV-调研方案.md)中收敛。这项产品范围确认不改变本报告的 9/9 渠道样本口径，也不代表 PV 已实现。

下一步若进入实施：保留来源时间轴与当前录音声学对齐的区别，沿用现有搜索/预览/采用、存储、IPC/BFF/原生网络抽象，分别适配三个来源；原有用户歌词和对齐结果不被静默覆盖。

## 本轮边界

已验证的是本机当前网络下的有限样本 API 取词与基本格式解读。尚未验证 Biu 内部页面、Electron IPC、Web BFF、Android/iOS 的实际集成，也没有重新运行声学对齐、听歌核对时间误差或测试 PV 性能。无需登录的本轮结果不等于所有歌曲、地区或未来版本均具相同条件。代码许可与平台/歌词内容权利依旧分开处理。

**状态：数据层与请求能力已接入并通过测试。界面入口见下方阶段 2。**

**做了什么**

- 规范化成一份毫秒时间轴：每行保留开始/结束（LRC 的结束是用下一行推断的，单独标出）、逐字开始/结束、译文、罗马音、和声（背景人声单独一轨）与演唱者。这仍是平台的原唱时间轴，不标成「已对齐当前录音」。
- TTML 只实现 AMLL 实际使用的绝对时间语义；遇到非 media 时基、顺序时间容器、帧时间、带时间与不带时间的文本混在同一行时直接报「格式不支持」，不悄悄错时。DTD / 实体声明一律拒绝。
- 取词逻辑只在主进程和 BFF 运行，渲染层只能传歌名、歌手和平台 ID。不引入上游 SDK，所以不会带进它们内置的自动重试；Electron 侧关闭 got 重试与重定向，BFF 侧 `redirect: "error"`。
- 错误按类型带回：限流（429）、服务异常（其他非 2xx）、超时、断网、业务码异常（含 QQ 2001）、未收录（AMLL 404、酷狗无歌词候选）、返回无法解析（含 HTTP 200 空正文）、格式不支持、参数不合法、平台不支持。每次用户操作只发必要的请求：搜索 1 个，取词 QQ/AMLL 1 个、酷狗 2 个。

**验证**

- 单元测试 `tests/lyrics-format.test.ts`、`tests/lyrics-providers.test.ts` 及扩展后的 `tests/web-lyrics-proxy.test.ts`，共 41 项通过（合成样本，仓库内不放真实歌词）。酷狗签名与实测请求逐字节一致。
- 离线回放上一节保存的 7 份真实响应（仓库外），解析计数与上表一致：KRC 63 行/602 字、90 行/593 字、91 行/676 字；TTML 62 行/494 字，日文/英文样本读出 78、85 行译文以及 1、14 行和声。
- 实网（本机网络，2026-10-21 23:5x，单次、不重试）：《晴天》经 Electron 传输层 AMLL 3.1 s 拿到 TTML 逐字 62 行，QQ 2.8 s 拿到 LRC 63 行，酷狗 4.0 s 拿到 KRC 逐字 63 行（每项耗时含搜索 + 取词，只是单次观测，不是基准）。
- 全量 Vitest：除 `tests/mobile-viewport-layout.test.ts` 外全部通过；该文件改动前的干净基线上已有 4 项失败，与本阶段无关。`tsc` 根配置与改动前相比没有新增错误；web-server 配置编译通过。

**剩余风险**

- AMLL 搜索只用了实测过的 `musicName`（+ `artistName`）；用户输入「歌名 歌手」整串时可能匹配不到，`q` 参数未验证。
- 酷狗取词的 10 秒超时在 BFF 里覆盖两次串行请求；慢网下可能比单请求更容易超时。
- QQ 原生 QRC 与译文未验证（三首样本的 `trans` 都为空）。
- 采用后的存储（来源元数据、原生时间轴与当前录音对齐分开保存）属于阶段 2，尚未实现。

**恢复方式**：本阶段新增文件 `shared/lyrics-format.ts`、`shared/lyrics-providers.ts`、`electron/ipc/provider-transport.ts`，其余是在现有 IPC / preload / 平台 / BFF 列表上各加两项；回滚即删除这些新增项，不涉及存储格式与已有歌词缓存。

**用户会经历什么**

1. 「歌词设置 → 搜索歌词」的说明改为「从网易云、LrcLib、QQ、酷狗、AMLL 搜索并使用」，弹窗多出三个页签。切到页签才搜，一次只搜当前来源。
2. 列表显示歌名、专辑、歌手、时长和时间轴类型（逐字 / 逐行；酷狗要预览后才知道）。
3. 点一行打开预览，顶部写明来源、格式、时间轴类型、社区歌词作者，逐字歌词另注「逐字时间来自原唱录音，采用后仍会按当前视频重新对齐」。关闭预览不写任何东西。
4. 点「采用歌词」后歌词立刻换上，按平台逐字时间填色，状态标为「未对齐 · 逐字按歌词平台的原唱时间」（黄点），不显示成绿点「已对齐」。之后沿用原有流程按当前视频自动对齐，对齐完成后换成对齐结果。
5. 出错时在列表区或预览里直接写原因：限流会提示「连续重试会延长限制，请过几分钟再搜」，未收录会建议换来源，QQ 业务码异常显示业务码，都不显示成「没搜到」。

**数据怎么存**

- 新增 `origin`（来源平台、平台内 ID、歌名、歌手、作者、格式、时间轴类型、采用时间）和 `nativeTiming`（采用时的行级 LRC 与逐行逐字的开始/结束毫秒）。原有 `source`（manual/auto/aligned/approved）含义不变，平台采用和网易云 / LrcLib 一样记为 manual，不会被生效版本或自动匹配覆盖。
- `nativeTiming` 只在 `lyrics` 还是采用时那份时才用：被对齐结果、自动匹配或别的歌词替换后自动作废，还原为对齐前时又重新生效。从网易云 / LrcLib 采用时这两个字段会显式清空。
- Web 版歌词缓存从 localStorage 迁到 IndexedDB（沿用现有迁移：首次读取时搬过去并删掉旧项，本机实测迁移成功）。原因：一首逐字歌词的平台时间轴约 19 KB（实测《背对背拥抱》56 行），几百首就会撑满 localStorage 的 5 MB 配额，之后写入静默失败。

**旧请求与切歌**

- 换来源、重新搜索、切歌都会丢掉还没回来的搜索结果；关闭预览后才回来的取词结果不会再弹出。
- 预览期间切了歌，点「采用」会拒绝并提示「已经切到别的歌了，这份歌词没有保存；请重新搜索」，不会写到新歌上。
- 组件测试中发现 HeroUI 表格行 `onClick` 点一次会触发两次取词，已改用表格的 `onRowAction`；浏览器里点一次只发一个取词请求。网易云 / LrcLib 页签仍是 `onClick`，本阶段没动。

**验证**

- 新增 `tests/provider-lyrics.test.ts`、`tests/lyrics-provider-tab.test.tsx`、`tests/provider-lyrics-alignment.test.ts`，扩展 `tests/lyrics-align-status.test.tsx`。全量 Vitest 除基线已有失败的 `tests/mobile-viewport-layout.test.ts` 外全部通过；`tsc` 根配置与改动前相比无新增错误，web-server 配置通过。
- Web 实机（`pnpm dev:web`，本机网络）：酷狗搜「背对背拥抱」发 1 个搜索请求，点第一行发 1 个取词请求，预览显示「酷狗 · KRC · 逐字」；采用后 IndexedDB 中该条为 `source: manual`、`origin.provider: kugou`、`nativeTiming` 56 行且与 `lyrics` 一致，没有 `alignment`；刷新后仍按平台逐字显示，状态标签正确。

**剩余风险**

- 声学对齐接入只有单测；需要登录并连上对齐服务后实机确认采用后会排队对齐、完成后替换。
- Electron 窗口未开过；IPC 链路在阶段 1 实网验证过，界面与 Web 共用。
- 网易云 / LrcLib 页签的行点击可能同样重复取词，未核实。

**恢复方式**：删除新增的 `provider-tab.tsx`、`provider-lyrics.ts` 及弹窗里的三个页签即可回到阶段 1。缓存里多出的 `origin`、`nativeTiming` 旧代码不读，不影响回滚；Web 缓存迁到 IndexedDB 后若回滚，需要同时保留 `LyricsCache` 在 IndexedDB 列表中，否则旧代码会读 localStorage 而看不到已迁移的歌词。

| KuGouMusicApi `server.js` | 成功响应缓存 2 分钟，同 URL 两分钟内只打一次上游 | 采用并放宽：搜索 30 分钟、取词 24 小时、「未收录」10 分钟；失败不缓存 |
| LDDC（`LDDC/core/api/lyrics/__init__.py`） | 搜索 / 取词结果磁盘缓存 4 小时；超时自动重试 3 次 | 缓存采用；**超时重试不采用**：限流期间的超时往往就是惩罚，再打只会延长（AGENTS.md「网络请求」） |
| LDDC QQ 接口 | 先 `GetSession` 拿匿名 uid / sid 再搜索 | 本轮复测「不存在的曲目」有无会话都返回业务码 0、空列表，原 2001 未复现，暂不加会话请求，仍把非零业务码原样报出 |
| LDDC 酷狗接口 | 注册设备拿 dfid 并缓存 | 未采用：实测 `dfid=-` 三首都能取词；若之后出现风控再加 |

**本项目在此基础上加的**

- 同一请求同时发起只打一次上游（例如连点同一行）。
- 429 后整个渠道冷却：按上游 `Retry-After`，没有就 1 分钟（服务异常 30 秒，最长 10 分钟）。冷却期间直接返回本地提示，不碰上游；到点后也不自动探测，等用户再点。其他渠道不受影响。
- 每个渠道每分钟最多 30 次上游请求。Web BFF 上所有用户共用服务器出口 IP，这道闸是为了不让一个人把服务器 IP 打进黑名单；单人正常使用到不了。
- 提示文案带等待时间：「QQ 音乐刚才提示请求过于频繁，约 45 秒后再试；期间可以先用其他来源。连续重试会延长限制」。

**手机端**：取词代码去掉 Node 专有 API（MD5 改用项目已有的 `spark-md5`，KRC 解压改用 `DecompressionStream`，base64 用 `atob`），在 App 里经 Capacitor 原生 HTTP 直连三个平台（要原始文本、不跟随重定向、10 秒超时）。在不带 Node 的 Chromium 页面里回放上文保存的真实响应：酷狗 63 行 / 602 字、QQ 63 行、AMLL 78 行 / 736 字，签名与实测请求一致，第二次取同一首走缓存。Android WebView 要求 Chromium 80+，iOS 要求 16.4+（`DecompressionStream`）。

**实测**：经 Electron 传输层实网跑两轮《晴天》：第一轮 AMLL / QQ / 酷狗 分别发 2 / 2 / 3 个上游请求，第二轮 0 个。Web BFF 同一搜索第一次 2.25 s，第二次 3 ms。

**剩余风险**

- 手机端没有真机验证，尤其是 Capacitor HTTP 在 Android / iOS 上对字符串 JSON 请求体和 `disableRedirects` 的实际行为。
- 网易云、LrcLib 在手机 App 上仍是空实现（搜索返回空），与本次三个渠道无关，未处理。
- 缓存只在内存里：桌面 / 手机重启、BFF 重启后清空。

## 证据 复查与持续更新

仓库内的[脱敏记录](evidence/多源歌词渠道-2026-10-21.json)保存本次样本、固定上游版本、27 个请求的数量口径、9 份取词响应的 SHA-256/状态/单次耗时、解析统计、异常结果和离线复查输出。单次耗时不是基准测试或渠道速度排名。

完整请求、原始歌词响应、上游源码、探测脚本和视频抽帧仍留在仓库外。本仓库不附带这些内容，也不依赖某台电脑的绝对路径。摘要哈希用于与保留的原始响应核对；仅有摘要不足以在其他设备复现原始网络观测。

本次离线复查输出：

```text
RAW_RESPONSE_HASHES_OK=27
LIVE_FETCH_PARSE_PASS=9/9
PROVIDER_PASSES={"amll": 3, "kugou": 3, "qq": 3}
NEGATIVE_CONTROLS=AMLL_EMPTY,AMLL_404,QQ_BUSINESS_2001,KUGOU_EMPTY
```

其中 WORKSPACE_CONTENT_CHANGES 与 GIT_STATUS 是渠道探测阶段的历史核查值，不代表后续添加文档后的 Git 状态。复查是读取原始快照、检查哈希与格式，没有重新调用平台接口。

后续更新方式：

1. 同一主题持续更新本文与[主方案](多源歌词与镜台PV-调研方案.md)；新结论同步修正正文，不以零散聊天或另建副本替代。
2. 新增采样批次时记录日期、网络/平台条件、样本选择、上游版本、实际结果与失败类型，在 evidence/ 增加对应脱敏记录并保留旧批次。
3. 用户决定写入主方案的已确认范围；建议和未验证推断仍留在待确认区。
