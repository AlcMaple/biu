## 结论

- QQ、酷狗、AMLL 已完成中文/日文/英文各一首的匿名取词验证，共 9/9 获取和基本解析通过；项目集成尚未实施。详见[实际验证结果](多源歌词渠道-实测报告.md)。

- 镜台目标保留三维歌词、透视景深、镜头运动、逐字强调及程序化背景。普通放大、模糊滚动歌词只是降级显示，不作为镜台目标交付。

### 标准 AGPL 条款怎样影响接入

- 第 5(c) 条要求受覆盖的整合作品整体依该许可分发；第 7、10 条限制向接收者再加非商业等限制。这与 Biu 现有上游的非商业许可形成冲突。仅免费、署名、保留一个 AGPL 文件、改变文件名或只复制少量有版权表达的模块，都不构成完整兼容方案。
- 第 6 条还涉及分发二进制时的对应源码。第 13 条针对修改后的程序及其远程网络交互用户的源码获取机会，不等于任何 API 调用都要求把整个客户端向全世界公开。
- 仅个人本地研究与对外分发/运营服务不同。普通歌词数据的 API 输出也不自动继承服务程序许可；具体输出与程序耦合方式仍要分别判断。独立进程、iframe、WebSocket 本身不构成自动豁免。

## 二 新增 QQ 酷狗 AMLL 歌词渠道

### 接口事实与建议路径

| 来源 | 源码/文档确认的能力 | 建议接法与门槛 |
| --- | --- | --- |
| AMLL | 官方 HTTP API 有无需鉴权的 /v1/lyrics/search 与 /v1/lyrics/get，可按元数据、文件或平台 ID 取 TTML；另有 LRCLIB 兼容接口 | 3/3 样本已取回含词级时间标记的 TTML。保留社区作者和文件 ID，独立处理 TTML 解析许可。LRCLIB 兼容层可用于快速验证，但需实测其时间信息保真度，逐字保真度另验 |
| QQ | MIT 上游 3.3.3 的 getLyric 服务获取普通歌词文本及可选译文；Folia 的原生逐字 QRC 使用另一条 GetPlayLyricInfo 与解码链路 | 3/3 样本普通歌词已验证，可先接 MIT 上游 LRC + Biu 现有声学对齐。原生 QRC 作为单独增强项，其请求、解码来源和许可另验，不把 MIT 包的许可延伸到 Folia 文件 |
| 酷狗 | MIT 上游 v1.6.0 提供歌词搜索、凭歌词 ID/accesskey 下载，并有 decode 参数与 decodeLyrics 工具 | 3/3 样本已走通曲库 Hash/时长到 KRC 获取和解码。完整译文/时间语义与项目规范化仍待验证；无需先复制 Folia 的 KRC 解码器 |

本轮已按 AMLL → QQ → 酷狗完成有限样本接口验证，此顺序不代表质量/覆盖率排名。最终用户仍可自行选择，保留网易云与 LRCLIB。

### 用户流程

1. 在现有“搜索歌词”弹窗增加来源页签，沿用现有 UI，不另起一套搜索器或状态管理。
2. 按用户当前来源与查询搜索；显示歌名、歌手、专辑/版本、时长、来源和时间轴类型。避免一次操作默认向所有来源扇出请求。
3. 候选预览不写入当前歌词；明确点“采用”才替换。切歌、换关键词或切来源时，旧请求结果不能落到新目标上。
4. 新采用的歌词可继续走现有按当前 B 站录音对齐的流程。原生逐字、比例估算和当前录音声学对齐分别标识，平台逐字不直接等于当前录音精确对齐。
5. 保护用户手动选择、已有对齐结果和“还原/停止自动对齐”意图；不因某来源新返回了结果就静默覆盖。

### 数据与缓存边界

- 现有 MusicLyrics.source 表示 manual/auto/aligned/approved 等工作流，不把它改成 qq/kugou/amll。新增来源元数据应与采用方式、对齐方法分开。
- 规范化后以毫秒为内部单位，保留行/词的开始与结束、正文、译文、原始格式、原始来源 ID、时间轴来历和目标录音关系。现有 words 只有开始时间，适配时保留真实结束时间，避免降成逐行 LRC 后丢失逐字信息。
- 原生平台时间轴与按当前 bvid/cid 得到的 alignment 分别保存，避免将来源时间轴标成已经校准当前录音。旧缓存兼容，用户原选择不变。
- 沿用 platform 的存储能力和 LyricsCache，不直接新增 localStorage/IndexedDB 体系；跨设备内容避免绝对路径。缓存受数据许可与服务条款约束。
- AMLL 文档指出按歌词 id/filename 获取的具体文件固定，可长期缓存；搜索/平台歌曲 ID 的匹配会随词库更新，应分开设置有效期。限流时按本项目规则停止自动请求，保留缓存，不采用上游文档的自动退避重试建议。
- TTML 解析要覆盖时间表达和继承、命名空间、空格/换行、嵌套 span、译文、罗马音与多声部；不支持的特性要明确处理，避免静默错时。QRC 与 KRC 分开审查，文本处理不使用 HTML 注入。

### 各端请求与错误

Electron：沿用主进程 got 和固定 IPC 能力。Web：沿用既有歌词 BFF/代理，只允许写死来源与参数，不接收任意 URL、不传播 Cookie 或签名地址。Android/iOS：通过已有平台/原生 HTTP 或相应 BFF，需同时覆盖各端而非只补 Electron IPC；当前 mobile 的歌词搜索方法仍返回空值，需要明确补齐或展示能力状态。

分别呈现未收录、鉴权失败、429、超时/服务错误、格式不支持和版本不匹配。取消或切目标后丢弃过期结果；429/5xx 不自动重试、不探测恢复、不静默吞错。上游包可能有内部续期/补请求，选型时也要检查实际请求放大。

歌词渠道这一部分只新增取词能力，不新增 QQ/酷狗音频、账号管理、付费能力、全平台播放或任意网络代理。是否采用完整 API 包，取决于必要路由、可维护性、许可证和实际请求行为，不预设“必须整包”或“绝不整包”。

### 已确认的 Lumisynth 产品角色

**另增 Lumisynth 式 PV 选项已确认，不再作为“仅参考编排还是新增风格”的二选一。** 在保留项目原有精美样式和新增镜台的同时，提供 Lumisynth 式歌词动效与自动编排的独立外观路线。

具体采用哪套或若干套视觉语言，需先做动态参考对照与样例确认；用户本次确认的是增加这条产品路线，不据此默认四套风格全部进入首期。

镜台也可参考按歌词结构选镜头、段落转场、绝对时间采样与资源生命周期的设计思想，但两类视觉分别实现、分别验收。Lumisynth 的编排输出绑定其风格包，不是可直接套在独立镜台上的通用脚本；需要各自的编排与渲染适配。

内核具有外部 clock 和可选 AudioAnalysis 输入，是源码层面的适配入口，不等于已经形成 Biu 插件。Lumisynth 原工作流涉及导入音频及离线音频特征，Biu 流式播放时如何供应或省略这部分特征仍需验证。当前研究也没有验证四套风格在播放器中的完整动态表现。

新增 Lumisynth 式 PV 保留现有音频、歌词与声学对齐；不自动引入视频编辑器、视频导出或付费 AI。新增目标不等于批准直接搬入其 AGPL 编译器、内核与风格代码，仍按前述许可边界独立设计实现。

当前已确认“项目原有精美播放器样式＋Folia 镜台式三维 PV＋Lumisynth 式 PV”三类外观。两条新增路线均纳入后续实施目标；具体样例、细分范围和实现验证继续记录，不将范围确认写成效果已实现。

### 已选镜台路线的首期视觉范围

- 当前歌词以真实空间中的文字平面呈现，前后歌词分布在不同景深；镜头随演唱行移动，逐字强调和长句布局可读。
- 程序生成的几何/点阵装饰，加封面或默认主题驱动的流体/双色背景。视频效果涉及 Diorama 与独立 Latent 背景的组合，不只一个文字组件。
- 默认字体、调色与程序几何即可运行；用户图片、视频、模型、外部 AI 均不是每首歌的必需输入。自定义素材可后续单独设计。
- 保留当前精美样式；新的选择放在精美播放器内部，不混淆现有普通/精美开关。首期不加入 Lumisynth 完整编辑器、视频导出、AI 主题服务或节拍/人声分离模型。

### 播放与渲染结构

Biu 现有音频与播放状态 → 现有歌词显示/对齐状态 → 统一时钟和歌词适配 → 原有精美样式 / 镜台式三维 PV / Lumisynth 式 PV。播放器控制、进度、歌词采用/偏移仍由 Biu 管理。

- 复用 playback-clock.ts 的权威读时钟：正常播放读 audio.currentTime，暂停/跳转按既有进度状态处理；不新建 Audio 元素、不另计播放时间。
- 当前显示约定是 readPlaybackMs() + offset。内部保持毫秒，向秒制渲染器转换一次；源歌词偏移和用户偏移只应用一次，先核对正负语义。
- 相机、文字高亮与场景采样以绝对播放时间决定，支持任意 seek 和恢复，而非累计帧增量。逐帧 GPU 更新不经 React 高频 setState。
- 有音频响应时复用既有音频图/分析节点；没有 FFT 时仍保持核心歌词舞台。节拍分析不替代声学歌词对齐，基础渲染也不以 WebGPU 模型为前提。
- 暂停冻结歌词进度与叙事镜头；seek 直接定位目标行和场景；切歌期间不继续显示上一首的歌词。单曲循环与从头跳转明确区分，复杂跨曲镜头飞越可后续做。
- PV 懒加载，仅可见且启用时占用渲染资源；关闭/切样式释放材质、纹理、监听与循环。限制缓存的文字平面范围，处理 GPU context lost、字体/封面失败及长句。
- 使用现有 UI 与 framer-motion；Three.js/Paper 等是待批准的渲染依赖，不更换构建工具、不照搬 Folia 的状态库、主题与整套应用。

### 平台与降级

当前全屏入口先分移动布局，并以 !isWeb && useFancyPlayer 进入现有精美播放器。桌面首期与 Web/原生移动端开放范围需要单独确认，不把共享 bundle 误当各端入口已打通。

窄屏优先调整镜头视野、排版和效果密度，不以固定 768px 一刀切。根据 GPU 能力、实测负载和减少动态效果设置分级：降低装饰/背景负载，必要时回到现有歌词展示；音频、所选歌词与进度保持连续。后台停止无用 GPU 渲染，恢复后从权威时钟直接重采样；不影响现有桌面歌词窗口。

## 四 后续阶段与验收门槛

以下是获得实施确认后的顺序，本轮未执行集成或运行效果验证。

歌词渠道已有有限样本证据，可以进入集成准备；镜台可以进入独立交互样例阶段；Lumisynth 式 PV 已纳入目标，接下来收敛具体风格与动态样例。其余平台集成、三类外观切换一致性和性能是实施中的验证工作，不需要重新讨论是否加入这两条 PV 路线，也无需扩大为一轮通用项目选型调研。

| 阶段 | 交付 | 进入下一阶段的门槛 |
| --- | --- | --- |
| 0 许可与范围 | 独立实现路线已定；按具体选型补齐底层依赖/数据许可与首期平台 | 相关模块有可发布依据；现行 Biu 许可和上游权利保持明确 |

重点验收：

- 同版本原唱与翻唱/现场/变速/剪辑分别测试；不因歌名相同就沿用源时间轴。
- 中英日韩、长句、空行、前奏尾奏、重复词、重叠声部、无译文与无逐字分别处理。
- 预览后取消不落盘；采用后仍能还原；对齐结果与来源变更不互相误标。
- 无歌词、需登录、429、5xx、取消、快速切歌均有可见且准确的状态；没有静默重试风暴。
- 暂停时逐字和镜头停止，seek 后直接落在目标位置；原有、镜台式、Lumisynth 式三类外观相互切换不中断音频，也不重复创建音频图。
- 背景/封面/字体异常、GPU 失效或降低画质仍有歌词与控制；窄屏键盘/触控均可操作。
- 测量首帧耗时、持续播放帧耗时、GPU/内存与多次开关释放情况，按同设备旧样式对照。性能预算及阈值在实测后定，本方案不宣称已达某帧率或观感百分比。
