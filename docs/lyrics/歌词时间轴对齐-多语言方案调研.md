# 歌词时间轴对齐：多语言（非中文）方案调研

> 2026-10-20 · 接 `歌词时间轴对齐-可行方案调研.md` 5.2.9 ~ 5.2.15（中文方案）与 `docs/ideas/002-歌词时间轴对齐.md` 第 4 节第 10 条

## 1. 结论

- **日语、韩语：在现有「分离人声 + MMS_FA」上补几处就能用**：
  1. 按语种转写：日语先过 MeCab 取读音，韩语逐音节转罗马字。
  2. 歌词清洗补上「演唱者标注」行。
  3. 新增「离群行局部重对齐」。
- **英语：对齐模型换成在歌声上训练的开源模型**（[LyricsAlignment-MTL](https://github.com/jhuang448/LyricsAlignment-MTL)，MIT 许可），再叠加同样的离群行修复。
  - 换模型后，所有指标都超过「MMS + 全部修复」。
  - 每首对齐从约 35 s 降到约 10 s。
  - 详见 4.8。
- **日语达到中文水准的大半**：行起点中位误差 47 ms，95% 的行误差在 300 ms 内，483 行里只有 1 行错 1 s 以上。
- **英语接近中文水准**：
  - 行起点中位误差 39 ms，95% 的行在 300 ms 内。
  - 643 行里 9 行错 1 s 以上，网易云逐行同口径是 20 行。中文 327 行里只有 1 行，英语还有差距。
  - Faded 中段连续重复短句整段错位的问题，已经靠「滑动扫描」修好（4.8），这首从 6 行降到 0 行。
  - 剩下的失败集中在：网易云原时间本身错的行、只有一个拟声词的行、同一句副歌连唱几遍的行。
- **韩语只有 3 首真值，样本不足以下结论**。网易云和 AMLL 社区库都找不到更多韩语逐字歌词；用户已定先不补（曲库里韩语歌少），等收录了韩语歌再处理。
- **线上的「歌词和音频对不上」判据不能用于外语**：
  - 23 首对得上的外语歌里，有 6 首会被它误判成配错，其中英语 5 首。
  - 换成「对齐出的行起点和原歌词时间是否吻合」以后，23 首对得上的歌吻合 80% ~ 100%，11 组故意配错的歌只有 6% ~ 27%，两边分得很开。
- **中文路径保持不变**：新增步骤只对外语生效，中文 27 ms / 96% 的结果不受影响。

## 2. 现有中文方案为什么不能直接用于外语

模型本身（MMS_FA）是多语言的，只认 a-z 和 `'`。中文能用，是因为先把汉字转成了拼音。直接搬到外语上会在三处坏掉：

| 问题 | 线上现象 | 原因 |
|---|---|---|
| 日语歌报「歌词对不上」 | 日语里的汉字被当成中文按拼音去对；假名直接丢掉 | 转写只有拼音一条路 |
| 纯韩文歌词报「暂时只支持中文和拉丁字母的歌词」 | 谚文全部丢掉，一个可对齐的字都没有 | 同上 |
| 英语歌能出结果，但部分行整行错位 | 行首被吸到前奏 / 伴唱上，或者重复短句整段错一个轮次 | 中文没有这类伴唱交错，原方案没有针对它的修复 |
| 对得上的英语歌被判成配错 | 判据要求「行置信度中位数 < 0.25 且局部重对齐 ≥ 3 行」 | 阈值只用中文歌标定过。英语的声学置信度整体偏低：对得上的英语歌中位数 0.11 ~ 0.33，中文是 0.28 ~ 0.67 |

## 3. 前人成果

按用户要求，先找现成方案，没有现成的才自研。

| 方案 | 做法 | 结论 |
|---|---|---|
| [PotLyrics](https://huggingface.co/Mes51/potlyrics-align) | Demucs 分离人声 + MeCab 转罗马字 + MMS 强制对齐 | 和我们的日语路线完全相同，说明这条路有人走通。但作者只测了 1 首日语（逐字中位 67 ms，82% 在 200 ms 内），没处理伴唱 |
| [lyric-align](https://pypi.org/project/lyric-align/) | Whisper 识别 + 模糊匹配 | 此前已否决：识别错字时整段漂移 |
| [Spotify ICASSP'23](https://arxiv.org/abs/2306.07744) | 对比学习，音频和歌词映射到同一空间 | 学术上最好，在 JamendoLyrics 上平均误差 < 0.2 s，只用英语训练也能迁移到其他语种。**没有公开权重**，用不上 |
| [LyricsAlignment-MTL](https://github.com/jhuang448/LyricsAlignment-MTL)（Huang 等，ICASSP 2022） | 在歌声（DALI 数据集）上训练的音素识别模型，联合做音高检测。仓库带训练好的权重 | MIT 许可，只支持英语。**英语采用它**：同一套评测下全面好于 MMS（4.8） |
| [LyricsAlignment-Multilingual](https://github.com/jhuang448/LyricsAlignment-Multilingual)（同作者，ISMIR 2025 LBD） | 同一网络，音素换成 IPA（espeak-ng），覆盖英、法、德、意、西 | 英语指标和上一行持平（4.8），但多依赖一个系统库 espeak-ng。以后要支持西语、法语等时再用它 |
| [DAFx 2025（产综研）](https://dafx.de/paper-archive/details/o-wYFu7sQFE_GuYrAHxIHA) | 掩码帧级交叉熵 | 在 Jamendo 上平均误差 0.216 s，没找到公开代码 |

- 学术基准是 JamendoLyrics MultiLang（英 / 法 / 德 / 西，词级时间），不含中日韩，所以不能直接拿来评我们的曲库。
- 没找到「B 站投稿 + 外语歌词对齐」的现成项目。

**所以中日韩仍以 MMS_FA 为主体，英语换成 LyricsAlignment-MTL**：

- 日语转写照 PotLyrics 的做法。
- 伴唱错位和配错判断是这些项目都没处理的部分，第 4 节是在它们的基础上补的。
- 歌声对齐模型只有英语（及西欧语种）的现成权重，中日韩没有，所以中日韩只能继续用 MMS。

## 4. 方案（拟采用）

整体链路不变：服务端拉 B 站音频 → Demucs 分离人声 → 强制对齐 → 局部重对齐 → 结果缓存共享。

- 中日韩：对齐模型仍是 MMS_FA（双切法平均 + 静音门控）。
- 英语：对齐模型换成 LyricsAlignment-MTL（4.8），分离人声、清洗、离群行修复、配错判据和中日韩共用。

### 4.1 语种检测（整首判一次）

- 整首出现 ≥ 5 个假名 → 日语。
- 否则出现 ≥ 5 个谚文 → 韩语。
- 都没有、但有汉字 → 中文路径（汉字转拼音，拉丁字母原样）。中文歌里夹英文的也走这条路。
- 一个汉字、假名、谚文都没有 → 英语路径（4.8）。

实测：21 份中文歌词全部判为中文，11 首英语、9 首日语、3 首韩语全部判对。

已知缺口：西语、法语等非英语的拉丁字母歌词也会进英语路径，被按英语发音转音素。样本里没有这类歌，没测过。要支持时，换用同作者的多语言版并加语种识别（6 节）。

**为什么按整首判，而不是逐字判**：日语歌词里的汉字单看分不出是中文还是日文。按整首判，有假名就整首按日语读，汉字才能拿到日语读音。

### 4.2 转写

| 语种 | 做法 | 新依赖 |
|---|---|---|
| 中文 | 拼音（与线上一致） | 无 |
| 日语 | MeCab（fugashi + unidic-lite）按上下文取读音，再把读音分回每个汉字和假名 → uroman 转罗马字。助词「は / へ」按发音读 wa / e；促音、长音不单独给字母；多字汉字按音拍平均切（花火 → ハナ / ビ），只影响字内点亮，行起点仍来自音频 | fugashi 1.5.2（1.2 MB）、unidic-lite 1.0.8（**248 MB**） |
| 韩语 | 每个谚文音节单独用 uroman 转写 | uroman 1.3.1.1（4.1 MB，Apache-2.0） |
| 拉丁字母 | 原样小写 | 无 |

**为什么日语不能直接用 uroman**：uroman 官方说明，汉字一律按中文读音转写。「花火」会变成 huahuo，而不是 hanabi。

**为什么用 unidic-lite 而不是更小的 ipadic**：unidic 对口语和活用形的读音更准。250 MB 只占服务端磁盘，不进客户端。

### 4.3 歌词清洗补充

在 `biu-align-server/src/lib/lyrics.ts` 现有规则上补两类：

1. **日韩文制作人员行**：`作詞` / `編曲` / `作詞・作曲` / `작사` / `작곡` / `편곡`，以及英文 `Lyrics` / `Composer` / `Written` 加冒号的行。
2. **整行是演唱者标注**：
   - 方括号整行一律删，例如 `[Chorus]`、`[Verse 1: X]`。
   - 圆括号整行，且里面每个词都首字母大写（连接词 & / x / feat 除外）、又不全是 Oh / Yeah 这类拟声词，也删，例如 `(The Kid LAROI)`、`(The Kid LAROI & Justin Bieber)`。
   - 保留：`(Oh, ooh-woah)`、`(Ohhhhh Ohhh Ohhh)`、`(Take that money)` 这类真正唱出来的伴唱。

实测：在 2263 行歌词（全部中、日、韩、英样本）里，只删掉了 STAY 的 7 行演唱者标注，没有误删。STAY 删掉这 7 行以后，行起点中位误差从 239 ms 降到 94 ms。

已知风险：首字母全大写的伴唱，比如 `(Take That Money)`，会被误删。误删一行的代价是这一行没有时间，比让人名去占一段音频小。

### 4.4 离群行局部重对齐（新增，只对外语）

**要修的问题**：英语里常见行首被提前吸到伴唱 / 前奏上，或者重复短句和伴唱交错。

- Blinding Lights 第 2 行「I've been on my own for long enough」里，前三个词被挤到上一行行尾，提前了 2.2 s，后面的词位置是对的。
- Counting Stars 的「Take that money / Watch it burn」整段错了一个轮次，3 ~ 4 s。

**做法**：

1. 判定离群：拿每行「对齐起点 − 原歌词时间」，和前后各 5 行同一差值的中位数比，差出 0.5 s 以上就算离群。前后几行一致，说明这一段原歌词时间对这份录音可信，唯独这一行丢了位置。
2. 重对齐：只在「原歌词时间 + 本地偏移」前后 0.6 s 到下一行之间的窗口里，单独把这一行再对一次。**逐字时间仍然来自音频**，不是回退到原歌词时间。
3. 三道闸，全部满足才采纳：
   - 新起点离预期位置 ≤ 0.5 s；
   - 新起点比旧起点更靠近预期位置；
   - 新的声学置信度不低于旧的 85%。如果旧位置已经和前后行**顺序颠倒**（比上一行还早，或比下一行还晚），免掉这一条。
4. 跑 2 轮：第一轮修好的行会改变邻居的本地偏移。

**为什么不要求「新置信度必须更高」**（交接时的版本）：Blinding 第 2 行重对齐已经落到 34.53 s，和真值完全一致，却因为置信度 0.171 < 0.178 被拒。挤到错位置的那几个词本来就很短，挪回去整行平均置信度几乎不变。

**为什么还要留 85% 这道闸**：Someone Like You 第 2 行和第 48 行恰好是网易云原歌词时间本身错了（+1.55 s、+1.69 s），整首对齐反而是对的。不设闸时，这两行会被「修」到错的原时间附近，新置信度只有旧的 80% ~ 82%；被正确修好的行都在 88% 以上。这是唯一能区分两类的信号，但样本只有这几行，0.85 和 0.80 的整体差别也只有 2 行（26 对 28）。

**为什么顺序颠倒的行免掉置信度闸**：Counting Stars 的「Take that money」错位到的是同一句的上一遍。那里也真的唱了这几个词，置信度天然和正确位置一样高，置信度闸永远过不去。顺序颠倒在歌词里不可能出现，比置信度更可靠。

**为什么不把窗口放宽到同时包住旧位置和预期位置**（试过）：放宽后，Blinding 一行都修不好；6 首英语里错 1 s 以上的行只从 45 减到 40，同样 6 首用「只在预期位置附近找」能减到 27。错位置本身对模型有吸引力，窗口包进去，局部对齐还是会选它。

**为什么只对外语开**：中文 327 行只有 1 行错 1 s 以上，已经人耳确认过。只对外语开，中文就不用重新做人耳确认，也不用重新标定。

上面的例子和参数都是在 MMS 上调出来的。英语换成歌声模型后，原样搬过去：错 1 s 以上的行从 18 降到 15，没有一首变差（4.8）。

### 4.5 「歌词和音频对不上」判据：改用时间吻合度

**新判据**（原歌词带时间时）：

- 用**修复前**的整首对齐结果，算有多少行的起点落在「原歌词时间 + 整首偏移」±1 s 以内。
- 低于 50% 判为配错。

| | 行起点吻合度（±1 s） | 行置信度中位数 | 局部重对齐行数 |
|---|---|---|---|
| 对得上：英语 11 首（MMS） | **80% ~ 97%** | 0.111 ~ 0.325 | 1 ~ 42 |
| 对得上：英语 11 首（歌声模型，拟采用） | **89% ~ 100%** | 0.305 ~ 0.534 | 0 ~ 5 |
| 对得上：日语 9 首 | **92% ~ 100%** | 0.228 ~ 0.509 | 0 ~ 12 |
| 对得上：韩语 3 首 | **88% ~ 100%** | 0.153 ~ 0.333 | 0 ~ 13 |
| 对得上：中文 10 首（旧输出，交叉验证） | **98% ~ 100%** | — | — |
| 故意配错：英语 4 组（MMS） | **6% ~ 11%** | 0.061 ~ 0.123 | 9 ~ 31 |
| 故意配错：英语 4 组（歌声模型，拟采用） | **6% ~ 23%** | 0.152 ~ 0.257 | 14 ~ 26 |
| 故意配错：日语 4 组 | **8% ~ 27%** | 0.135 ~ 0.242 | 11 ~ 37 |
| 故意配错：韩语 3 组 | **12% ~ 25%** | 0.086 ~ 0.160 | 21 ~ 30 |

故意配错的组合是同语种的另一首歌的歌词：Blinding Lights + Perfect、Yellow + Someone Like You、Sugar + Viva la Vida、Faded + Love Story、Lemon + 群青、夜に駆ける + ドライフラワー、アイドル + 打上花火、紅蓮華 + 千本桜、Celebrity + Black、Psycho + Celebrity、Black + Psycho。

**为什么必须用修复前的结果**：局部重对齐和离群行修复本来就是把行往「原歌词时间 + 偏移」附近拉。拿修复后的结果算，配错的歌也会被拉出很高的吻合度。

**为什么不继续用置信度**：配错的日语组合（アイドル音频 + 打上花火歌词）置信度 0.242，比 7 首对得上的英语歌还高。英语声学置信度整体偏低，任何一个阈值都会两头误判。重对齐行数也不行：对得上的 Shape of You 有 42 行，比所有配错组合都多。

**为什么阈值定 50%**：对得上的最低 80%（Blinding Lights，伴唱多），配错的最高 27%（紅蓮華 + 千本桜，两首都是快歌）。50% 落在中间，两边各留出 20 多个百分点。

**原歌词没有时间时**（只出现在用户上传歌词）：

- 日语、韩语只能看置信度，但两边重叠（对得上的最低 0.153，配错的最高 0.242），分不开。
- 英语换成歌声模型后，置信度能分开：对得上的最低 0.305，配错的最高 0.257。但间隔只有 0.05，样本只有 11 首对 4 组。
- 建议：没有时间的外语歌词一律不做自动判错，交给人工审核。用户上传本来就要先预览，再由审核员通过。
- 中文继续用原规则：中位数 < 0.2。

**中文要不要也换成新判据**：

- 吻合度在中文对得上的歌上同样是 98% ~ 100%，换过去大概率没问题。
- 但中文的 4 组配错样本是用旧输出标定的，没有修复前起点这一项，要重跑才能确认。
- 建议：先按语种分开，中文保留原判据；以后要统一，再补这 4 组。

### 4.6 中文路径保证不变

- 转写：21 份中文歌词，新旧转写送进模型的字母序列逐行对比，完全一致。唯一不同的一行是「后来」里的 `ISRC …` 编号行，线上清洗本来就会删。
- 挤压检测：新版对拉丁字母按词首计时，中文歌里夹英文的行（江南 5 行、唯一 6 行……）会受影响。所以实现时，语种为中文就沿用线上规则「跳过所有 ASCII 字符」。
- 离群行修复和新判据：只对日语、韩语、拉丁字母歌词开。

做到这三点，中文的输出和线上逐字节一致，不需要重新分离人声做回归。

| `src/lib/result.ts` | `looksMismatched` 按语种分开：外语用吻合度 < 50%；没有时间的外语歌词不判错；中文不变。`quality` 里加吻合度，审核页同时显示 |
| `src/lib/result.ts` | `ALIGNER_VERSION` 1 → 2。`LYRICS_MISMATCH` 是粘滞失败，会被缓存。不加一，线上以前记下的日语「对不上」会一直命中旧结果 |
| `src/lib/errors.ts` | `LYRICS_UNSUPPORTED` 文案改为「暂时只支持中文、日语、韩语和英文等拉丁字母的歌词」。俄语、泰语等 uroman 能转写，但没有测过，先不开 |
| 客户端 `QUIET_AUTO_FAILURES` | 保留。自动对齐碰到不支持的语种（如俄语）仍然不该弹提示，用户没主动发起 |

**性能**（不含 Demucs）：

- 中日韩：单首对齐约 35 s，只在 Blinding Lights 上用 MMS 计过时，和线上相当。离群行修复只重对齐个别行，MeCab 分词耗时可以忽略。
- 英语歌声模型：Counting Stars（约 4 min）对齐 9.5 s，内存峰值 3.5 GB，和 MMS 的 3 ~ 4 GB 相当。
  - 它整首一次过双向 LSTM，不分块，所以没有 MMS 的块边缘问题。
  - 歌越长，内存越高，按时长线性增长。现在服务端对投稿时长有上限，在上限内没有问题。

### 4.8 英语：换用歌声训练的对齐模型

**为什么换**：

- MMS 是在朗读语音上训练的。英语歌里大量伴唱、和声和拖长音，它会把行首吸到伴唱上（4.4 的两个例子）。
- LyricsAlignment-MTL 是在 DALI 歌声数据集（以英语流行歌为主，分离人声后训练）上训练的，正好针对这类情况。

**怎么接**：

- 输入沿用同一份 Demucs 分离人声，按原仓库的做法先重采样到 16 kHz 再到 22.05 kHz（模型在 16 kHz 分离人声上训练），算 128 维 mel 送进模型。
- 歌词用 g2p_en 转成英语音素（39 个，去掉重音标记），词与词之间夹一个「空格」音素，和原仓库一致。
- 解码：
  - 原仓库是纯 Python 动态规划，一首要几分钟，改用 torchaudio 的 CTC 强制对齐，同一套接口 MMS 也在用。
  - 两者唯一的差别：CTC 要求同一音素连续出现时中间夹一个空白。词间本来就有空格音素，影响可以忽略。
- 帧长 34.8 ms，比 MMS 的 20 ms 粗，实测没有体现在误差上。
- 4.3 的清洗、4.4 的离群行修复、4.5 的配错判据原样复用。

**三个权重 / 版本的对比**（11 首，口径同 5.1，都不加离群行修复）：

| | 行起点：中位 / ≤ 150 ms / ≤ 300 ms / > 1 s | 段起点：中位 / ≤ 150 ms / > 1 s |
|---|---|---|
| MMS + 全部修复（交接后调出的最好结果） | 56 ms / 77% / 87% / 26 | 64 ms / 81% / 185 |
| MTL 仓库 · 基线权重 | 46 ms / 75% / 82% / 88 | 56 ms / 75% / 687 |
| **MTL 仓库 · MTL 权重（带音高任务）** | **40 ms / 86% / 93% / 18** | **50 ms / 88% / 100** |
| 多语言仓库（2025）· 基线权重 | 39 ms / 85% / 93% / 18 | 50 ms / 88% / 115 |
| 参照：网易云逐行 | 95 ms / 63% / 81% / 20 | — |

- 基线权重在 Shape of You 上整首跟丢（行起点中位误差 2 s，85 行里 76 行错 1 s 以上），其余 10 首都不错。带音高任务的 MTL 权重没有这个问题，所以选 MTL 权重。
- 多语言版和 MTL 权重打平，但要多装一个系统库 espeak-ng（Homebrew 上和老的 espeak 冲突，实验时是解包到实验目录里用的）。只做英语时不值得，以后要支持西语、法语再换。

**再加离群行修复**：40 ms / 87% / 94% / **15**，段起点 50 ms / 88% / 87。错 1 s 以上的行从 18 降到 15，11 首里没有一首变差。

**再加滑动扫描兜底**（拟采用）：39 ms / 88% / 95% / **9**，段起点 50 ms / 89% / 72。

Faded 第 36 ~ 41 行（「Where are you now」×2 +「Another dream」×4，2:14 ~ 2:30）一起晚了一个轮次，离群行修复修不动，原因有三：

1. **邻居也是错的**：每行只和前后各 5 行比，这 6 行一起错，看不出离群。
2. **原歌词时间本身偏了**：网易云对这几行的时间早了 0.5 ~ 1.3 s，正确位置过不了「离预期 ≤ 0.5 s」那道闸。
3. **长窗口会把起点拖早**：在一个长窗口里对齐一行时，CTC 会把第一个音素拉得很长，起点被拖到窗口前部的弱匹配上。例如「Another dream」整窗对齐给出 145.17 s，真值是 146.24 s。

诊断：在 2:13 ~ 2:33 每隔 0.2 s 用 1.4 s 的短窗扫一遍「Another dream」。模型在 140.85 / 143.50 / 146.18 / 148.4 s 有四个清楚的峰，真值是 140.93 / 143.56 / 146.24 / 148.91 s。也就是说，**音频里的证据是对的，坏在用法上**。

修法：离群行修复的原做法失败时，再试一次扫描。

- 在「原歌词时间 + 本地偏移」±1.5 s 范围内，每 0.1 s 放一个短窗。窗长取这一行到下一行原时间间隔的 0.6 倍，限制在 1 ~ 3 s。
- 每个短窗单独对齐这一行，取平均置信度最高的位置。
- 采纳条件：
  - 离预期 ≤ 1.5 s，比旧位置更近；
  - 和旧位置相差 > 0.2 s；
  - 夹在前后两行之间。这里只和没被判离群的行比：连续错位时，紧挨着的邻居自己也是错的；
  - 置信度不低于旧的 85%，或者旧位置和前后行顺序颠倒。

效果：Faded 第 36 ~ 40 行都落在真值 0.07 s 以内，最后一行「Another dream」差 0.49 s。

| 修复方式（11 首英语） | 行起点：中位 / ≤ 300 ms / > 1 s | 说明 |
|---|---|---|
| 原离群行修复 | 40 ms / 94% / 15 | Faded 6 行错 |
| 只用扫描（替换原做法） | 39 ms / 95% / 10 | Faded 修好，但 Blinding、Shape of You、Counting Stars 各有 1 ~ 2 行反而变差：长句塞不进短窗，扫描找不到原做法能找到的位置 |
| **原做法优先，失败再扫描（拟采用）** | **39 ms / 95% / 9** | 11 首里没有一首变差 |
| 同上，邻居范围放宽到前后 8 行 | 39 ms / 95% / 11 | Shape of You 少 2 行错，但 Someone Like You、Yellow 各多 1 行、Faded 多 2 行，合计多 2 行，不采用 |

**试过但没用的：成段重对齐**。把连续几行放在前后两行好行之间一起重对齐：

- 前后各 5 行时，判出来的段把对的行也包了进去。
- 前后各 8 行时，段判对了（第 36 ~ 41 行），但一起对齐的结果和原来一模一样。错位置本身对模型有吸引力，空档里包着它，联合对齐还是选它。实验代码里留着这个开关（`BLOCK=1`），没有采用。

扫描目前只接在英语歌声模型上。MMS（中日韩）没有测过，日语 483 行里只有 1 行错 1 s 以上，暂时不需要。

**为什么不把两个模型的结果合并**：

- 按「错 1 s 以上的行数」，歌声模型在 11 首里有 10 首好于或等于 MMS，只有 Faded 差（歌声模型 6 行，MMS 3 行）。
- 合并要再加一套「哪个模型对」的判据，又是一个只有 11 首能标定的阈值。收益最多几行，不值。

**许可**：

- 代码和权重都是 MIT。
- 训练数据 DALI 是研究用途数据集，权重的上游数据许可和 MMS（CC-BY-NC 4.0）属于同一类问题。中文方案阶段已经接受过 MMS 的非商用限制，这里不额外增加限制。

## 5. 实测

### 5.1 数据与口径

- **样本**：英语 11 首、日语 9 首、韩语 3 首，全部是 B 站录音室版投稿（MV / 官方音源），音频跳过 PCDN 节点下载。
- **输入**：网易云逐行歌词，等同于线上「原歌词」。
- **真值**：网易云逐字歌词（yrc）；没有时，用 AMLL 社区库（CC0）同 id 的逐字歌词。
- **打分**：
  - 两边都摊平成字符流，整首配对。
  - 只在真值每段的首字符上打分。
  - 每首扣掉自己的中位偏移，B 站投稿和网易云音源之间有固定差。
- **两组指标**：
  - 行起点：每行第一个字。
  - 段起点：英语每个词，中日韩每个或几个字。
- **参照栏**「网易云逐行」：把输入的原歌词行时间直接当答案，同口径打分，也就是「不对齐、只平移」的水准。
- 中文已用同一口径重算（7 首 327 行），可以直接对比。

### 5.5 日语、韩语要注意的点

- **夜に駆ける**：行起点 82 ms，正常；段起点 165 ms，明显偏大。怀疑是真值的分段粒度问题（yrc 一段含几个字，我们按字亮），未核实。
- **アイドル**：行起点 96 ms，是日语里最差的一首。错 1 s 以上的行从 3 行降到 0 行。
- **快歌的挤压检测会误触发**：真值里うっせぇわ、夜に駆ける、アイドル各有约 10 行字距 < 0.15 s，是真唱这么快，不是对齐挤压。触发后只会多做一次局部重对齐，指标没有变差。旧判据会把「重对齐行数」算进配错判断，うっせぇわ有 8 行；新判据不用这个数，所以误触发不再有后果。
- **韩语 Psycho**：行起点 94 ms，错 1 s 以上的有 4 行，是韩语里最差的一首，未逐行查。

## 6. 剩余风险

- **歌词里的特殊读法**：日语「本気」写作「マジ」读、当て字，MeCab 只会给字典读音。这些字的行内点亮会错，行起点通常不受影响（前后字是对的）。
- **数字不发音**：「2」「100」在 MMS 字母表里没有，这些字的时间取前一个字。中文、日语、英语都有这个问题，样本里没出现成片数字的行。
- **韩语连音**：逐音节转写不处理连音（如 「먹어」读作 머거），字母序列和实际发音有偏差。3 首里没看出明显影响，样本太少。
- **英语里网易云原时间本身错的行**：见 5.4，修复以原时间为锚，锚错了就修不了，这是英语剩余误差的主要来源。
- **非英语的拉丁字母歌词**（西语、法语等）：会进英语路径，按英语发音转音素，没测过。曲库里出现这类歌时，再换成同作者的多语言版（espeak-ng 支持对应语种）并加语种识别。
- **英语歌声模型对长歌的内存**：整首一次过，4 min 的歌峰值 3.5 GB，随时长线性增长。投稿时长上限必须保留。
- **韩语样本只有 3 首**：两轮在网易云共搜了约 30 首热门韩语歌，除已经在用的 Celebrity、Psycho 外都没有逐字歌词（Fake Love 只找到翻唱版）；AMLL 社区库里除已在用的 Black 外，没有韩语歌。要扩样本只能走 QQ 音乐逐字歌词（QRC 格式，需要解密）。用户已定（2026-10-20）：曲库里韩语歌少，先不补，收录韩语歌后再处理。

| `align_ml.py` | 实验版 worker（MMS，中日韩）。开关：`OUTLIER=1 GATE=ratio GATE_R=0.85 ORDER=1` 即拟采用方案。`WIN=union` 是 4.4 里否掉的窗口做法；`DBG=1` 逐行打印候选与闸门判定 |
| `huang_align.py` | 英语歌声模型的对齐脚本（4.8）。`OUTLIER=1 SCAN=1` 即拟采用方案（离群行修复 + 扫描兜底）；`BLOCK=1` 是否掉的成段重对齐；`NB_W` 改邻居范围；`DBG=1` 打印每次扫描的判定。第一个参数 `mtl` / `multi` 选仓库，第二个参数 `Baseline` / `MTL` 选权重 |
| `diag_scan.py` | 诊断：在一段时间里滑动短窗，看模型认为某一行在哪些位置最像 |
| `listen_ml.py` → `../listen/ml.html` | 试听页 |
| `../ext/LyricsAlignment-MTL`、`../ext/LyricsAlignment-Multilingual` | 两个开源仓库（含权重），`git clone --depth 1` 拉的 |
| `../ext/espeak-ng/` | espeak-ng 1.52 的 Homebrew 包解包到这里，改了动态库路径、重新做了本地签名。只有多语言版需要；系统里原来的 espeak 没动 |
| `eval_ml.py` / `lines_ml.py` | 多语言评测 / 逐行列误差 |
| `consist.py` | 4.5 的时间吻合度 |
| `out/<key>.r85o.json` | 中日韩拟采用方案的输出；英语的 `.r85o` 是 MMS 最好结果 |
| `out/<key>.c5.json` | 英语拟采用方案（歌声模型 MTL 权重 + 离群行修复 + 扫描兜底）的输出。`.hmmo` 是不带扫描的上一版，`.hmm` / `.hmb` / `.hxb` / `.hxbo` / `.s5` / `.c8` 是 4.8 表里的其他组合 |
| `out/mm-<音频>+<歌词>.r85o.json` | 故意配错的 11 组（MMS）；英语 4 组另有 `.hmmo`（歌声模型） |
| `lrc/en-stay.raw.json` | STAY 清洗前的原歌词，`orig.json` 是清洗后的 |

运行命令（在 `spike-2026-10/` 下执行）：

```bash
BIU_ALIGN_VOCALS=ml/sep/<key>/vocals.wav OUTLIER=1 GATE=ratio GATE_R=0.85 ORDER=1 <python> ml/align_ml.py none ml/lrc/<key>.orig.json ml/out/<key>.r85o.json ml/work/<key>
SUFFIX=.r85o python3 -I ml/eval_ml.py <keys…>
OUTLIER=1 SCAN=1 <python> ml/huang_align.py mtl MTL ml/sep/<key>/vocals.wav ml/lrc/<key>.orig.json ml/out/<key>.c5.json
SUFFIX=.c5 python3 -I ml/eval_ml.py <英语 keys…>
```

多语言版还要设两个环境变量，指向 `ext/espeak-ng` 里的数据目录和动态库：`ESPEAK_DATA_PATH`、`PHONEMIZER_ESPEAK_LIBRARY`。
