# 歌词时间轴对齐：可行方案调研

> 调研日期：2026-10-19。代码基线：`9ccfb92`（2.7.0）。
> 状态：**开发前调研**。本轮没有调用任何付费 ASR、没有跑新歌，文中的准确率数字都标了出处；没有出处的就是待验证。
> 用途：后续按本文实施。第 5 节的验证门槛必须先过，过了再写 UI。

## 0. 结论

**可行，并且推荐的路线不是新发明，而是开源社区对「已有歌词 + 整曲音频」的标准做法：**

> 能识别带伴奏歌声的 ASR 给出**字级时间戳** → 用**已知歌词**去匹配 ASR 文本（容忍听错字）→ 把时间戳借给已知歌词 → 输出行级 LRC。

lyric-align、stable-ts `align()`、PotLyrics、syncalong 都是这个范式（第 3 节）。Biu 之前第三次尝试（阿里云 ASR + DTW）走的就是这条路，而且在《唯一》上**已经对准了**——它不是败在算法上。

具体方案：

1. **在服务端做，一首歌只算一次，结果全平台共享。** 客户端只提交 `bvid + cid + 当前歌词`，服务端自己取 B 站音频、调 ASR、对齐、缓存。用户机器上不装 Python、不跑模型、不上传音频。
2. **ASR 用云端 Fun-ASR**（阿里百炼，支持带伴奏整曲、字级时间戳，之前已实测《唯一》）。引擎做成可替换接口，后续可换自建 Qwen3-ASR（Apache-2.0、官方标明支持带 BGM 歌曲）省掉按次费用。
3. **对齐算法沿用已有 DTW**（`biu-lyrics-server/src/lib/`，66 个单测全绿）。本来打算拿开源的 lyric-align（MIT，CJK 优先）对标，第 5.2 节 5 首实测里，同一份识别结果交给 DTW 准得多，所以不引入 lyric-align。
4. **优先「整体平移」，不得已才逐行重打时间**。网易云 / LrcLib 的行间节奏是人工打的，通常比 ASR 准；B 站音频多数只是同一录音前面多了几秒。ASR 只用来找偏移，残差大（剪辑版、Live 版）才逐段/逐行改。
5. **用户主动触发**，不自动对每首歌跑；结果标出「哪些行是 ASR 真识别到的、哪些是推测的」，可一键还原。

## 2. 问题拆解：B 站音频为什么对不上

网易云 / LrcLib 歌词是按**官方发行版音频**打的轴。B 站的投稿音频与之不一致，常见几类（频率是经验判断，待第 5 节样本统计）：

| 类型 | 表现 | 需要的修正 |
|---|---|---|
| A. 同一录音，前面多/少了几秒（MV 片头、UP 主加的黑场、裁掉前奏） | 全曲恒定偏移 | 一个全局偏移即可，原歌词行间节奏全保留 |
| B. 同一录音，中间被剪过（删间奏、MV 中插对白） | 分段恒定偏移 | 分段偏移 |
| C. 不同版本（Live、翻唱、变速、Remix） | 节奏整体不同 | 逐行重打时间 |
| D. 歌词与演唱内容不一致（副歌只写一遍、歌词版本不对） | 部分行没有对应演唱 | 标为「推测」，不能假装对准了 |

现有的「歌词偏移」控件（`src/components/lyrics/offset-control.tsx`）只能手动解决 A。本方案要自动解决 A/B/C，并把 D 如实暴露给用户。

## 3. GitHub / 开源现状

本轮检索没有找到「B 站音乐播放器 + 自动对齐歌词」的现成项目：BBPlayer、bili-music、APM 等 B 站音乐客户端只做歌词搜索/逐字歌词展示，不做对齐。可用的都是通用的「歌词 ↔ 音频」对齐工具：

| 项目 | 做法 | 中文 | 实测数据（出处自报） | 许可 | 对 Biu 的意义 |
|---|---|---|---|---|---|
| [lyric-align](https://github.com/ijuinryukichi/lyric-align) | faster-whisper 字级时间戳（或**外部 ASR JSON**）→ 按行单调锚定（副歌按顺序消费）→ 一段盖多行时按换气停顿切 → 行内按比例分字；匹配不上的行**标为未匹配**而不是瞎猜 | CJK 优先设计，中文阈值 0.25；作者只报了日语数据 | 日语说唱 3 首：中位误差 0.30~0.36 s；与 stable-ts `align()` 基本持平；WhisperX 47 s 平均误差（VAD 合并整段） | MIT，核心零依赖 | **对齐算法的主要对标物**。`--segments` 可以直接吃 Fun-ASR 结果，验证成本极低；可移植成 TS |
| [stable-ts](https://pypi.org/project/stable-ts/) `align()` | Whisper 交叉注意力 + 已知文本强制对齐 | 依赖 Whisper，中文可用 | 无公开歌曲基准；lyric-align 实测与其持平 | MIT | 备选对照，需 torch，不适合轻量服务端 |
| [PotLyrics align](https://huggingface.co/Mes51/potlyrics-align) | Demucs(ONNX int8) 分离人声 → 中文转拼音 → MMS_FA CTC + Viterbi 强制对齐，纯 CPU | 支持（拼音），无中文数据 | 日语 1 首：字级中位 67 ms，82% 在 200 ms 内；8 线程 CPU 每 4 分钟歌约 100~130 s | MMS 权重 CC-BY-NC 4.0（Biu 本身是 PolyForm Noncommercial，可兼容，但部署方商用受限） | **零费用自建路线的最佳参考**，精度高于 ASR 匹配；CPU 开销大 |
| [Qwen3-ASR](https://github.com/QwenLM/Qwen3-ASR)（2026-01） | 1.7B/0.6B ASR 官方标明支持「歌声、带 BGM 歌曲」；配套 Qwen3-ForcedAligner-0.6B | 原生 | ASR 整曲 WER：EntireSongs-zh 13.91、Opencpop 3.08；Aligner 在**语音**上平均 32~53 ms，**未标歌声** | Apache-2.0 | 自建 ASR 的首选替代（有 GPU 时）；Aligner 用于歌声需自测 |
| SOFA / MFA / AutoLyrixAlign 等 | 音素级强制对齐，面向歌声合成标注或英文 | 需词典/音素模型 | 研究向 | 各异 | 部署复杂，不推荐 |

外部也印证了一点：**整曲直接喂通用语音模型（WhisperX）会翻车，要么用支持歌声的 ASR，要么先分离人声。** Fun-ASR / Qwen3-ASR 属于前者，所以不需要 Demucs。

## 4. 推荐方案

### 4.1 总体链路

```
用户在歌词面板点「自动对齐时间轴」
  │  客户端只发：bvid、cid、当前采用的歌词文本（LRC）
  ▼
Biu 服务端（部署在现有 Web 服务器上）
  1. 查缓存 key = bvid + cid + 歌词内容哈希 → 命中直接返回（任何用户、任何平台）
  2. 自己取 playurl，按已有选流规则避开 PCDN，拉最低码率音频
  3. 交给 ASR（Fun-ASR 异步任务，服务端轮询）→ 字级时间戳；ASR 原始结果也按 bvid+cid 缓存，换歌词不必重跑 ASR
  4. 对齐：先估全局偏移 → 看残差 → 决定「平移」「分段平移」还是「逐行重打」
  5. 生成 LRC + 每行可信度，写缓存
  ▼
客户端展示预览：「已对准 N 行 / 推测 M 行」，用户确认后采用；原歌词保留可还原
```

### 4.2 为什么放在服务端

- 一首歌全网只算一次，费用和等待都被共享摊薄，正好对应「后台一次性修正、永久生效」。
- 服务端已经会按规则拉 B 站音频（Web 版媒体代理、PCDN 规避都在），**不用再让客户端上传音频**，第 3 次尝试里最重的 OSS + STS 链路整条删掉。如果 Fun-ASR 只收公网 URL，服务端直接把音频传到百炼临时存储（官方提供 48 h 的 `oss://` 临时地址，需带 `X-DashScope-OssResourceResolve: enable`；官方称适合开发测试，生产可改用已有的 `biu-lyrics-audio` bucket，由服务端直接上传，不需要 STS）。
- 桌面、Android、iOS、Web 一套实现；桌面走 IPC → 主进程请求服务端，符合「渲染进程不裸发请求」的边界。
- API Key 只在服务端。

### 4.3 对齐策略：先平移，后重打

原歌词的行间节奏是人工打的，比 ASR 准。所以：

1. 用 ASR 字与歌词字的匹配点，估计「歌词时间 → 音频时间」的映射。
2. 若所有匹配点的残差都在阈值内（初值 300 ms，待验证调整）→ **只输出一个全局偏移**（类型 A）。
3. 若残差呈现几段各自恒定 → 分段偏移（类型 B）。
4. 否则逐行用 ASR 时间（类型 C），每行取首个非标点字的时间。
5. 没有任何匹配点支撑的行标为「推测」（类型 D），插值得出时间但在 UI 里区分显示。

已有的 `estimateGlobalOffset` + `dtwAlign` + `interpolateNulls` + `align-report.ts` 覆盖了 1、4、5，2、3 需要补。lyric-align 的「按行单调锚定 + 换气切分 + 未匹配不瞎猜」思路用来补强 4、5。

### 4.4 客户端行为

- 入口：歌词面板一个按钮，只在「已有歌词 + 服务端支持该能力」时出现。不对每首歌自动跑（费用、限流，也避免偷偷改用户采用的歌词）。
- 进度：排队中 / 识别中 / 对齐中，有真实阶段而不是假进度条；Fun-ASR 一般 15~60 s（第 3 次尝试的实测估计）。
- 结果预览：显示「整体平移 +3.2 秒」或「逐行校准 38 行，其中 4 行为推测」，可试听后采用；可还原原歌词。
- 持久化：写入现有歌词缓存（`{bvid}-{cid}`），记录来源为「自动对齐」及偏移/原歌词，Electron 与 Android 走同一个 `platform.getStore`，不写本机路径。
- 错误文案逐类区分：服务端未开通 / 歌曲取流失败 / 识别服务限流 / 识别超时 / 歌词与演唱内容对不上。**失败不自动重试**，限流时提示等待时长。

### 4.5 费用与性能

- Fun-ASR：第 3 次尝试的估算约 0.17 元 / 4 分钟歌（需按现价复核）。Qwen3-ASR-Flash 文件转写按 0.00022 元/秒，约 0.05 元/首，但**是否返回字级时间戳未核实**，验证时一并测。
- 缓存后同一首歌第二个人请求为 0 成本、秒回。
- 对齐计算本身 < 100 ms，服务端无 GPU 需求。

### 4.6 安全边界（对照 AGENTS.md）

- 接口只收 `bvid + cid`，服务端自己解析音频地址，不接受任意 URL，避免变成开放代理。
- 选流不用 playurl 的第一个 `baseUrl`，沿用现有 PCDN 规避。
- 按用户限流，ASR 失败不自动重试、不静默返回空。
- 接口设 `Cache-Control: no-store`，避免 304 空 body。

## 5. 验证门槛（实施前必须先过）

不写 UI，只用脚本跑。目的：用数据回答「准不准」和「用哪个对齐算法」。

**样本（15 首左右，每首人工标注每行真实起唱时间）**：
纯中文慢歌 3、纯中文快歌 2、中英混 2、粤语 1、日语 2、说唱 1、MV 版带长片头 1、Live 版 1、翻唱 1、歌词副歌只写一遍 1。音频全部取自真实 B 站投稿，歌词取自 Biu 当前会匹配到的网易云/LrcLib 结果。

**对比组**：

| 组 | ASR | 对齐 |
|---|---|---|
| A | Fun-ASR | 现有 DTW（含全局偏移） |
| B | Fun-ASR | lyric-align（`--segments` 喂同一份 ASR 结果） |
| C | Qwen3-ASR-Flash（若有字级时间戳） | A/B 中较好者 |
| D（可选，零费用对照） | lyric-align 本地 faster-whisper + Demucs | lyric-align |

**通过标准（建议值）**：

- 行首误差中位数 ≤ 300 ms，且 ≥ 85% 的行在 500 ms 内（对「可信」行统计）。
- 「推测」标记要诚实：被标为可信的行里，误差 > 1 s 的不超过 3%。
- 类型 A 歌曲应被识别为「整体平移」，输出偏移与人工值相差 ≤ 200 ms。
- 单首端到端 ≤ 90 s。

不达标就不做集成，结论回写本文。

### 5.1 止损顺序：先花最少的钱看效果

上次放弃的直接原因是阿里云 OSS / STS 配置繁琐，且对效果没把握。所以验证按「投入从小到大」走，每一步都可以停：

| 步 | 投入 | 做什么 | 停止条件 |
|---|---|---|---|
| 1 | 半天，0 元，**不开任何云服务，不动 Biu 代码** | 开发机上 `uv tool install "lyric-align[asr]"`，挑 5 首（3 首类型 A、1 首 Live、1 首中英混），音频从 B 站下载，歌词用 Biu 当前匹配到的；跑出 LRC 后放进任意 LRC 播放器听 | 5 首里类型 A 都对不准 → 整个方向停，损失半天 |
| 2 | 1 天，几毛钱 | 同 5 首走 Fun-ASR（百炼控制台网页即可上传试用，或临时 URL，**不配 OSS / STS / RAM**），结果用 lyric-align `--segments` 和现有 DTW 各跑一遍 | 云 ASR 不比步骤 1 明显好 → 放弃云，P3 自建路线或停 |
| 3 | 2~3 天，几元 | 扩到第 5 节完整样本，人工标注，出报告 | 不达第 5 节标准 → 停 |

只有步骤 3 通过才进入 P1。前三步都不改 Biu 仓库的业务代码。

### 5.2 步骤 1 结果（2026-10-19，本地 0 元）

**结论：过了止损线，方向继续。** 有片头的投稿能被自动找出整体偏移；而且同一份识别结果上，**仓库里已有的 DTW 比 lyric-align 准得多**，对齐算法不用换。还没有人耳试听，下面的数字都是「和网易云/LrcLib 原轴比」得出的。

**做法**：B 站取最低码率音频 → Demucs 分离人声（CPU）→ faster-whisper medium 出字级时间 → 同一份识别结果分别交给 lyric-align 和现有 DTW（`biu-lyrics-server/src/lib/`）。歌词取自网易云（晴天网易云无版权，取 LrcLib《叶惠美》版）。

**样本与结果**（「与邻行一致」= 该行偏移与前后 3 行的中位偏移相差 ≤ 0.5 s，用来衡量「是不是落在同一段整体平移上」）：

| 投稿 | 类型 | 自动找出的偏移 | 现有 DTW：与邻行一致 | lyric-align：定位行数 / 与邻行一致 |
|---|---|---|---|---|
| 晴天 Hi-Res（BV1BZbSzZEGT） | A，约等于原轴 | −0.1 s | 88%（42/42 行） | 30/42 行，55% |
| 晴天 4K MV（BV1d4411N7zD） | A+B，MV 片头 + 尾段有剪辑 | 前 28 行 +14.4 s（每行误差 ±0.3 s 内），尾段 +16.0 s | 67% | 27/42 行，33% |
| 光年之外 MV（BV1ws411Y7wi） | A，约等于原轴 | +0.1 ~ +0.2 s | 75% | 53/57 行，14% |
| 唯一 MV（BV1nGbP6QEJF） | 原轴本身粗糙（每行都是 .30 s） | +1~2 s，波动大 | 67% | 30/36 行，42% |
| 江南 演唱会（BV1ji4y1v7JT） | B，现场版 | 前 22 行 −11.9 s，后 20 行 −15.7 s | 93% | 24/43 行，47% |

**观察**：

- 类型 A 成立：晴天 MV 的 14.4 s 片头被稳定找出，前 28 行几乎完全平移一致。现场版江南呈现干净的两段平移（间奏长度不同），「分段平移」能直接处理。
- lyric-align 在中文上的弱点：Whisper medium 常把两句唱词合成一段，它的「换气切分」把第二句放早 2~5 s。现有 DTW 用逐字时间，不受这个影响。**第 0 节第 3 点的结论改为：对齐算法沿用现有 DTW，lyric-align 不引入。**
- 出错集中在两处：结尾反复的副歌（晴天 MV 有 6 行被错配到别的重复段）、原歌词本身打轴粗糙（唯一）。前者靠「分段平移 + 少于 3 行的段标为推测」兜住；后者原轴不能当真值，只能人耳判断。
- 繁体歌词（LrcLib 晴天）与转简体后结果几乎一样，繁简不是问题。
- 歌词末尾的制作人员名单（如「混音师 : xxx」）必须在对齐前过滤，否则会被插值到结尾。
- 耗时（M3 笔记本 CPU）：Demucs 约 1.5 min + Whisper medium 约 4.5 min，**约 6 min/首**。作为「后台算一次、全网共享」可以接受，意味着**不接任何云服务也能跑通**；云 ASR（步骤 2）买的是速度（30~60 s）和可能更高的准确度。
- lyric-align 自带的 Demucs 在 Apple 芯片上走 MPS 会崩，需强制 `-d cpu`。

**实验材料**（gitignore 目录，不入库）：`biu-lyrics-server/spike-2026-10/`，含取音频、预处理、DTW 调用、分段平移、评分脚本，以及试听页 `listen/index.html`（三栏对照：原歌词 / 逐行重打 / 分段平移，跟随播放高亮）。

#### 5.2.1 人耳试听第 1 首：晴天 Hi-Res（2026-10-19）

**听感**（只看「分段平移」栏，整首听完）：部分行第一个字一出来就切到该行，完全同步；部分行有轻微延迟——下一句已经开唱，高亮还没切过去。延迟不大，但能察觉。

**拆解**：这首「分段平移」和原轴几乎一样，听到的延迟来自三处叠加，不全是对齐算法的问题：

| 来源 | 量 | 说明 |

| 试听页刷新太慢 | 0 ~ 250 ms，随机 | 试听页靠播放器的「进度更新」事件刷新高亮，Chrome 约每 250 ms 才发一次，所以同一份时间轴有时立刻切、有时晚一拍——正好对应「部分同步、部分延迟」。已改成每帧刷新，需重听。 |
| 分段平移把中段推晚 | 第 6~13 行 +0.23 s | 被切成 3 段：+0.23 / −0.13 / −0.06 s，段间差都 < 0.3 s，本应合并成一段（≈ 原轴）。这 8 行比原轴晚 0.23 s。 |

#### 5.2.2 改用客观真值：网易云逐字歌词（2026-10-19）

**为什么换**：人耳 + 看高亮判断「准不准」本身有几百毫秒的误差，反复听还会疲劳、产生错觉，调参会没有止境。门槛（5 节）本来就要求数字，所以改为用数字评估，人耳只在最后做一次确认。

#### 5.2.3 整体偏移：查清了，是平移算法偏晚约 0.2 s（2026-10-19）

#### 5.2.5 逐字高亮的听感与生产环境的逐字来源（2026-10-19）

**用户试听（光年之外，逐字填充）**：人声比填充快，画面慢 1~2 个字；行内后段填充像在加速，到行尾又对齐。

**数据上不支持「慢 1~2 个字」**：第 4 栏行起点对逐字真值中位 −0.05 s（略早），逐字真值对人声起唱点 −0.03 s。光年之外每个字中位 0.36 s，慢 1~2 个字 ≈ 0.4~0.7 s，比测到的偏差大一个量级。更可能是显示方式造成的：渐进填充下，一个字从开始唱时才开始填、唱完才填满；原来未唱字和已唱字颜色接近，半填的字看不出来，眼睛会把「填满」当作「亮」，于是总慢一个字。行尾那个字通常是拖长音（中位 0.53 s），拖音期间填充追上来，看起来像「行尾强行对齐」。

**已改**：试听页加「逐字方式」，默认「按字点亮」（字开始唱的那一刻整字变色），并调大了未唱字与已唱字的颜色对比；「渐进填充」保留可切换。按字点亮下若仍慢 1~2 个字，再回头查时间轴。

**生产环境不能「有的歌有逐字、有的没有」**：用户手动选的歌词也要自动校对，且用户无从判断哪份歌词带逐字。方案：对齐服务统一输出「行时间 + 每字时间」，逐字来源按质量分三级自动选，界面表现完全一样：

| 级别 | 条件 | 每字时间来源 | 精度 |
|---|---|---|---|
| 1 | 歌词来自网易云且该曲有逐字歌词（自动匹配和手动选网易云都知道歌曲 id，多取一个字段即可判断） | 网易云逐字时间，跟随本行校准后的起点平移 | 人工逐字，最高 |
| 2 | 无逐字歌词（LrcLib、网易云无逐字），但这一行被识别到 | 识别结果里对上的字用识别时间，没对上的字在相邻已知字之间插值 | 待测：可在有逐字真值的歌上直接量 |
| 3 | 这一行没识别到（标「推测」） | 行内按字均匀分配 | 示意，等同桌面歌词现状 |

第 2 级的精度还没测，下一步在光年之外上用逐字真值量（识别出的字时间 vs 人工逐字时间）。

**桌面歌词**：此前时间轴不准，桌面歌词的逐字也只是行内均匀填充。时间轴达标后，桌面歌词改为吃上表的每字时间，作为后续单独优化项。

**可察觉门槛**：广播电视音画同步的常用标准 ITU-R BT.1359：画面早于声音约 125 ms 开始可察觉、约 185 ms 内可接受。用户把 −180 ms 判为同步、把 −200 ms 左右判为「快一点点、可忽略」，和这个范围一致；而且歌词略早于人声本来就利于跟唱（网易云逐行整体早 110 ms）。**第 4 栏的整体精度已在可接受范围，不需要再加提前量。**

**试过逐行吸附到起唱点**（`snap_eval.py`，不写进试听页）：只有附近有清晰起唱点才挪，±0.5 s 内、差 > 0.1 s 时挪了 6 行，≤ 200 ms 从 79% → 82%，> 500 ms 的 3 行一行没修好（结尾是连唱，附近没有起唱点）。收益太小、只有 1 首样本，暂不采用。

**剩余问题**：原歌词个别行本身错 0.5 s 以上（光年之外结尾 4 行）。平移、起唱点都修不了，只能靠更准的逐行识别；列入扩样本时观察出现频率再决定是否投入。

**结尾 4 行的诊断补充**：Whisper 把 206~229 s 整段识别成一句「我没想到」（长拖音 + 和声，没有停顿，起唱点也测不到）。只截这 30 s 重新识别（带 / 不带歌词提示词）文本能出来，但字时间仍偏 0.8~1.2 s，无效。下一个候选是在该窗口内对**已知歌词做强制对齐**（不让模型猜唱了什么，只定时间），先看扩样本里出现频率。

#### 5.2.8 逐字精度：三级来源实测（2026-10-19）

**口径**：同样的 7 首、同一录音的样本。每个字「开始亮」的时间对比网易云人工逐字时间（加上投稿偏移 X），统计每字误差。三级都以「合并段 + 校准」的行起点为锚，区别只在行内每个字的节奏从哪来：

- 第 1 级：照搬网易云逐字时间。误差只来自行起点。
- 第 2 级：用现有 DTW 的逐字结果（`dtw-chars.ts` 导出：每个歌词字对到的识别字时间，没对上的字插值）。只评已识别的行。
- 第 3 级：行内均匀分配，从行起点到下一行起点，每字最多 0.45 s。这就是试听页和桌面歌词现在的做法。

**结果（汇总）**：

| 来源 | 字数 | 中位偏差 | 中位误差 | ≤ 150 ms | ≤ 300 ms | > 500 ms |
|---|---|---|---|---|---|---|
| 第 1 级 网易云逐字 | 2738 | −25 ms | 79 ms | 76% | 98% | 1% |
| 第 2 级 原样（每行以首字为锚） | 2205 | +120 ms | 165 ms | 47% | 74% | 12% |
| 第 2 级 B：整首只用一个偏移锚定 | 2205 | +120 ms | 140 ms | 53% | 88% | 4% |
| **第 2 级 B + 减固定偏差（留一估计）** | 2205 | 0 ms | **90 ms** | **72%** | **92%** | 4% |
| 第 3 级 均匀分配 | 2738 | +205 ms | 306 ms | 29% | 49% | 32% |

**结论**：

- **第 2 级可用**：整首锚定并减去固定偏差后，中位误差 90 ms、92% 的字在 300 ms 内，接近网易云逐字（79 ms / 98%），远好于均匀分配（306 ms / 49%）。
- **均匀分配不能当逐字用**：三分之一的字偏差超过 0.5 s。桌面歌词现在的「逐字」就是这种，时间轴达标后要换成第 1 / 2 级。
- **为什么不逐行以首字为锚**：Whisper 给每段第一个字的时间常常偏早，以它为锚，同一行后面的字就整体偏晚。改为整首只用一个偏移（取各已识别行「行起点 − 识别首字时间」的中位数）。
- **固定偏差约 +120 ms**：识别出的字起点普遍比人工逐字晚。每首都用「其余 6 首」的中位数来估（不拿自己拟合自己），各首估出的值是 100~130 ms，很稳定，说明这是识别本身的特性，不是拟合出来的。生产上可以先用常数 120 ms，样本增加后再复核。
- 只看「同字匹配」到的字并不更好（160 ms vs 165 ms）：误差主要来自识别时间本身，而不是插值。
- 同字匹配率是 60~98%。Whisper 常输出繁体字（「個」「覺」），现有 DTW 只认完全相同的字，繁体字对不上就只能靠插值。在 DTW 前把识别结果转成简体，有望提高匹配率（未测）。

**实现注意**：第 2 级的每字时间来自整首锚定，行内第一个字可能比该行的高亮时刻略早或略晚。生产上要把每字时间限制在本行的「行起点 ~ 下一行起点」之内，保证字的点亮不会跑出本行。

**脚本**：`dtw-chars.ts`（导出逐字结果）、`word_eval.py`（三级评测、留一偏差）。

#### 5.2.9 对标开源强制对齐：MMS_FA 明显胜出（2026-10-19）

**起因**：用户指出不应该在没跑过前人做法的情况下自研。第 3 节调研里的 PotLyrics（Demucs + 拼音 + MMS_FA 强制对齐）和 Qwen3-ForcedAligner 此前都没在同一套样本上跑过。这一轮用同样 7 首、同一套评测补上。

**做法**：
- **MMS_FA**（`mms_align.py`）：torchaudio 自带的 MMS_FA（wav2vec2 CTC），中文转拼音（pypinyin），行与行之间插通配符 `*` 吸收歌词里没有的和声和即兴。发射概率按 15 s 一块计算再拼接，整首直接过模型内存会爆。纯 CPU，**每首 17~25 s**（不含 Demucs）。
- **Qwen3-ForcedAligner-0.6B**（`qwen_align.py`）：整首人声加歌词一次对齐，CPU float32，**每首 1~5 min**。安装时 pip 会卡死，因为它依赖的日语分词库 nagisa 需要编译，torch 也是大包。最后的办法：建一个复用现有 torch / transformers 的 venv，只装缺的小包，nagisa 用占位代替（只做中文）。

**意外发现：评测基准本身在 2 首歌上偏了约 0.19 s**。

在 5 首歌上，所有方法都和逐字真值一致。但在光年之外和年少有为上，MMS_FA（+194 / +222 ms）和 Qwen3（+120 / +180 ms）这两个互相独立的强制对齐，都把整首歌放得比真值晚约 0.19 s，而它们在另外 5 首上都接近 0（MMS +20~40 ms，Qwen −20~−70 ms）。

原因：真值是「网易云逐字 + 投稿偏移 X」，X 是用人声起唱点估的；而「合并段 + 校准」也是对齐到起唱点。两者共用同一个信号，起唱点在某些歌上系统性偏早时，评测和算法会一起偏，看起来就互相吻合。这和用户在光年之外第 4 栏听到的「画面比声音快 100 多毫秒」一致。

**下面以修正后的 X 为准**（这两首 X + 0.19 s，取两个独立对齐器的共同结论），同时给出修正前的数字，结论都一样。

**行起点（7 首，327 行）**：

| 方法 | 中位误差 | ≤ 150 ms | ≤ 300 ms | > 500 ms | > 1 s |
|---|---|---|---|---|---|
| 网易云逐行歌词 | 194 ms | 39% | 77% | 6 | 0 |
| 合并段 + 起唱点校准（自研） | 115 ms（修正前 72） | 59%（修正前 79%） | 92%（修正前 98%） | 4 | 1 |
| **MMS_FA 强制对齐** | **37 ms**（修正前 73） | **91%**（修正前 62%） | **98%**（修正前 92%） | 3 | 2 |
| Qwen3-ForcedAligner | 50 ms | 73% | 77% | 62 | 47 |

**逐字（7 首，2738 字）**：

| 方法 | 中位误差 | ≤ 150 ms | ≤ 300 ms | > 500 ms |
|---|---|---|---|---|
| 网易云逐字，跟随自研行起点 | 115 ms | 59% | 92% | 1% |
| 识别字时间（第 2 级 B + C） | 122 ms | 58% | 89% | 4% |
| 均匀分配 | 290 ms | 28% | 51% | 29% |
| **MMS_FA 强制对齐** | **24 ms** | **95%** | **98%** | 1% |
| Qwen3-ForcedAligner | 70 ms | 73% | 78% | 18% |

**结论**：
- **MMS_FA 全面胜出**：行级和字级都远好于自研的「识别 + DTW + 合并段 + 起唱点校准」，也好于网易云自己的逐行歌词。逐字误差 24 ms，比「网易云人工逐字跟随我们的行起点」还准。即使不做 0.19 s 修正，它的字级也是最好的（40 ms / 96%），行级和自研持平（73 ms vs 72 ms）。
- **方向调整**：核心算法从「Whisper 识别 + DTW」改为 **Demucs + MMS_FA 强制对齐**。不再需要 Whisper；每首耗时从约 6 min 降到约 2 min（Demucs 1.5 min + 对齐 20 s）。逐字时间直接由对齐得到，第 5.2.5 节的三级来源可以简化。
- **Qwen3 不采用**：在 CPU 上慢（1~5 min），而且鲁棒性差，18% 的字偏差超过 0.5 s，47 行偏差超过 1 s，很可能和整首一次性输入有关。在 5 首上它的精度不错（60~70 ms），等有 GPU 或分段输入时可以再评。
- **MMS_FA 的失败行**：327 行里有 2 行偏差超过 1 s。孤勇者「你的沉默 震耳欲聋」偏 −5.2 s，光年之外结尾「危难中相爱」偏 −1.1 s（就是之前 Whisper 也识别不出的那段）。生产上需要一个兜底：MMS 的行起点和平移估计相差超过约 1 s 时，标为推测或回退。
- **评测方法的教训**：求真值偏移和做校准不能用同一个信号；以后要用一个与算法无关的方法交叉验证（这次用的是两个独立对齐器）。

**还没验证的**：MMS_FA 是对整首已知歌词做强制对齐，前提是歌词都按顺序唱了。现场版（江南）、MV 有剪辑（晴天 4K MV）、有些行没唱或者多唱的情况，还没测。这类歌没有逐字真值，只能和之前的分段平移、人耳对比。
**授权**：MMS 权重是 CC-BY-NC 4.0，Biu 本身是非商业许可，可以兼容；但部署方如果商用会受限（见第 3 节）。
**多语言**：MMS_FA 靠罗马字化支持多语言，中文已经接上拼音；日语、韩语需要另外接转写。

**脚本**：`mms_align.py`、`qwen_align.py`，以及 `word_eval.py`（环境变量 `FA=mms|qwen` 选对齐结果，`XFIX` 修正投稿偏移）。

#### 5.2.10 MMS_FA 的失败行兜底，以及现场版 / 剪辑版（2026-10-19）

**兜底规则**（`fallback_eval.py`）：MMS_FA 的行起点和「合并段 + 校准」相差超过 T 秒，就认为强制对齐在这一行跑偏了，回退到平移估计并标为推测。两边的来源是独立的（一个强制对齐，一个识别 + 平移），同时错到同一处的概率低。在 7 首有真值的歌上（投稿偏移已修正）：

| | 中位误差 | ≤ 300 ms | > 500 ms | > 1 s | 回退行数 |
|---|---|---|---|---|---|
| MMS_FA 原样 | 37 ms | 98% | 3 | 2 | — |
| 兜底 T = 0.5 s | 38 ms | 98% | 5 | 1 | 7 |
| **兜底 T = 1.0 s** | 37 ms | 98% | 2 | **0** | 2 |
| 兜底 T = 1.5 s | 37 ms | 98% | 2 | 0 | 2 |

取 **T = 1 s**。被回退的 2 行（孤勇者「你的沉默 震耳欲聋」MMS 偏 −5.2 s，光年之外「危难中相爱」偏 −1.3 s），平移估计在这两行上都更准。

**现场版 / 剪辑版 / 原轴粗糙**（无逐字真值，只能看 MMS 和平移估计是否一致，最终要靠人耳）：

| 投稿 | MMS − 平移估计 | 两者相差 ≤ 0.3 s 的行 | 相差 > 1 s 的行 | 解读 |
|---|---|---|---|---|
| 江南 现场版 | +0.06 s | 95% | 1 | 现场版也能处理，两种方法一致 |
| 晴天 Hi-Res | +0.06 s | 93% | 3 | 一致；首行被 MMS 放早 26.6 s（前奏里有声音），由兜底挡住 |
| 光年之外 MV | +0.28 s | 51% | 1 | 整体差 0.28 s，正是 5.2.9 发现的平移估计偏早 |
| 晴天 4K MV | +0.22 s | 57% | 17 | 从第 28 行起相差 +10 ~ +19 s：MV 有剪辑，强制对齐默认「每行按顺序唱一次」，被剪掉的段落会把后面的行挤歪 |
| 唯一 MV | +0.70 s | 19% | 14 | 原轴粗糙，平移估计本身不可靠，这首说不清谁对 |

**注意兜底的前提**：在 7 首真值歌上，两者分歧时平移估计总是对的；但在**剪辑版、原轴粗糙**的歌上未必，此时回退可能反而更糟。所以兜底行要标为推测，交给人耳确认（晴天 4K MV、唯一）。如果人耳判断 MMS 在剪辑后的段落里是对的，兜底就要改成「只在孤立的单行分歧时回退，连续成段的分歧另做处理」。

**试听页**（`listen_mms.py` 生成）：精简为 4 栏——原歌词 / 合并段 + 起唱点校准 / **MMS_FA 原样** / **MMS_FA + 兜底**。MMS 两栏用强制对齐得到的真实逐字时间点亮；回退行标「推测」，改为均匀填充。

#### 5.2.11 人耳裁决：去掉「推测」兜底，改为静音门控（2026-10-19）

**结论**：MMS_FA 原样比「回退到平移估计」更准；唯一的系统性问题是首行被放进前奏。用「人声静音处不许放歌词」修掉后，不再需要推测兜底。

**用户试听**（第 3 栏 MMS 原样 vs 第 4 栏 MMS + 兜底）：

- 唯一：第 3 栏更好。凡是标了「推测」的行都不准，没标的行两栏一样准，也就是说兜底回退的那些行全是回退错了。
- 晴天 4K MV 第 28 行以后：第 3 栏更准，只有开头不准。但这首中途有一段像海浪一样的沙哑人声，属于特殊编排，**不作为判断依据，也不为它专门处理**。目标是常规歌曲，以晴天 Hi-Res 这类投稿为准。

**首行为什么被放早**：晴天 Hi-Res 的人声轨前 29 s 能量是 0（Demucs 分离后前奏完全静音），MMS 却把首行「故事的小黃花」放在 2.8 ~ 4.6 s；4K MV 同理被放在 17.4 s，那里人声轨也是 0。强制对齐只要求「所有字按顺序出现一次」，静音帧上字母的代价并不比真唱段高多少，而行间的 `*` 通配符又能把真正唱首行的那几秒吞掉，于是整行落在静音里。

**修法：静音门控**（`mms_align.py`，默认开启，输出 `.mmsg.chars.json`）：人声轨能量低于整首 90 分位能量 2% 的帧，只允许 blank 和 `*`，前后各留 0.3 s 免得切掉辅音起头。

| | 晴天 Hi-Res 首行 | 晴天 4K MV 首行 | 其余行 |
|---|---|---|---|
| 原歌词（参照） | 29.4 s | 29.4 + 片头约 14 s | — |
| MMS 原样 | 2.8 s（早 26.6 s） | 17.4 s（早约 26 s） | — |
| **MMS + 静音门控** | **29.3 s** | **43.7 s** | 5 首试听歌里，除这 2 个首行外，行起点变化全部 < 0.3 s |

7 首真值歌（327 行）上门控前后指标完全相同：行起点中位误差 37 ms、98% ≤ 300 ms，逐字 24 ms、95% ≤ 150 ms。也就是说门控只修首行跑进前奏这一种错，别的地方不受影响。

**去掉推测兜底的代价**：7 首真值歌上仍有 2 行偏差超过 1 s（占 0.6%）：

- 孤勇者「你的沉默 震耳欲聋」偏 −5.2 s：整行 13 个字被挤进 1.3 s，每字约 0.1 s，然后后半句英文才落到正确位置。这首在这里有大段说唱式英文和声，属于非常规编排。
- 光年之外「危难中相爱」偏 −1.3 s：副歌重复段，同一句连续出现两次。

为了这 2 行去保留兜底，会在剪辑版和原轴粗糙的歌上把成片正确的行改错（唯一回退了 14 行，全是改错）。按用户「以常规歌曲为主」的取舍，不保留。

**顺带发现的清洗漏洞**：江南歌词里的「录音室 : The Garden」「混音师 : Joe Vanelli」（冒号前有空格），以及后来结尾的「ISRC TW-A45-99-…」都没被清洗掉，被当成歌词对齐到了尾奏。生产环境的清洗规则要加上这两类。

**试听页**：第 4 栏改为「MMS_FA + 静音门控（拟采用）」，不再出现「推测」。

#### 5.2.12 用户给的 3 首常规投稿，以及「挤压回退」（2026-10-19）

**结论**：3 首里有 2 首直接可用；跳楼机副歌有 4 行被强制对齐挤成「唱不出来的速度」，用这个特征就能把它们挑出来，改回原歌词时间。

用户给的投稿：为你写诗（吴克群，歌词来自 LrcLib，网易云没有原唱）、跳楼机（LBI利比）、没能成为你的白马（杨天一，B 站版比网易云长 21 s）。三首都没有网易云逐字歌词，没有真值，只能和原歌词的时间比较，最终靠人耳。整条流程用 `align_lrc.py` 一条命令跑完，每首约 2 min。

| 投稿 | 整体偏移（对齐 − 原歌词） | 平移后与原轴差 ≤ 0.3 s 的行 | 差 > 1 s 的行 |

| 没能成为你的白马 | +0.01 s | 88% | 0 |

**跳楼机的失败**：副歌「baby 我们的感情好像跳楼机」的「跳楼机」三个字被拉长到 87 ~ 90 s，后面三行「让我突然地升空…」「你带给我一场疯狂」「劫后余生好难呼吸」被挤进 90.3 ~ 93.8 s，每字约 0.08 s。原歌词这三行在 85.6、89.3、91.1 s，间隔正常，是原歌词对、对齐错。

**挤压回退**：中文字的中位字距 < 0.15 s 视为对齐失败（正常演唱很难持续每字快于 0.15 s），这一行改用「原歌词时间 + 整首中位偏移」，标「推测」，行内均匀填充。阈值在 14 首歌上扫过：

| 阈值 | 命中 |
|---|---|
| 0.10 s | 孤勇者 1 行、跳楼机 1 行、江南制作人员行 1 行 |

| **0.15 s** | 孤勇者 1 行、跳楼机 4 行、白马 1 行（「对我是惩罚」，待人耳确认）、江南制作人员行 3 行（清洗漏掉的，本来就该删） |

**试听页**：`listen/new.html`（`listen_new.py` 生成），3 栏：原歌词 / MMS_FA + 静音门控 / 再加挤压回退（拟采用）。

#### 5.2.13 人耳否掉挤压回退，改为局部重对齐（2026-10-19）

**结论**：对齐失败的行不再回退到「原歌词时间 + 均匀填充」，而是只拿原歌词时间划一个窗口，在窗口里重新做一次强制对齐，逐字时间仍然来自音频。跳楼机副歌的连续错位修好了，7 首真值歌上偏差 > 1 s 的行从 2 行降到 1 行，其余指标不变。

**用户试听**（5.2.12 的 3 栏页）：

- 跳楼机 1:22 ~ 1:35：第 2、3 栏一开始都卡住；第 3 栏先恢复，但两栏都没跟上，第 3 栏最近，约差 1 个字。带「推测」的行基本都不准。卡住的根源在「baby 我们的感情好像跳楼机」这一行：它没被判为挤压，没被修，行尾「好像跳楼机」仍被拉到 87 ~ 90 s，所以高亮停在「感情」。
- 白马：第 2 栏更准，「对我是惩罚」是误判，回退后反而变差。
- 白马「下次就请换我来」（4:16）：高亮晚一点，唱出「下」时画面还在「如果可以」。差 0.4 s 左右，用户认为可以接受，个别行可以人工调整。
- **用户定的验收线**：个别行有些许误差可以接受，但不能「一段错，后面就连续错」。

**局部重对齐**（`mms_align.py`，默认开启，输出 `.mmsr.chars.json`）：

1. 找出挤压行（中文字中位字距 < 0.15 s），连同它的前一行一起处理。前一行的行尾往往就是被拉长的那部分，跳楼机就是这样。
2. 每行只在「原歌词时间 + 整首中位偏移」前后各放宽 0.6 s 的窗口里，单独再做一次强制对齐。
3. 两道闸，防止原歌词时间和这份录音本身对不上时把对的行挪走：
   - 被连带的前一行，行起点挪动 > 1 s 就不收。江南现场版的「心碎了才懂」没加这道闸时被挪了 17 s，因为现场版的节奏和录音室版原轴不同。
   - 挤压行重对齐后必须比原来松，否则不收。
4. 原歌词没有时间（纯文本）时跳过这一步。

| 行 | 整首对齐（行起点 / 行尾） | 局部重对齐后 | 原歌词时间 + 偏移 |
|---|---|---|---|
| baby 我们的感情好像跳楼机 | 82.1 s / 「跳楼机」在 87 ~ 90 s | 82.1 s / 「跳楼机」在 84.4 ~ 85.1 s | 82.1 s |

**7 首真值歌**：行起点中位误差 37 ms、98% ≤ 300 ms 不变；偏差 > 1 s 的行从 2 降到 1。孤勇者「你的沉默 震耳欲聋」行起点修好了，剩下的是光年之外「危难中相爱」（副歌同一句连续唱两遍）。逐字 24 ms / 95% ≤ 150 ms 不变。

**残留**：「急速落地」4 个字仍被挤在行尾 89.6 ~ 90.1 s，和下一行有约 0.4 s 重叠。行起点都对了，属于「个别字误差」，在用户的验收线以内。

**试听页**：`listen/new.html` 第 3 栏改为「再加局部重对齐（拟采用）」，不再有「推测」。

#### 5.2.14 真正的根因：分块边缘，改为双切法平均（2026-10-19）

**结论**：跳楼机卡住，不是「baby」英文的问题，而是把音频切成 15 s 一块送进模型时，块边缘附近的识别会变差。「又急速落地」正好压在 90 s 的块边界上。改成两种起点各切一遍再取平均后，跳楼机整首一行都不用修；7 首真值指标基本不变。

**用户试听**（5.2.13 的局部重对齐）：「让我突然地升空又急速落地」高亮停在「升空」，然后一下闪过去，接着略慢一点，再慢慢追上。比之前好，但仍不合格。

**排查**：

- 卡住的这一行是纯中文。数据上「让我突然地升空」在 85.8 ~ 87.4 s，「又急速落地」被放到 89.6 ~ 90.1 s，和下一行挤在一起。局部重对齐的窗口里也是同一个结果，说明问题出在模型的发射概率本身，不是窗口划错了。
- 单独拿 80 ~ 96 s 这一段算发射概率，再对齐，结果正常：又 87.5、急 88.2、落 88.5、地 88.9 s。
- 整首按 15 s 一块切时，90 s 是块边界。wav2vec2 是双向自注意力，块边缘的帧只能看到一侧的上下文。这句唱得含糊（每字置信度只有 0.02 ~ 0.25），一边上下文就会丢。
- 只换一种切法不够：前后各补 3 s 上下文的重叠切法，在这句上反而更差（整句被推到 89.4 ~ 90.1 s）。单一切法总会有某一句压在边缘上。

**修法：双切法平均**（`mms_align.py`，默认开启，`CHUNK2=0` 关闭）：按起点 0 s 和 7.5 s 各切一遍，两份概率取平均（对数域上 logsumexp 后减 log 2）。任何时刻至少有一份离块边缘 ≥ 3.75 s。

| 跳楼机 | 起点 0 s 单切 | 起点 7.5 s 单切 | **双切平均** | 原歌词时间 + 偏移 |
|---|---|---|---|---|
| baby 我们的感情好像跳楼机 | 「跳楼机」在 87 ~ 90 s | 82.1 s 起 | **82.1 s 起，「跳楼机」在 84.6 ~ 85.1 s** | 82.1 s |
| 让我突然地升空又急速落地 | 「又急速落地」在 89.6 ~ 90.1 s | 85.9 s | **85.9 s，「又急速落地」在 87.8 ~ 88.9 s** | 85.9 s |
| 你带给我一场疯狂 | 91.5 s | 89.6 s | **89.6 s** | 89.6 s |
| 劫后余生好难呼吸 | 92.6 s | 91.4 s | **91.4 s** | 91.5 s |

**全量结果**（15 首重跑，每首约 40 s，原来约 25 s；另加 Demucs 约 1.5 min）：

| 7 首真值歌 | 单切 + 局部重对齐 | **双切平均 + 局部重对齐** |
|---|---|---|
| 行起点中位误差 | 37 ms | 40 ms |
| 行 ≤ 150 ms | 91% | 93% |
| 行 ≤ 300 ms | 98% | 98% |
| 行 > 1 s | 1 | 1 |
| 逐字中位误差 / ≤ 150 ms | 24 ms / 95% | 26 ms / 95% |

- 跳楼机：需要局部重对齐的行从 6 行变成 0 行。
- 孤勇者「你的沉默 震耳欲聋」：靠局部重对齐修好，不变。
- 剩下 > 1 s 的 1 行仍是光年之外「危难中相爱」（副歌同一句连续唱两遍），由早 1.3 s 变成晚 1.6 s。
- 局部重对齐保留，作为第二道保险：14 首里只有孤勇者、白马、江南各有 1 ~ 2 行触发，被采纳的行时间基本不变。

**试听页**：`listen/new.html` 第 2 栏是旧的单一切法，第 3 栏是「双切平均 + 局部重对齐（拟采用）」。

#### 5.2.15 「歌词和音频对不上」的判据，以及 P1 服务端（2026-10-19）

**结论**：用「行置信度中位数 < 0.25」且「局部重对齐采纳 ≥ 3 行」两个条件同时满足来判定歌词配错。在 15 首对得上和 4 组故意配错的歌上，两边各 100% 判对。P1 服务端 `biu-align-server` 已经端到端跑通：真实拉 B 站音频 → 对齐 → 提交审核 → 通过后匿名可读。

**为什么要判**：强制对齐不会说「不知道」。歌词配错时它仍会把每个字硬塞到某个位置，用户和审核员看到的就是满屏乱跳。用户上传歌词以后，这种情况一定会出现。

**标定数据**（worker 输出的每行平均 token 置信度；人声复用已分离好的，只跑对齐）：

| | 行置信度中位数 | 25 分位 | 局部重对齐采纳行数 | 整首偏移 |
|---|---|---|---|---|
| 对得上的 15 首（含江南现场版、晴天 4K MV、唯一 MV、带英文的孤勇者） | **0.277 ~ 0.670** | 0.19 ~ 0.52 | 0 ~ 2 | 与投稿实际一致 |
| 配错的 4 组（跳楼机音频 + 白马歌词，为你写诗 + 晴天，后来 + 孤勇者，江南 + 十年） | **0.161 ~ 0.215** | 0.10 ~ 0.18 | 4 ~ 12 | +7.5 ~ −65 s |

- 单看中位数，两边只差 0.06（0.215 和 0.277），离得太近。
- 单看采纳行数也不够稳：对得上的歌最多采纳 2 行。
- 两个条件同时满足才判错，一首对得上的歌要被误判，得两项同时变差。
- 纯文本歌词没有原时间，不做局部重对齐，只能单看中位数，阈值放到 0.2。

**P1 服务端**（`biu-align-server/`，接口见它的 README）：

- 独立服务，不并进同步服务。对齐吃满 CPU，崩溃或重启不能连累同步。登录复用同步服务签发的 token（共用 `JWT_SECRET`），客户端不用再接一套登录。
- 服务端自己拉 B 站音频：只接受 bvid + cid，并校验 cid 属于这个 bvid；B 站请求串行、间隔 ≥ 3 s；只用非 PCDN 地址；风控（-352 / 412）单独报错，不重试。
- 单并发队列：同一份歌词重复提交复用同一个任务；每人同时只能有 1 个任务；排队上限 20；每人每天 20 首，命中缓存不算次数，服务端原因失败退还次数。
- 缓存：投稿 + 分 P + 歌词哈希 + 算法版本 → 对齐结果，内存 LRU 加磁盘两级。
- 审核：用户必须先对齐、预览过，才能提交。审核员（`ADMIN_MIDS`，部署配置里填 B 站 UID）可以通过，或填写原因打回。同一人重复提交，旧的待审记录自动撤回；新版本通过后，旧版本标为「已被替换」。
- 错误码共 26 个，每个都有对应文案（被 B 站限流、歌词对不上、排队满、次数用完……），不用统一的「网络请求失败」兜底。
- 所有接口 `no-store`、不带 ETag：轮询任务状态时不会拿到 304 空 body。

**端到端实测**（本机起服务，真实 B 站请求 + 真实模型）：

| 场景 | 结果 |
|---|---|
| 跳楼机 + 网易云原始 LRC（含 JSON 制作人员行） | 106 s 完成：下载 3 s，对齐 100 s；55 行；副歌「又急速落地」在 87.8 ~ 88.9 s，和人耳确认的版本一致 |
| 提交审核 → 审核员通过 → 匿名读取 | 通过，匿名读到 55 行 |
| 另一个用户提交同一份歌词 | 命中缓存，立即返回，不排队 |
| 跳楼机音频 + 白马歌词 | 102 s 后返回 `LYRICS_MISMATCH`「歌词和这首歌的音频对不上……」 |

单测 26 个：歌词清洗、哈希、bvid / cid 校验、逐段切分、PCDN 判定与客户端一致、队列（去重 / 单并发 / 排队上限 / 配额退还）、配错判据、HTTP 全流程。测试还抓到一个真 bug：`/lyrics/:bvid/:cid` 注册在 `/lyrics/submissions/mine` 前面，后者会被当成 bvid / cid 吃掉。

### 5.3 改动范围预估（通过验证后）

对现有代码的侵入很小，大头是新增：

- 服务端：新增一组对齐接口和缓存（复用已有取流逻辑），约等于再加一个代理路由。
- 客户端：歌词面板加一个按钮 + 预览弹窗；歌词缓存多记「来源 / 原歌词」两个字段；新增一个 IPC 通道（按 AGENTS.md 一次改齐 channel / preload / 类型 / Android）。
- 播放、歌词渲染、现有偏移控件：**不改**。对齐结果仍是普通 LRC，走原来的显示链路。
- 最小可交付版本可以只做「整体平移」：服务端只回一个偏移值，客户端写进已有的偏移字段，连歌词文本都不用换。

## 7. 风险与待决

- 第 3 次尝试的放弃原因（2026-10-19 用户确认）：阿里云 OSS / STS 配置太繁琐，加上对效果没把握、担心投入大而失败、担心改动大。对应处理：取消客户端上传（不再需要 OSS / STS / RAM），验证按第 5.1 节从 0 元开始逐步加码，改动范围见第 5.3 节。
- **待你确认**：ASR 费用由部署方承担是否可接受（含是否需要每日额度上限）。
- **待你确认**：没部署服务端的桌面用户（开源自用）是否需要此功能。按本方案，他们看不到入口。
- Fun-ASR 对日语/韩语歌、说唱的效果未测；Qwen3-ForcedAligner 官方只标语音，用于歌声未验证。
- 百炼临时存储官方定位是开发测试，生产要换自有 bucket。
- 安全：`biu-windows-test/README.md` 记录 DashScope Key 曾在聊天里明文出现过，重新启用前先轮换 Key。
