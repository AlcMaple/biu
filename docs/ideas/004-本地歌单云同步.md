# 004 - 本地歌单云同步

> 开始：2026-08-01

## 🎯 这个阶段的产物

把本地歌单的三个持久化文件（`local-favorites.json` / `local-fav-items.json`
/ `tags.json`，见 [`local-fav-items.ts`](../../src/store/local-fav-items.ts)、
[`favorite.ts`](../../src/store/favorite.ts)、[`tags.ts`](../../src/store/tags.ts)）
从"靠百度网盘做整文件同步"换成"客户端主动调用阿里云 ECS 上的轻量同步服务"，
按 B 站登录 `mid` 分用户存储，解决网盘低性能模式不实时、容易整文件互相覆盖
的问题。不做网页版，只是给 Electron 客户端加一层同步 IPC/HTTP 调用。

**约束条件**（决定了下面所有技术选型）：
- ECS 配置：2 核 / 1.8G 内存，且已有其他服务常驻，`free -h` 显示常态下只有
  100~200Mi 空闲、swap 已用掉一半以上 —— **内存是唯一紧约束**，磁盘还有
  28G 空闲，不是问题。
- 不引入新增付费服务（放弃 OSS 方案，虽然费用本身可忽略不计，但用户不想
  维护多一个云服务的账单和权限）。
- 用户量小，但**同一用户可能 Mac + Windows 同时在线**，必须处理真实的多
  设备并发写入，不能假设"同一时刻只有一台设备在改"。
- 不能因为这个新服务把已有服务挤到 OOM。

## 📖 详细说明

### 运维前置问题：SSH 连不上

这次调研发现从本机 `ssh root@8.163.0.99` 在 TCP 三次握手后、密钥交换阶段就
被服务器主动断开（`kex_exchange_identification: Connection closed by remote
host`），用户反馈"以前能连，现在不行"。这不是密钥/密码问题（密钥交换阶段
还没到认证步骤），大概率是以下之一：
- 阿里云控制台**安全组规则**变了（22 端口的入方向规则被收紧、限了源 IP）
- 服务器本机 `sshd_config` 改了 `ListenAddress` / `Port` / `AllowUsers`
- `fail2ban` 或类似工具封了当前出口 IP（多次失败尝试后自动封禁）
- 服务器资源耗尽时 sshd 被某种保护机制限制新连接

**这个必须在部署前解决**——建议用户通过阿里云网页控制台的"远程连接/VNC"
方式登录一次，检查 `sudo iptables -L -n`、`sudo fail2ban-client status
sshd`（如果装了的话）、以及阿里云控制台安全组的 22 端口规则，确认能恢复
标准 SSH 后再继续部署步骤。这个仓库里没有相关代码能修，纯运维排查。

### 整体架构

```
[Electron 客户端 A（Mac）]  ─┐
                             ├─HTTPS─> [Apache 反代 :80/:443] ─> [sync 服务 :3002（内网）] ─ 读写 ─> [本地磁盘 /data/biu-sync/{mid}/*.json]
[Electron 客户端 B（Win）]  ─┘
```

- 复用 [`docs/release/自动更新部署指南.md`](../release/自动更新部署指南.md) 里已经在跑的
  Apache，新服务只监听 `127.0.0.1:3002`，不直接暴露公网端口。
- 服务本身参考 [`biu-lyrics-server/`](../../biu-lyrics-server/README.md) 的
  项目结构（同一个仓库风格，Express + TypeScript + `.env`），新建
  `biu-sync-server/` 目录，独立部署、独立进程，不共用 lyrics-server 的内存。

### 鉴权：复用 B 站登录，不建独立账号体系

1. 客户端已持有登录后的 B 站 cookie（`SESSDATA` 等），调用
   `POST /api/auth/exchange`，body 带上 cookie 值。
2. 服务端拿这个 cookie 调 B 站 `nav` 接口（`api.bilibili.com/x/web-interface/nav`）
   验证有效性并拿到 `mid`——**不信任客户端自己上报的 mid**，永远以这次校验
   拿到的为准。
3. 服务端签发一个短期 JWT（比如 2 小时过期，payload 只含 `mid` + 签发时间），
   返回给客户端。
4. 之后所有同步请求带 `Authorization: Bearer <jwt>`，服务端从 JWT 里解出
   `mid` 用于拼存储路径——**路径规则里不接受请求体/query 传入的 mid**，杜绝
   跨用户读写。
5. JWT 过期后客户端用同样的 cookie 重新换发（Electron 侧本来就一直持有登录
   cookie，静默重试即可，不需要用户感知）。

`mid` 校验时顺带做一次防御性检查：正则 `^\d+$`，拒绝非数字值，防止路径
穿越（`path.join` 前先 `Number.isInteger` 校验）。

### 存储层设计

路径：`/data/biu-sync/{mid}/{store}.json`，三个 store 各一个文件：
`favorites.json` / `fav-items.json` / `tags.json`。

每个文件内容统一包一层信封：

```json
{
  "version": 17,
  "updatedAt": 1735600000000,
  "updatedBy": "device-uuid-abc",
  "data": { /* 与本地 electron-store 里同名字段的内容一致 */ }
}
```

- **原子写**：先写 `xxx.json.tmp`，`fs.rename` 覆盖原文件（同分区 rename 是
  原子操作，避免半截写入被读到）。
- **进程内互斥**：维护 `Map<mid, Promise>` 作为每用户串行队列，同一 mid 的
  请求排队执行，避免同一进程内两个并发请求同时读改写导致的丢失更新。
  **这个机制只在单进程时成立**——见下方部署章节，pm2 必须用 fork 模式单
  实例，不能开 cluster，否则每个子进程各有自己的 Map，互斥形同虚设。
- 不引入 SQLite：数据量（单用户几百 KB 量级）和读写模式（整用户粒度的
  读 + 条目级合并后整体落盘）用不上关系型查询能力，纯增加运维负担。

### 同步协议与冲突合并（重点）

这是本次设计要解决的核心问题——"Mac 和 Windows 同时在线改同一个收藏夹"。

**拉取（GET `/api/sync/:store`）**
返回当前 `{version, updatedAt, data}`。客户端本地记录这个 `version` 作为
"我上次同步到的基线"。

**推送（POST `/api/sync/:store`）**
客户端带上 `baseVersion`（本地基线）+ 本次变更的操作列表，而不是整个文件：

```json
{
  "baseVersion": 17,
  "ops": [
    { "type": "upsert", "id": "rid-123", "payload": { ... } },
    { "type": "remove", "id": "rid-456" }
  ]
}
```

服务端处理逻辑：
1. 读当前文件，若 `currentVersion === baseVersion`：没有其他设备插入过修改，
   直接把 `ops`应用到 `data`（按 `id` upsert / remove），`version + 1`，
   原子写回，返回新版本。
2. 若 `currentVersion > baseVersion`：说明基线之后已经有别的设备推进过。
   **不直接拒绝，也不整文件覆盖**——按条目 id 做三路合并：
   - 服务端当前数据 + 客户端本次 `ops` 都是"从 baseVersion 出发的增量"，
     两边操作的 `id` 集合大概率不相交（用户在两台设备上改的是不同的
     收藏/标签条目），直接合并即可。
   - 如果同一个 `id` 被两边都改了（真冲突，概率低但要处理）：按
     `updatedAt` 更晚的一方为准（last-write-wins），因为这是用户自己的
     单人数据，冲突时"最后一次编辑生效"符合直觉，不需要做复杂的 UI 冲突
     选择框。
   - 删除操作用**墓碑机制**兜底"先删后加"的顺序竞态：`remove` 不是物理
     删除条目，而是打一个 `{deletedAt}` 标记，`upsert` 如果撞到一个
     `deletedAt` 更晚的墓碑则丢弃自己（说明这条数据已经被另一台设备判定
     该删）；墓碑本身可以在合并时超过一定天数（比如 30 天）后清理，避免
     文件无限增长。
   - 合并完成后 `version + 1`，返回**新的完整快照**给客户端（而不是只返回
     ack），客户端用这个快照覆盖本地 store 并更新基线——这一步保证两台
     设备最终收敛到同一状态，不会因为"我以为推送成功了但其实被合并过"
     而出现本地状态和服务端不一致。

**客户端接入点**：在 `local-fav-items.ts` / `favorite.ts` / `tags.ts` 的
`setState` 之后（现有持久化路径里）挂一个防抖（比如 800ms）触发同步上报，
失败时静默重试一次（网络瞬断级别），**不做 5xx / 限流的自动重试轮询**——
按 `AI_GUIDELINES.md` 的既有原则，业务性失败要么静默失败等下次操作触发，
要么在 UI 上给出"同步失败，检查网络"提示，不在惩罚窗口内反复探测。

### 部署方式

- `biu-sync-server/`：独立 Node 服务，`pm2 start ecosystem.config.js`，
  **`instances: 1`，`exec_mode: "fork"`**（不能用 `cluster`，原因见上）。
- `pm2` 配置 `max_memory_restart: "150M"`——服务本身是无状态薄层（不缓存
  用户数据在内存里，每次请求现读现写文件），150M 对这个工作负载是宽松
  上限，超过说明有内存泄漏，触发自动重启好过拖累其他服务到 OOM。
- Apache 侧新增一个 `ProxyPass /biu/sync/ http://127.0.0.1:3002/`（参考
  `docs/release/自动更新部署指南.md` 里已有的静态目录配置手法，新增反代配置而非
  破坏原有 `updates/` 静态托管）。
- `systemd` 层面额外给这个 pm2 托管的进程配置 `MemoryMax`（通过 pm2 的
  systemd 集成或者手动 cgroup），双保险防止极端情况下拖垮整机——如果
  ECS 上其他服务本身就没做这层隔离，这次新服务至少不能成为压垮骆驼的
  那根稻草。
- 日志：`pm2` 默认日志会无限增长，必须配 `pm2-logrotate`（`pm2 install
  pm2-logrotate`），避免日志把 28G 磁盘慢慢吃满——虽然磁盘现在宽裕，
  但这是长期运行必须有的兜底。

### 边界情况清单（实现时逐项检查）

- [ ] `mid` 非数字 / 缺失 → 401，不拼路径
- [ ] JWT 过期 / 篡改 → 401，客户端静默用 cookie 重新换发
- [ ] 请求体 `ops` 为空数组 → 直接返回当前快照，不产生新 version（避免
      空操作也推进版本号，干扰其他设备的 baseVersion 判断）
- [ ] 单个 `store` 文件不存在（用户第一次同步）→ 视为 `version: 0`，
      客户端首次全量上传
- [ ] 磁盘写入失败（权限 / 磁盘满）→ 500，客户端本地数据不受影响
      （本地 electron-store 仍是 source of truth，同步失败不影响本地可用性）
- [ ] 并发压力：单进程 + 每 mid 互斥队列，天然限制了同一用户的写入吞吐，
      不需要额外加限流；但要防止恶意/异常客户端高频请求打满这台内存
      紧张的机器 —— 加一个简单的每 IP/每 mid 速率限制（比如 10 req/s）
- [ ] 墓碑数据的定期清理任务（避免文件无限增长），可以用一个每日
      `node-cron` 任务而不是额外的系统级 crontab，减少运维面

### 明确不做的事

- 不做网页版、不做除同步接口外的任何 UI 暴露。
- 不做实时推送（WebSocket/SSE）通知"别的设备改了"——客户端下次启动 /
  下次操作前拉取一次最新版本即可，双端几乎同时改动导致短暂不一致是可接受
  的，用户手动切换设备使用场景下不构成问题。
- 不引入独立账号体系（邮箱注册/密码等）——身份完全绑定 B 站登录。
- 不做字段级 CRDT 之类的高级冲突算法——条目级合并 + 墓碑 + last-write-wins
  对这个数据规模和使用场景已经足够，过度设计只会增加维护负担。

## 事故复盘与最终实现（2026-08-04）

> 2.5.0 上线后发生数据丢失：云端 `favorites`（歌单夹）被整体删空。
> 完整链路图见 [`docs/devlog-assets/sync-flow-and-guards.svg`](../devlog-assets/sync-flow-and-guards.svg)。

### 出了什么事

事故当天从客户端同步记账里读到的云端基线状态：

| store | 状态 | 结论 |
|---|---|---|
| favorites | 0 活 / 5 墓碑 | 被删空 |
| fav-items | 259 活 / 2 墓碑 | 完好 |
| tags | 227 活 / 0 墓碑 | 完好 |

被删的只有歌单夹这一个 store。UI 上表现为「歌单全没了」，因为夹子没了、歌变成看不见的孤儿。

**两个独立的 bug 叠加**：

1. **状态未就绪就 diff**。三个 store 都是 zustand `persist`，rehydrate 走
   `platform.getStore` → IPC → 主进程读盘，是异步的；而同步只等了 800ms 防抖就
   `encodeNow()`。冷启动时主进程忙于建窗口/初始化/校验登录，这条 IPC 排队超过
   800ms 完全正常。拿到初始空值后：第二次及以后的启动 `hasSyncedBefore === true`，
   走的是 `diffSnapshots` 而非只增不删的 `diffForMigration` → 基线里每个 id 都不在
   空快照里 → 全量 `remove` → 服务端打墓碑（payload 直接丢弃，不可逆）→ 返回空快照
   → `applyRemote` 写回本地 → persist 落盘，本地也空了。

2. **同步是单向的（只推不拉）**。`pullSnapshot` 只在首次迁移里调过一次，之后
   `syncOnce` 在 `ops.length === 0` 时直接 return。用户表现：Windows 上加的歌，
   Mac 开着等一天都不下来，重新登录才生效——重登会重走迁移分支，那里才有拉取。

### 是什么救了数据

**不是同步系统自己的安全网**，而是 6 月那次事故（commit `f47b0cb`，「防本地收藏夹被
登录覆盖，并启动时自动快照备份」）留下的两样东西：

- [`electron/store-backup.ts`](../../electron/store-backup.ts)：每次启动把
  `Documents/Biu` 的三个 json 快照到 `userData/data-backups/<时间戳>/`。用户正是从
  这里找回了最新数据。
- [`favorite.ts`](../../src/store/favorite.ts) persist `setItem` 里的防覆盖保险：
  「本地夹为空但 `folderItems` 还在 → 保留磁盘上的夹」。它让本地文件在 `applyRemote`
  写入空数据时没有被清掉。

同步自己那层 `preMigrationBackups` **只写一次、之后永不更新**，只能救回首次迁移当天的
状态，对事故窗口内新增的数据无效——这是设计缺陷，不是实现 bug。

### 最终实现

**触发时机**（本地变更走防抖合并，外部触发一律立即执行）：

| 触发源 | 用途 |
|---|---|
| store `subscribe` | 本地改动后上报（防抖 400ms，**最长等待 1.2s**）|
| 通知通道 `/watch` 返回 changed | 另一台设备改动后下拉（主路径，`syncNow` 不走防抖）|
| 窗口 focus | 补一次（防系统休眠唤醒后连接已死但未超时）|
| 登录态 mid 出现 | 冷启动首次对账（`syncNow`）|

**一次 `syncOnce` 的顺序**（三道闸门见流程图）：

1. `await waitReady()` —— 等 persist rehydrate，**必须在任何 `encodeNow` 之前**；
2. `pullSnapshot()` —— **每次都拉**，本机无变更也要拉，否则同步是单向的；
3. 空快照闸门 —— 本地空 + 基线非空 → 拒绝推送并 `log.error`；
4. `diffSnapshots` → 有变更才 `pushLocalBackup` + `pushOps`；两边都没动则直接返回
   （不写回本地，否则 `setState` 会触发订阅再排一轮，空转不停）；
5. `applyRemote` + 落 meta。

**数据保护共四层**，各自独立、互为兜底：

| 层 | 位置 | 份数 |
|---|---|---|
| 启动快照 | `userData/data-backups/` | 10 |
| 推送前滚动备份 | `playlist-sync-backups.json` | 10 |
| 首次迁移前快照 | `playlist-sync-meta.json` 的 `preMigrationBackups` | 1（只写一次） |
| 服务端写前历史 | `/data/biu-sync/{mid}/history/` | 10 |

还原工具：[`dev_tools/restore-local-playlist.mjs`](../../dev_tools/restore-local-playlist.mjs)，
默认只预览，`--apply` 前会把现有 json 另存一份。

### 为什么跨设备实时用长轮询，不用定时轮询

需求是「另一台设备一改，这台立刻看到」，可接受延迟约 800ms 级别。

- **定时轮询 800ms**：3 个 store × 每 800ms = **225 请求/分钟**，撞服务端限流
  （60/min），也白烧这台 1.8G 内存机器的 CPU。调稀到能接受的频率，延迟就上去了。
- **长轮询 + 进程内事件总线**（最终方案）：客户端挂一个 `GET /watch?versions=...`，
  服务端有变更立刻返回、无变更挂到 25s 超时。空闲时不轮询、不耗 CPU，只占一个连接；
  写入时 `notifyChange(mid)` 即时唤醒，端到端延迟 ≈ 一次请求往返，**比 800ms 轮询
  更快且更省**。
- 未用 WebSocket/SSE：长轮询走普通 HTTP，Apache 反代不用额外配置（只需
  `ProxyTimeout > 25s`），也不引入连接状态管理。

**前提**：pm2 必须 `fork` 模式单实例——事件总线和存储互斥队列都是进程内的，
开 cluster 会导致写入发生在 A 进程、等待挂在 B 进程，唤醒串不过去。

### 服务端加固

客户端可以出错，服务端不能因此丢数据：

1. **写前留历史**：`mutateEnvelope` 覆盖前把上一版完整存进 `{mid}/history/`，保留 10 份。
   墓碑只记「这条被删了」、payload 直接丢弃，没有历史版本云端就是不可逆的。
2. **全量删除闸门**：一批操作删光全部活条目且无任何新增 → 409 拒绝 + 日志。
   活条目少于 5 条时不启用（用户真删光两三条是正常操作）。

   **但用户真的删光是合法的**——比如只有一个歌单、里面 200 首歌，整个删掉，这批操作
   正好删光 `fav-items` 的全部活条目。硬拦会让这台设备之后每次同步都被拒、彻底卡死。
   客户端能区分两者：真删是「本次会话里先见过内容、现在没了」（`witnessedNonEmpty`），
   故障是「一上来就是空的」。前者推送时带 `allowFullDelete: true`，服务端认这个确认。

### 升级过渡：记账世代号

`SYNC_META_EPOCH` 改动一次，所有设备本地的旧基线作废一次，下次同步强制走
`migrate`（只增不删）。

Why: 2.5.0 的 bug 会让设备本地数据和它的基线严重不一致（本地被清空/回退，基线还停在
事故前）。修好的版本若直接拿旧基线 diff，「基线有、本地没有」会被算成删除推上云，把
另一台设备刚恢复的好数据删掉。作废一次基线、走一次并集合并是唯一安全的过渡；代价是
那台设备上「曾经删掉的条目」可能被云端复活，比误删数据轻得多。

### 延迟从哪来（实测 3s → 优化后 ~0.8s）

用户反馈"改一次要等 3 秒，连续操作还会卡住不同步、过一会儿一起到"。拆开看是两个问题：

1. **两处防抖叠加**。发送端 800ms 是合理的（合并连续操作），但接收端被 `/watch`
   通知唤醒后又走了一遍 `scheduleSync()` 的 800ms——接收端不是用户连续操作触发的，
   没有需要合并的后续变更，这 800ms 纯属白等。改用 `syncNow()` 直接执行。
2. **纯防抖被连续操作饿死**。每次变更都 `clearTimeout` 重置计时器，用户以小于防抖
   时长的间隔连续收藏时，推送被无限往后顺延，直到停手才一次性全推。加 `SYNC_MAX_WAIT_MS`
   上限：距第一次未处理变更超过 1.2s 就强制推，不再等安静。

| 环节 | 优化前 | 优化后 |
|---|---|---|
| 发送端防抖 | 800ms（连续操作时无上限顺延）| 400ms，上限 1.2s |
| 推送 | ~100ms | 同 |
| 服务端通知唤醒 | ~20ms | 同 |
| 接收端防抖 | 800ms | **0（syncNow）** |
| 拉取 + 渲染 | ~200ms | 同 |
| **合计** | **~2-3s** | **~0.8s** |
