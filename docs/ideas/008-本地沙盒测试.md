# 008 本地沙盒测试：不用 B 站账号跑通整个项目

## 结论

在现有的「响应式离线 Demo」上加一个**开发用的沙盒模式**：

- **B 站这一层全部换成本地假数据**（沿用离线 Demo 的做法：同一棵组件树，只在请求出口替换）
- **自家服务（对齐服务、之后的同步服务）跑真代码的 mock 模式**，在本机起
- **身份在页面里一键切换**：未登录 / 普通用户 A / 普通用户 B / 管理员，不重启、不签 token、不碰真实账号

一条命令起来，打开浏览器就能测。按需增量做：第一期只覆盖「播放 + 歌词对齐 / 报错 / 审核」，以后哪个功能要测再补那几个接口的数据。

**状态**：第一期已实现（2026-10-27）。用法：

```bash
pnpm sandbox            # 打开 http://localhost:5679 ，顶栏中间「沙盒」菜单切换身份
pnpm sandbox --reset    # 先清空对齐服务的沙盒数据（报错、提交、对齐结果）
```

浏览器里的设置、歌单、播放列表用菜单里的「清空本页数据」清。

## 为什么现在测起来累

几乎每个功能都同时依赖两样东西：

| 依赖 | 现在的测法 | 问题 |
|---|---|---|
| B 站（登录、播放地址、收藏、搜索、字幕） | 用真实账号 | 每个操作都是真的，有心理压力；限流、PCDN 卡流、0 播放量这类边界几乎造不出来 |
| 自家服务的身份（对齐、同步） | 测试 token + 改设置文件 + 重启 `pnpm dev` | 切一次身份要重启；步骤多，容易忘了还原设置 |

「测试账号」只解决了第二行的一半。

## 为什么在离线 Demo 上扩展，而不是另起一个「假 B 站服务器」

项目里已经有一套离线 Demo（`BIU_TARGET=demo`，见 `docs/responsive-prototype/网页原型设计.md`）：

- 渲染层的 axios 换成本地适配器，按路径返回假数据（`src/common/offline-demo-fixtures.ts`，已覆盖登录信息、收藏夹、合集、播放地址、搜索建议等）
- 平台层（`src/platform/web.ts`）对歌词搜索、AI 字幕等能力返回空结果
- 存储用独立前缀（`biu-demo:`），和真实数据隔离

它已经证明了「只在出口替换，页面和状态机都是真的」这条路可行。另起一个假 B 站 HTTP 服务器的话：

- 要同时让渲染层 axios、Electron 主进程、Web BFF、手机原生 HTTP 四条路都改指向它，还要模拟 wbi 签名、Cookie、Referer 校验，工作量大得多
- 和离线 Demo 是两套假数据，必然各自漂移

所以沙盒复用离线 Demo 的假数据和替换点，**只补它缺的东西**。

## 沙盒和离线 Demo 的区别

两者不能合并成一个开关：离线 Demo 是给文档原型静态部署用的，要求**没有任何副作用**；沙盒恰恰要连本机的自家服务，否则测不了对齐、报错、审核、同步。

| | 离线 Demo | 沙盒 |
|---|---|---|
| 用途 | 文档原型，静态部署 | 本机开发测试 |
| B 站 | 假数据 | 同一份假数据 |
| 对齐 / 同步服务 | 关闭 | 连本机 mock 模式的真服务 |
| 身份 | 固定一个演示用户 | 页面内切换 |
| 音频 | 静音 | 有声音、有长度的测试音频 |
| 构建 | `build:responsive-demo` | 只有 dev，不出产物 |

做法：新增构建期标记 `BIU_TARGET=sandbox`，它**包含**离线 Demo 的替换，再额外打开下面几项。离线 Demo 的行为不变。

## 第一期：播放 + 歌词对齐 / 报错 / 审核（Web）

只做 Web，因为 Web 的请求全在浏览器和本机 dev 中间件里，替换点最少。

### 1. 一条命令启动

`pnpm sandbox`：
- 用临时数据目录起对齐服务的 mock 模式（不下载音频、不跑模型，返回假对齐结果）
- 用 `BIU_TARGET=sandbox` 起 Web dev
- 退出时一起关掉；`pnpm sandbox --reset` 清空对齐服务的数据目录（`~/.biu-sandbox`）
- **独占 5679 端口**：有些 store 存在不带前缀的 localStorage 里（播放列表、搜索历史），和 `dev:web` 同源就会共用。独立端口 = 独立的浏览器源，「清空本页数据」可以整源清空

不新增依赖，用 Node 自带的子进程起两个服务。

### 2. 身份切换器

- 只在沙盒构建里出现：页面角落一个小菜单，四个身份：未登录 / 普通用户 A / 普通用户 B / 管理员
- 切换后：
  - B 站假数据的「当前登录用户」跟着变（未登录时返回未登录）
  - 对齐请求带上这个身份。Web 原本由 BFF 用 B 站登录会话换 token；沙盒里 dev 中间件改为向本机 mock 对齐服务要这个身份的 token
- token 由 dev 中间件直接签：`pnpm sandbox` 每次启动随机生成密钥，同时传给 mock 对齐服务和 dev 中间件。对齐服务**一行不改**，也就不存在「生产环境里多出一个发 token 接口」的风险（原计划是在 mock 对齐服务上加签发接口，实现时换成了这个）
- 对齐请求仍走线上同一份 Web 转发代码（放行名单、登录检查、错误文案都是真的），只把「拿 B 站会话去同步服务换 token」替换掉
- 当前身份存在 cookie 里：dev 中间件签 token 要读，页面返回「当前登录用户」也要读，两边读同一份。换身份后刷新页面，比逐个 store 重置可靠

为什么不沿用「测试 token 环境变量 + 重启」：报错 → 审核 → 报错人看结果这条链要来回切三次身份，每次重启是现在最累的地方。

### 3. 测试音频

- 离线 Demo 的播放地址是一段空的静音 wav，播放器拿不到时长，进度条和逐字高亮都动不了
- 沙盒改为 dev 服务器现场合成的一段 60 秒音调（每句歌词换一个音），不进仓库、不需要 ffmpeg，没有版权问题；支持 Range，可以拖动进度
- mock 对齐不分析音频内容，所以不需要真人演唱

### 4. 歌词假数据

- 至少一首「视频」带一份固定 LRC，供歌词显示、自动对齐、报错用
- 一首没有歌词，用来看「暂无歌词」
- 第一期不做填词歌画面识别

### 5. 第一期能测什么

用这套就能不碰 B 站跑完上一轮审核改动的测试：
1. 普通用户 A：播放 → 自动对齐 → 报错 → 「我的提交」里看到处理中
2. 切到管理员：审核页「重新对齐对照」→ 并排对照 → 驳回 / 下线 / 替换；播放器里试听 → 切歌回来续上 → 放弃 / 发布
3. 切回普通用户 A：看到「已换成管理员重新对齐的版本」

## 之后几期（按需做，不预先做）

| 期 | 内容 | 什么时候做 |
|---|---|---|
| 二 | 同步服务 mock + 两个窗口各选一个身份，测跨设备同步 | 下次改同步时 |
| 三 | 故障注入：切换器里加「下一个请求返回 429 / 5xx / 超时 / 播放地址卡住」 | 下次改错误处理或选流时 |
| 四 | Electron 沙盒：主进程里那些直接请求 B 站的能力（歌词、AI 字幕、下载）也换成假数据 | 下次改桌面独有功能时 |
| 五 | 用 Playwright 把关键流程写成自动化脚本，跑在沙盒上 | 手动流程稳定后 |
| — | Android / iOS | 暂不做：手机原生 HTTP 适配器会覆盖掉替换用的适配器，要单独设计 |

每一期都只补当时要测的那几个接口和数据，不预先铺满。

## 边界与红线

- **不进生产**：沙盒代码只在 `BIU_TARGET=sandbox` 时通过动态导入加载，`sandbox` 目标拒绝 `build`。动态导入处必须直接写 `process.env.BIU_SANDBOX === "true"`：写成跨模块的常量，打包器折叠不了，沙盒代码会被打成正式产物里的异步包（实测踩过）。已用正式 Web 构建确认产物里没有沙盒代码
- **不复用真实数据**：存储前缀 `biu-sandbox:`，对齐服务用临时数据目录，和真实账号、离线 Demo 都隔离
- **mock 签发 token 只在 mock 模式**：生产启动时这个接口根本不存在，而不是「存在但做校验」
- **沙盒测不到的**：B 站真实接口的变化（字段改名、签名规则、PCDN 节点）、真实对齐效果、各平台原生能力。发版前仍用真实账号做一次冒烟测试
- **假数据要标口径**：每条假数据注明它模拟的是哪种真实情况（比如「0 播放量」对应 AGENTS.md 里收藏夹接口的事故），否则以后没人敢改
