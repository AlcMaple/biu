# 002 - 歌词时间轴对齐：研究过程报告

> 目标：网易云 / LrcLib 拿到的歌词，时间轴和 B 站音频对不上 → 自动修正，效果像网易云 / QQ 音乐 / Apple Music 那样跟唱。
> 不要求实时，**后台算一次、永久生效**即可。
>
> 本文是研究过程的总账，达到预期效果之前一直保留。每做一轮研究就在第 2 节追加一轮记录，
> 要求每轮至少比上一轮多一个实测数据点或排除一个方向。方案细节和最新数据写在
> [`docs/lyrics/歌词时间轴对齐-可行方案调研.md`](../lyrics/歌词时间轴对齐-可行方案调研.md)。

## 1. 当前位置（2026-10-19）

- **方向**：服务端做，按 `bvid + cid + 歌词哈希` 缓存，全平台共享。**核心算法改为 Demucs 分离人声 + MMS_FA 强制对齐**（PotLyrics 式，对标开源后胜出），不再用 Whisper 识别 + DTW。
- **进度**：第 4 轮。在 7 首、327 行（网易云逐字真值）上：MMS_FA 行起点中位误差 37 ms、98% ≤ 300 ms；逐字 24 ms、95% ≤ 150 ms。自研的「合并段 + 校准」是 115 ms / 92%，网易云逐行 194 ms / 77%。Qwen3-ForcedAligner 鲁棒性差，不采用。评测基准在 2 首歌上偏 0.19 s（起唱点同时被用来求真值和做校准），已用两个独立对齐器修正。
- **兜底**：已取消「回退到平移估计、标推测」。人耳试听唯一、晴天 4K MV，凡标推测的行都是回退错了，MMS 原样更准。改为**静音门控**：人声轨静音处不许放歌词，修掉首行被放进前奏（晴天 Hi-Res 首行从早 26.6 s 修到 29.3 s，原轴 29.4 s），7 首真值指标不变。剩 2 行 > 1 s（0.6%），都出在非常规编排，不专门处理。
- **取舍**：以常规歌曲为准（如晴天 Hi-Res）。剪辑版、特殊编排（如晴天 4K MV 中段的沙哑人声）不专门处理。
- **失败行兜底**：局部重对齐。对齐结果每字快于 0.15 s 的行和它的前一行，只在「原歌词时间 + 整首偏移」附近的窗口里重新做强制对齐，逐字时间仍来自音频；另有两道闸防止现场版 / 剪辑版被挪错（调研 5.2.13）。跳楼机副歌的连续错位已修好；7 首真值歌上偏差 > 1 s 的行 2 → 1。
- **双切法平均**：模型按两种起点（0 s / 7.5 s）各切一遍音频，概率取平均，修掉 15 s 块边缘附近识别变差的问题（跳楼机卡住的真正根因，不是英文「baby」）。每首对齐约 40 s（原来约 25 s）。7 首真值：行起点 40 ms / 93% ≤ 150 ms / 98% ≤ 300 ms，> 1 s 的行只剩 1 行（调研 5.2.14）。
- **验收线（用户定）**：个别行些许误差可以接受，可人工调整；不能「一段错，后面连续错」。
- **部署**：服务器是 Mac mini（Apple M4 10 核、16 GB 内存、剩余磁盘 71 GB，平时负载约 2、内存空闲 76%），够跑单任务队列。审核员 B 站 UID 写进服务端部署配置，不进仓库。
- **P1 服务端已完成（未部署、未提交）**：`biu-align-server/`，端到端实测跑通（跳楼机 106 s；配错歌词正确拦下），26 个单测通过（调研 5.2.15）。
- **下一步**：部署到 Mac mini（装 Python 依赖、launchd、反代 + 隧道），Web 版 BFF 加转发；然后 P2 客户端。

## 2. 历次尝试

### 第 1 轮 · 桌面本地 Demucs + WhisperX（2026-03 ~ 04，已移除）

- 做法：Electron 主进程调用户本机 Python，Demucs 分离人声 → WhisperX 强制对齐。
- 结果：能跑，但从 GUI 移除。主进程里残留代码（`whisperx-sync.ts` 等）目前没有调用方。
- 坑：
  - 依赖用户本机 Python / 模型 / ffmpeg，安装就劝退大部分人；Android / Web 用不了。
  - tqdm 进度条在 Electron 里乱码（UTF-8 被日志按 GBK 显示）、`\r` 不能原地刷新，因为主进程 stdout 不是 TTY。只能把进度解析成数据，通过 IPC 交给 UI 画。
  - WhisperX 整首歌会因 VAD 把整段合并，错位几十秒（lyric-align 作者实测平均误差 47 s）。
- 带走：**不在用户机器上跑模型**；整首歌不能直接喂通用语音对齐。

### 第 2 轮 · 拖拽歌词手动校准（2026-05，已撤回）

- 做法：用户拖动歌词到当前唱的位置，算出偏移。
- 坑：拖动时播放还在走，松手算出的偏移总慢 1~2 s；拖动时视口冻结，和播放进度脱节。
- 带走：手动打轴体验做不好。现有的「整体偏移」控件留作兜底，不再在手动方向投入。

### 第 3 轮 · 阿里云 ASR + DTW，客户端经 OSS 直传（2026-05-15 ~ 06-04，放弃）

- 做法：客户端用 STS 临时凭证把音频传到 OSS → 服务端调 paraformer-v2 / fun-asr 拿字级时间戳 → DTW 把原歌词字符和识别字符匹配，借用时间戳 → 行级 LRC。
- 结果：《唯一》（人为整体 +5 s）对齐后在播放器里听已经准了。`biu-lyrics-server/src/lib/` 的 parseLrc / DTW / buildLrc / 全局偏移估计都已写完，66 个单测全绿（旧版本文写「未动工」是错的）。
- 放弃原因（用户确认）：OSS / STS / RAM 配置太繁琐，只测了一首歌，对效果没把握，担心改动大、投入白费。
- 坑：
  - fun-asr 是异步任务，要轮询状态；结果在 `transcription_url` 里，还要再 GET 一次。
  - 歌词副歌只写一遍、实际唱多遍时，DTW 只能对上第一遍。
  - DashScope Key 曾在聊天里明文出现，重新启用前要轮换。
- 带走（算法层面验证过的设计）：
  - 插入代价 0.3 < 删除代价 1.2（宁可 ASR 多认字，也不漏真实歌词）；DP 允许开头、结尾任意跳过，以此跳过前奏和尾奏；中间间奏线性插值。
  - 原 LRC 的旧时间戳当软先验（默认 0.05 分/秒），元数据行按原文透传。
  - 每行取首个非标点字的时间，避免行内节奏抖动放大成行间偏移。
- 教训：**先用多首歌、最低成本验证效果，再碰云配置和集成。**

### 第 4 轮 · 重新调研 + 分级止损验证（2026-10-19，进行中）

- 调研结论：开源界（lyric-align、stable-ts、PotLyrics）对「已有歌词 + 整首音频」用的就是「歌声识别 → 已知歌词匹配 → 借时间戳」，和第 3 轮同一个思路。第 3 轮输在部署形态和验证不足，不是算法。
- 新方案的改进：服务端自己拉 B 站音频，客户端不再上传，OSS / STS 整条链路删除；按投入从小到大分 3 步验证，每步都能停。
- 步骤 1（本地 0 元，不改业务代码）：Demucs（CPU）→ faster-whisper medium 字级时间 → 同一份识别结果分别交给 lyric-align 和现有 DTW。

  | 投稿 | 自动找出的偏移 | DTW 与邻行一致 | lyric-align 与邻行一致 |
  |---|---|---|---|
  | 晴天 Hi-Res | −0.1 s | 88% | 55% |
  | 晴天 4K MV | 前 28 行 +14.4 s（±0.3 s），尾段 +16.0 s | 67% | 33% |
  | 光年之外 MV | +0.2 s | 75% | 14% |
  | 唯一 MV | 原轴粗糙，不能当真值 | 67% | 42% |
  | 江南 现场 | 两段：−11.9 s / −15.7 s | 93% | 47% |

  「与邻行一致」= 该行偏移与前后 3 行中位偏移相差 ≤ 0.5 s。数字都是和原歌词轴比，**还没有人耳试听**。

- 结论：
  - 片头偏移、现场版两段平移都能自动找出，「分段平移」成立。
  - **对齐算法沿用现有 DTW，不引入 lyric-align**（Whisper 常把两句并成一段，lyric-align 按换气切分会把第二句提前 2~5 s，还漏行）。
  - 本地免费链路可行，约 6 min/首（M3 CPU），适合服务端后台一次性计算。
- 坑：
  - lyric-align 自带的 Demucs 在 Apple 芯片上走 MPS 会崩，要手动 `python -m demucs ... -d cpu`。
  - B 站搜索接口高频请求返回 412，要放慢并带 buvid3 cookie；yt-dlp 下载 B 站当前失效，改用 view + playurl 接口自己取流。
  - 歌词末尾的制作人员名单（「混音师 : xxx」）必须在对齐前过滤，否则会被插值到结尾。
  - 结尾反复的副歌容易错配到别的重复段（晴天 MV 有 6 行）。
  - 原轴本身粗糙的歌（唯一，每行都是 .30 s）不能拿原轴评分，只能人耳判断。
  - 繁简体对结果几乎没影响，不用处理。
- 人耳试听第 1 首（晴天 Hi-Res，只看「分段平移」栏）：部分行第一个字一出来就切，部分行轻微迟切。拆开看是三处叠加：
  - 试听页靠播放器的进度事件刷新，Chrome 约 250 ms 一次 → 0~250 ms 随机迟切，正好解释「有的准、有的晚」。已改为每帧刷新。
  - 分段平移把这首切成 +0.23 / −0.13 / −0.06 s 三段，第 6~13 行被推晚 0.23 s；段间差 < 0.3 s 应合并（待做第 3 条）。
  - 这首平移后基本等于原轴，原轴本身若偏晚，平移无法修正。
- 重听（每帧刷新后）：大部分行跟唱，个别行晚几百毫秒 ~ 1 s。和识别结果比对，偏晚的候选行是「沒想到失去的勇氣」+0.4 s、「好想再問一遍」+0.5 s、「颳風這天」+0.7 / +1.4 s 等，量级吻合。说明分段平移打底后，还要按行微调：原歌词个别行本身打晚了，平移只能整段搬，修不了单行。
- 新增试听第 4 栏「平移 + 逐行微调」：识别到的行若和平移结果差 0.25~1.5 s，改用识别时间；其余不动。另加「提前量」选择（0~300 ms），和行本身准不准分开听。
- 用户指出：看高亮 + 听，本身就有几百毫秒的判断误差，反复听还会产生错觉，这样调下去没有尽头。→ **改用网易云逐字歌词（人工逐字打点）当真值，按数字评估**，人耳只做最后确认。
- 光年之外的客观结果（各栏扣掉自己的整体偏移后）：原歌词 91% 行 ≤ 300 ms；分段平移 91%；平移 + 逐行微调 84%；逐行 DTW 68%（6 行 > 1 s）。→ 平移方向对；用识别时间逐行改反而变差，第 4 栏否掉。
- 未解决：平移结果整体比原歌词晚约 0.25 s。从分离人声量起唱上升沿，得到 −0.05 s / +0.21 s 两个峰，暂时分不清。
- 网易云逐字歌词只有光年之外有（晴天、江南、唯一都取不到），真值不够。→ 改从分离人声里找「静了 ≥ 0.3 s 后开始出声」的起唱点，不依赖歌词，5 首都能测。在光年之外上和人工逐字时间比，中位 −0.03 s、100% 在 300 ms 内，检测器可信。
- 用起唱点量出：**分段平移在光年之外、晴天 Hi-Res、晴天 4K MV 上都晚约 0.2 s**，唯一 ≈ 0，江南早 0.12 s。整体偏晚就是试听时「个别行晚一点」的来源；偏差不是常数，不能统一减。
- 新增第 5 栏「平移 + 起唱点校准」：每段 ±0.5 s 内整段微挪对齐起唱点，段内起唱点 < 3 个不挪。偶数行拟合、奇数行打分：晴天 4K MV ≤150 ms 从 20% → 80%，光年之外 50% → 83%，江南 50% → 88%；晴天 Hi-Res、唯一起唱点太少，不变。
- 拿人工真值复核光年之外：校准把整体偏差从 +0.14 s 拉到 −0.04 s，但逐行误差仍约 150 ms，与网易云自己逐行歌词的误差（132 ms）同一量级，已接近原歌词精度上限；这首已过第 5 节门槛。
- 坑：起唱点不够时用「整首歌一起拟合」兜底会把噪声当信号（晴天 Hi-Res 被纠过头到 −0.17 s），已弃用。每首打分只有 5~8 行，样本小。
- 用户试听第 5 栏：光年之外前段达标，2:12~2:28 整段迟切，之后恢复。对真值确认属实：识别噪声把本来就准的原歌词切成 +0.19 ~ +0.71 s 五段，小段起唱点不够、校准不动。
- 修法：相邻段平移差 < 1 s 并成一段（真实剪辑都是秒级以上的跳变），再整段对齐起唱点（`merge.py`，试听页第 4 栏「合并段 + 起唱点校准」，替换已否掉的逐行微调栏）。光年之外：中位误差 110 ms、91% 行 ≤ 300 ms、无 > 1 s，各项不差于网易云自己的逐行歌词（132 ms / 88%）；晚 > 300 ms 的行从 10 行降到 2 行。
- 「达到网易云水准」改成可量的口径：网易云对同一首歌有逐行、逐字两份人工时间轴，逐行对逐字的误差就是「网易云水准」；我们的结果对逐字真值不差于它即可。用户反馈自己看高亮判断有误差、反复听会产生错觉，这个口径替代了人眼。
- 试听页加了逐字填充：光年之外用网易云逐字时间，其余歌按字均匀填充（仅示意）。桌面歌词窗口现有的「逐字」也是均匀填充。
- 用户看逐字填充：画面慢 1~2 个字，行尾又对齐。数据不支持（行起点对真值 −0.05 s，每字约 0.36 s），判断为显示方式所致：渐进填充下字唱完才填满，未唱 / 已唱颜色太近时半填的字看不出来；行尾拖音让填充追上。试听页改为默认「按字点亮」并加大颜色对比，待用户复听。
- 用户提出：生产环境不能有的歌有逐字、有的没有；手动选的歌词也要自动校对，用户也判断不了哪份带逐字。→ 对齐服务统一输出行时间 + 每字时间，逐字来源自动分三级：网易云逐字 > 识别结果的字时间（插值补齐）> 行内均匀分配；界面表现一致。第 2 级精度待测。
- 用户按字点亮听第 4 栏：基本没问题，2:12~2:21 完全同步，其余穿插「画面快一点点、可忽略」。数据吻合：那段 −180 ~ +70 ms；「快一点点」是副歌几行每次都早 170~250 ms，网易云逐行歌词本身就早。按 ITU-R BT.1359，画面早 125 ms 开始可察觉、185 ms 内可接受，和用户感受一致。→ 不再加提前量。
- 用户没听出、数据有问题的：结尾 4 行偏差 0.5~0.9 s，原歌词本身就错，平移修不了。试过逐行吸附到起唱点：≤ 200 ms 从 79% 到 82%，这 4 行一行没修好（连唱、附近没有起唱点），暂不采用。
- 扩样本：20 首候选里 11 首有网易云逐字歌词，B 站按「非现场 / 翻唱、时长相近、播放量最高」自动挑投稿，跑同一流水线。先用人声起唱点核对是否同一录音（≥ 8 行、≥ 80% 在 300 ms 内），12 首过 7 首。结果：合并段 + 校准 72 ms / 98% ≤ 300 ms，网易云逐行 194 ms / 77%；7 首里 6 首更准，修炼爱情整体早 150 ms 待查。「原歌词个别行错 0.5 s 以上」只在光年之外结尾出现（0.9%），强制对齐暂缓。
- 坑（扩样本）：网易云逐行歌词里有 JSON 制作人员行、英文制作名单、「歌手 - 歌名」标题行，漏过滤一行就整体错位（平移量变成 −15 ~ −28 s）；PCDN 节点可能不在域名里带 mcdn（`*.edge.mountaintoys.cn`，只有 `os=mcdn` 参数能识别），应用的 `isPcdnUrl` 也会漏判；评测偏移不能全范围搜，副歌重复会出假峰。
- 逐字精度（7 首、2738 字，对网易云人工逐字）：网易云逐字 79 ms / 98% ≤ 300 ms；识别字时间按原样（每行以首字为锚）165 ms / 74%，整首一个偏移锚定 140 ms / 88%，再减固定偏差 90 ms / 92%；均匀分配 306 ms / 49%，> 500 ms 占 32%。→ 第 2 级可用；桌面歌词现在的均匀填充要换掉。
- 坑（逐字）：Whisper 每段首字常偏早，逐行以首字为锚会让行内后面的字整体偏晚，要改为整首锚定；识别出的字普遍晚约 120 ms（各首留一估计 100~130 ms，很稳定）；Whisper 常出繁体字，现有 DTW 只认同字，同字匹配率 60~98%，DTW 前转简体有望提高（未测）。
- 用户质疑「没看前人做法就自研」。补跑第 3 节调研过的两个开源方案：MMS_FA（PotLyrics 式：Demucs + 拼音 + CTC 强制对齐，每首 20 s CPU）和 Qwen3-ForcedAligner（每首 1~5 min CPU）。**MMS_FA 全面胜出**：行起点 37 ms / 98% ≤ 300 ms，逐字 24 ms / 95% ≤ 150 ms；自研只有 115 ms / 92%。→ 核心换成 MMS_FA，Whisper + DTW 退役。Qwen3 有 18% 的字偏差超过 0.5 s，不采用。
- 坑（评测）：MMS_FA 和 Qwen3 都显示光年之外、年少有为整首比真值晚约 0.19 s，原因是评测里的投稿偏移 X 和自研校准都基于人声起唱点，偏在一起、互相印证。修正后自研从 72 ms 变成 115 ms。教训：求真值和被评的算法不能共用同一个信号，要用独立方法交叉验证。
- 坑（环境）：qwen-asr 依赖的日语分词 nagisa 需要编译，pip 会卡死；大包（torch）在当前网络下也下不动。解决：venv 加 `--system-site-packages` 复用现有 torch / transformers，只装小包，nagisa 用占位代替。
- MMS_FA 的失败行：孤勇者一行偏 −5.2 s，光年之外结尾一行偏 −1.1 s。需要兜底。
- 兜底：MMS 行起点与「合并段 + 校准」相差 > T 就回退。7 首真值上 T = 1 s 最好（> 1 s 的行 2 → 0，回退 2 行）。
- 现场版 / 剪辑版：江南现场版 95% 行两者相差在 0.3 s 内，MMS 能处理现场版；晴天 4K MV 第 28 行起差 +10 ~ +19 s（MV 剪辑，强制对齐假设每行按顺序唱一次）；唯一 14 行差 > 1 s（原轴粗糙）。剪辑版上「平移估计更准」这个前提未经验证，回退行一律标推测，等人耳确认。
- 试听页改成 4 栏：原歌词 / 合并段 + 校准 / MMS_FA 原样 / MMS_FA + 兜底，MMS 两栏用真实逐字时间点亮。
- 用户试听裁决：唯一、晴天 4K MV 都是第 3 栏（MMS 原样）更准，标「推测」的行全是回退错了；4K MV 中段有特殊编排，不作判断依据。→ 取消推测兜底。
- 首行被放进前奏：人声轨前 29 s 能量为 0，MMS 仍把首行放在 2.8 s（`*` 通配符吞掉了真正的首行演唱）。加静音门控（静音帧只允许 blank / `*`）后首行 29.3 s；5 首试听歌其余行变化全 < 0.3 s；7 首真值 37 ms / 98% 不变。
- 坑（清洗）：「录音室 : xxx」（冒号前有空格）和「ISRC …」行没被清洗，被对齐到尾奏。
- 用户给 3 首常规投稿（为你写诗、跳楼机、没能成为你的白马）。一条命令（`align_lrc.py`）每首约 2 min 跑完。为你写诗、白马和原轴平移后 80~88% 的行差在 0.3 s 内；跳楼机副歌 4 行被挤到每字 0.08 s（唱不出来的速度），原歌词才是对的。
- 挤压回退：中文中位字距 < 0.15 s 的行改用「原歌词时间 + 整首偏移」。14 首里只命中孤勇者 1 行、跳楼机 4 行、白马 1 行，外加清洗漏掉的制作人员行；剪辑版 / 原轴粗糙的歌没有误触发。试听页 `listen/new.html` 第 3 栏，待人耳确认。
- 用户试听挤压回退：跳楼机两栏都卡住，带「推测」的行基本都不准（原歌词时间 + 均匀填充跟不上）；白马「对我是惩罚」是误判，回退后反而变差。卡住的根源是前一行行尾「好像跳楼机」被拉长，它本身没被判为挤压。
- 改为局部重对齐：挤压行连同前一行，在原歌词时间附近的窗口里重新做强制对齐。跳楼机 4 行的行起点都落到原歌词时间 + 偏移 0.1 s 以内；误判行重对齐后不变。闸：前一行行起点挪动 > 1 s 不收（江南现场版「心碎了才懂」曾被挪 17 s），挤压行重对齐后必须变松。7 首真值歌上 > 1 s 的行 2 → 1，其余不变。
- 用户试听局部重对齐：跳楼机「让我突然地升空又急速落地」仍卡在「升空」，然后闪过去，再慢慢追上。用户怀疑是英文「baby」导致的。排查结果：单独对 80 ~ 96 s 算概率时这句是对的，问题在 90 s 的 15 s 块边界（模型在块边缘只看到一侧上下文）。只换一种切法会让别的句子压在边缘上，改成两种起点各切一遍取平均后，跳楼机 0 行需要修，真值指标基本不变。
- 配错判据：15 首对得上的行置信度中位数 0.277 ~ 0.670、局部重对齐采纳 0 ~ 2 行；4 组故意配错的 0.161 ~ 0.215、4 ~ 12 行。两条同时满足才判错，两边 100% 判对。
- P1 服务端 `biu-align-server`：独立服务（不连累同步），登录复用同步服务的 token；只接受 bvid + cid，B 站请求串行、间隔 3 s、只用非 PCDN；单并发队列 + 每人每天 20 首；审核员通过 / 填原因打回。端到端：跳楼机 106 s 完成，提交、通过、匿名读取都通；配错歌词 102 s 后返回「歌词和这首歌的音频对不上」。
- 坑：**Biu 播放器的歌词高亮也吃同一个进度事件**，App 里同样有 0~250 ms 随机迟切。P2 做客户端时要按帧取播放位置，否则对齐再准，用户看到的仍是「时快时慢」。

## 3. 已确认的结论（不要再重新争论）

- 不在用户机器上跑 Python / 模型；不让客户端上传音频。
- 整首歌不能直接喂 WhisperX 这类通用语音对齐；要么用支持歌声的 ASR，要么先分离人声。
- 对齐算法用 MMS_FA 强制对齐（第 4 轮对标开源后替换了 DTW），不换 lyric-align，不回自研。
- 不用「回退到平移估计、标推测」做兜底：人耳试听证明回退行几乎都是改错（第 4 轮）。以常规歌曲为准，不为剪辑版 / 特殊编排专门处理。
- 由用户主动触发，可预览、可还原；失败不自动重试，错误文案分类。
