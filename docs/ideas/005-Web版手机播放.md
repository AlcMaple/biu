# Web 版手机播放：踩过的坑与推翻过的结论

记录反复权衡的设计决策、走过又被推翻的路，以及后来被证伪的旧结论。开发日志只写结论和效果，这些过程性的东西放这里，避免下次重走一遍。

## 被证伪的旧结论：「断音的根因是缓冲配额」

2026-08-26 的第一条日志写过「iPhone 给网页音频的缓冲配额极小，大窗口/整段喂都会撞配额」。后来的线上日志推翻了这个说法：同一台设备把整首 89 秒、2.34 MB **一次性**喂进同一个缓冲区， **没有**报配额。设备装得下，问题是「装错了地方」。

配额报错的真正触发条件是**数据离播放位置太远**，不是字节数超了。所以：

- 判断是不是配额问题之前，先确认播放位置是否落在已送到的范围内；
- 「小段喂 + 严格窗口」这套做法本身仍然保留——它对控制内存驻留是有效的，只是它并不是断音的解药。

## 推翻的方案一：带位置续播时一律退回原生播放

最早的修法是「只要需要从中间某个位置开始播，就不走自己送数据那套，交给手机原生下载」。它确实能消掉崩溃，但把「无声」换成了「拖进度条要等十几秒」——而原生播放起播慢正是当初要自己送数据的原因。等于绕了一圈回到起点，和「跳转要快」的目标直接冲突。已撤回。

**教训**：修的是崩溃不是体验。一个把已知问题换成另一个已知问题的方案，不算解决。

## 自己造出来又修掉的三个问题

补「从任意位置开始取」这个能力时，一次自查里发现三个都是自己新引入的：

1. **定位时顺手多读的那段被整块喂进去**。那段有几百 KB，一次性喂等于把防配额的分片机制废掉，正好重新踩回配额坑。改成一律按固定大小切片喂。
2. **续流的字节范围没判文件尾**。扫描窗口一旦读到文件末尾，续流就会请求一个越界范围，真实服务端返回 416，白白掉回兜底路径。
3. **拖进度条会引发取流风暴**。两端进度条用的都是连续触发的拖动事件，不做合并的话拖一次会重新取流六次。加了合并；后来又发现点击跳转时按下和抬起各触发一次、间隔超过合并窗口，于是再加了「同一目标不重复取流」的判断。

**教训**：给一条链路补能力时，要回头检查这条链路原有的每一条约束是否仍然成立。

## 写过又删掉的假测试

同一轮里写出过三条恒真的测试：测试环境里那套「自己送数据」的机制根本没启用，所有断言都不成立也能通过。后来抽出一个能真正启用它的测试夹具重写了两条，删掉一条实在测不出的。

还有一次把「单首循环播完会卡住」当成了自己引入的回归写进日志，实际推演下来那条路径本来就不会卡——外层还有一次播放调用会兜住。改动保留了（更直接），但结论已更正。

**教训**：新测试写完要故意把修复改坏一次，确认它真的会变红。恒真的测试比没有测试更糟，因为它给的是假的安全感。

## 已知但未解决

**为什么会在播放中途突然重新挂载一次**，日志里没有记录到起因。已经在几个会静默重新挂载的路径上补了日志，等下次复现时定位。就算不知道起因，现在这条路也只是「一秒内重新取流并接着播」，不会再变成无声二十多秒。
