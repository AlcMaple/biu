# 自动更新发布指南

> 保存在仓库外、权限为 `600` 的私有运维配置中。模板见 [`ops/production.example.env`](../../ops/production.example.env)。

## 安全模型与边界

Windows 的首次安装包没有公开受信任的 Authenticode 发布者身份，用户可能看到 SmartScreen 警告

首次手动安装后，之后的 Windows NSIS 更新走以下链路：

```text
HTTPS latest.json → 应用内置 Ed25519 公钥验签 → SHA-512 校验完整安装包 → 用户确认安装
```

- HTTPS 防止传输链路被篡改
- Ed25519 防止更新服务器或 SFTP 发布账户被攻破后伪造更新清单
- 禁用差分下载；客户端只下载完整安装包并按已验签清单中的 SHA-512 校验
- 这不能让未签名的首次安装包获得 Windows 发布者信任，也不能抵御发布私钥本身泄露

## 私钥管理

私有配置至少提供以下变量：

```bash
BIU_UPDATE_SIGNING_KEY=/private/update-signing-ed25519.pem
```

- 私钥文件权限必须为 `600`，仅保留在发布者的私有开发机；不进 Git、不传服务器、不发聊天。
- 正常发版只使用已有私钥。`node dev_tools/generate-update-signing-key.js` 仅用于首次建立新产品身份或经过批准的密钥轮换；它会生成一把新私钥，轮换还需要发布新的手动安装过渡版。
- 把私钥放入加密的离线备份。私钥丢失不会泄露历史版本，但将无法签发后续自动更新。

## 发布前提

1. 更新源只能使用 HTTPS。
2. 发布账户必须是独立 SFTP-only 账户，无 shell、无 root、不能读取业务数据或修改反代。
3. 发布认证只能使用 SSH key 或 SSH agent，禁止密码认证。
4. 私有发布密钥必须与应用内置的 Ed25519 公钥匹配；上传工具不匹配即中止。
5. Windows 自动更新只发布 `win-setup-*.exe`，不为便携版启用自动安装。

## 每次发布

在已授权终端加载私有配置后执行：

```bash
: "${BIU_OPS_CONFIG:?缺少私有运维配置}"
set -a
. "$BIU_OPS_CONFIG"
set +a

git status --short
pnpm install --frozen-lockfile
pnpm build
node dev_tools/upload-update.js --win
node dev_tools/verify-update-manifest.js --x64
```

上传工具会先上传安装包，再计算 SHA-512，生成并用 Ed25519 签名 `latest.json`（arm64 则为 `latest-arm64.json`），最后通过临时文件加原子改名发布清单。不要手工改写或上传这两个 JSON 文件。

## 首次上线与真实验证

1. 发布后，让测试机从旧版手动安装 Windows NSIS 安装包
2. 提升版本并发布
3. 在装有上一版的测试机点击“检查更新”，确认显示可更新；下载后退出安装
4. 重启后确认版本为最新版本。篡改 `latest.json` 或安装包时，客户端必须拒绝更新

## 事故处理

- SFTP 发布 key 泄露：立即撤销该账户对应公钥，保留日志并新建发布 key
- 更新私钥疑似泄露：暂停自动更新；当前客户端不能再信任该密钥，必须发布新的手动安装过渡版并内置新公钥
- 清单或安装包异常：停止发布写入、保留证据，恢复最后一个已验证的清单；不要直接删除现场文件
